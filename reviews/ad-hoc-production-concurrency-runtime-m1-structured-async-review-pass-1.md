### Non-blocking residual risks

- **`task.select` branch-name flexibility vs. doc** — `crates/sifr_lowering/src/lower/task_calls.rs:287-306` accepts any two unique keyword names (e.g. `one=…, two=…` is exercised by `expressions_tests/ownership_and_async.rs:467`), but `internal_docs/async_concurrency_model.md:370` writes the signature literally as `*, first: Task[…], second: Task[…]`. The disclosure further down does call out that names are positional labels for `Select2.First/Second`, so this is internally consistent, but the signature line gives the impression that `first`/`second` are reserved. Consider either restricting the impl to those two names or softening the signature wording in a follow-up.
- **`async_with.rs` is at 894/900 lines** — touching it again will push over the maintainability cap. The next change in this module should split it (the four scope-exit/`stmt_contains_*` helpers are an obvious responsibility-based extraction candidate).
- **Group-name-keyed tracking persists across sequential same-name scopes** — `ctx.task_group_error_types`, `ctx.task_handle_group_owners`, and `ctx.task_groups_not_proven_open` are never cleared when an `async with task.TaskGroup() as group` body finishes (`crates/sifr_lowering/src/lower/async_with.rs:838-855` only saves/restores `active_task_owner_depth` and `active_task_owner_bindings`). This is pre-existing behavior, not an M1 regression, but with M1 making `spawn_scoped` rely on the same name-keyed tracking, a function that opens two sequential `task.TaskGroup() as group` scopes with different error shapes could see a spurious "children must share one error type" message. Worth a small fixture or explicit cleanup on scope exit before more code grows on top of it.
- **Worktree contains unrelated network/HTTP artifacts** — per the review instructions these were excluded from the M1 PR scope, but the PR author will need to be careful that those changes do not slip into the same commit/PR.
