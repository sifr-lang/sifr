## Residual risks (non-blocking)

1. **Sibling reassignment-mismatch sites still on the bridge.** [crates/sifr_hir/src/lower/statements.rs:1551](../crates/sifr_hir/src/lower/statements.rs:1551) and [crates/sifr_hir/src/lower/tuple_unpack.rs:112](../crates/sifr_hir/src/lower/tuple_unpack.rs:112) emit `type mismatch: cannot assign '{}' to variable '{}' of type '{}'`, which the inventory maps to the same `TypeErrorKind::TypeMismatch` family ([internal_docs/diagnostic_emission_inventory.md:69](../internal_docs/diagnostic_emission_inventory.md:69)) but without the canonical `expected/got` wording. They are correctly out of scope under the slice's "expected/actual" framing and have no e2e fixture pinning them today, so they cannot regress this slice. Worth tracking explicitly in the next slice (assignment-shape / tuple-unpack call sites) so they don't get forgotten when the `CompilePhase::TypeCheck => SIFR-TYPE-0001` bridge is finally deleted; otherwise either the bridge deletion or `check_diagnostic_code_coverage` will surface them late.

2. **Registry `message_template` divergence for `SIFR-TYPE-0003`.** Active entry template is `conditional branches have incompatible types: {then_type} and {else_type}` ([crates/sifr_diagnostics/src/codes.rs:587](../crates/sifr_diagnostics/src/codes.rs:587)), but the preserved emission renders `if expression branches have incompatible types: …`. The slice correctly preserves the rendered text per its scope, so this is not a regression. The phase issue does require compact grouping and recovery limits to use `message_template` rather than rendered text ([issues/ad-hoc-…:1121-1122](../issues/ad-hoc-semantic-diagnostic-code-taxonomy-and-structured-hir-diagnostics.md:1121)); when that grouping work lands (later in `diag_4a` follow-ups or `diag_10`), the renderer will see the abstract template diverge from the human message. Either align the message template with the rendered emission in a registry-hygiene slice or align the rendered emission with the template — but only after the phase clarifies which side is canonical for this code.

3. **Bounded-recovery fixture stability.** [bounded_multi_error_recovery.sifr](../crates/sifr/tests/e2e/fail/bounded_multi_error_recovery.sifr) declares two `SIFR-TYPE-0002` substrings against three would-be emissions; correctness depends on the recovery cap and substring matcher continuing to admit the two declared expectations. That contract pre-dated this slice and is not perturbed by re-keying — flagged only because re-keying the cap-related fixture without re-running the cap-summary path would have been the most likely place for a silent regression, and the supplied `--profile quick` evidence covers it.
