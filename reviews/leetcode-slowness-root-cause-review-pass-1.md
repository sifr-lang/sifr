## Finding 1 — F1: Wrong Count of Slower Problems (Required Fix)

The document states:
> "75 complete problems have at least one fixture where Sifr is slower than Python"

Ground truth from re-reading all 838 `.hyperfine.json` files in `.raw/`:
- **78 problems** show Sifr slower at one or more sizes, not 75.
- The 3 extras are problems where the largest fixture succeeded for Python but had a corrupted or Python-only hyperfine file for Sifr.

The document also states:
> "53 problems failed build, correctness, timeout, or validation"

Ground truth: **52 problems** have no hyperfine data for Sifr at any size (i.e., true failures). The document's 53 count is off by 1.

The internal arithmetic (`75 + 53 = 128`) does not reconcile with the actual problem universe of ~273 complete + 52 failed = ~325 total. The correct count is approximately `78 + 52 = 130`.

**Fix**: Update the counts to 78 and 52. The exact numbers are less important than the document not claiming 75 when it is 78, and not adding 53 when it is 52.

## Finding 2 — F2: Failed Problems Not Listed (Required Fix)

The document acknowledges 53 failed problems but names only two (`0002`, `0006`, `0007` from the type-error run.log excerpts) and the correctness case `0212`. The other 50 type-error and build-error failures are invisible.

## Finding 3 — F3: Classification Errors in Core Table (Required Fix)

The table's primary owner column is the document's most consequential content. Several entries are wrong.

### F3a: `0015_3sum` — Wrongly labeled "Mixed", should be "LeetCode Sifr code"

The document says "Python and Sifr may differ around duplicate handling/storage" and calls it Mixed. The source code shows a **fundamental algorithmic mismatch**:

- **Python**: O(n²) two-pointer after sorting — standard optimal solution.
- **Sifr**: O(n³) brute-force triple-nested loop with `seen` deduplication dictionary.

The Sifr implementation is not a variant of the Python algorithm; it is a completely different, asymptotically worse algorithm. The root cause is **LeetCode Sifr code**, not compiler. There may be additional compiler overhead, but it is not the dominant factor — the algorithmic gap is.

**Fix**: Reclassify as **LeetCode Sifr code**. Root cause: brute-force instead of sorted two-pointer.

### F3b: `0239_sliding_window_maximum` — Wrongly labeled "LeetCode Sifr code (verify)", should be "LeetCode Sifr code" with high confidence

The document says "Python likely uses deque/monotonic queue; verify Sifr implementation parity before compiler work." The Python source confirms it uses `collections.deque` for a monotonic queue — O(n) time. The Sifr source is an explicit O(n·k) brute force with a sliding window over every position. There is nothing to verify; the algorithm mismatch is obvious from source inspection.

**Fix**: Reclassify as **LeetCode Sifr code** immediately, not as a "verify before compiler work" item. Root cause: brute-force instead of monotonic deque.

### F3c: `1834_single_threaded_cpu` — Wrongly labeled "LeetCode Sifr code", should be "LeetCode Sifr code" (correct direction but underconfident)

The document flags this but does not assert it confidently. From source comparison:
- Python: O(n log n) heap-based scheduling.
- Sifr: O(n²) scan for minimum remaining task.

**Fix**: The classification direction is right, but the root cause note should say "O(n²) linear scan for min instead of heap."

### F3d: `1046_last_stone_weight` — Wrongly labeled "LeetCode Sifr code (slight slowdown)", should be "LeetCode Sifr code"

The document says "slight Sifr slowdown at largest size suggests data-structure parity should be checked first." Source comparison shows:
- Python: O(n log n) heap-based.
- Sifr: O(n² log n) repeated sorting with `stones.sort()` on every iteration.

This is not a "slight data structure parity" issue — it is a clear O(n log n) vs O(n² log n) algorithm gap. The 0.784x ratio (Sifr ~28% slower) is consistent with that gap being real but the constants helping Sifr.

**Fix**: Reclassify as **LeetCode Sifr code**. Root cause: repeated `stones.sort()` instead of heap.

### F3e: `0146_lru_cache` — Correctly labeled "Mixed", but the algorithmic divergence is more severe than stated

The document calls it Mixed and notes "class methods that emit heavy HashMap/list clones." The source comparison shows:
- Python: Doubly-linked list nodes with Python object references (O(1) insert/remove via pointer surgery).
- Sifr: Pure dict-based integer-node LRU with 5 separate dicts (`key_to_node`, `node_key`, `node_value`, `prev`, `next`). Every `detach`/`insertAfter` rebuilds entire dicts.

The Sifr approach is not just a compiler clone problem — it is an algorithmic redesign that trades pointer-surgery O(1) for full-dict-copy O(n) per operation. The classification is directionally correct but the root cause note understates the algorithmic divergence.

**Fix**: The "Mixed" label is defensible, but the root cause should note "Sifr uses integer-node dict-based LRU with full-dict clones on state updates; Python uses doubly-linked list with O(1) pointer surgery."

### F3f: `1472_design_browser_history` — Correctly labeled "Mixed", but the source shows two distinct Python implementations

The Python file contains **two separate `BrowserHistory` class definitions** — one using a doubly-linked list, one using a list-with-index. This is a fixture-generation artifact (both versions are tested). The Sifr version uses the list-with-index approach. The algorithmic comparison should note this.

**Fix**: Add a note in the root cause that Python's benchmark file contains two implementation variants and the comparison may be against the doubly-linked-list version.

## Finding 5 — F5: String Indexing Claim Overstates Compiler Responsibility (Subtle)

The document attributes 22 problems to "C1: String Indexing And Character Iteration" and says emitted Rust "uses `s.chars().nth(i)` in loops." This is a valid compiler issue. However, the classification of some problems as "Compiler" for string overhead understates where the real issue is the Sifr code's use of patterns Python handles efficiently:

- `0402_remove_k_digits`: Python uses a stack of integers; Sifr uses string/list operations that trigger string indexing. The string indexing is real, but so is the algorithmic choice to work with strings instead of integers.
- `0763_partition_labels`: Python and Sifr are nearly identical in structure. The string indexing cost is genuine compiler overhead.

The C1 track is valid but needs to distinguish between cases where string indexing is an unavoidable consequence of the problem's nature vs. cases where Sifr code chose a string-heavy approach that Python solved differently.

**Fix**: Add a note in the C1 track that for `0402`, the dominant issue is the choice to work with strings/char indexing rather than integer-stack semantics. Separate "inevitable string overhead" from "string-heavy approach choice."

**Fix**: For each L1 problem, add the Python complexity and Sifr complexity side by side in the root cause column.
