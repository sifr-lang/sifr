## Review summary

**Result: PASS — no material blockers.**

The M3 implementation meets the phase contract:

- **Phase-contract compliance**: `LocaleId`, parsing/canonicalization, likely-subtag (via `LocaleCanonicalizer::new_extended` / `LocaleExpander::new_extended`), object-scoped `NumberFormatter`/`DateTimeFormatter`/`PluralRules`/`Collator`, and read-only `host_locale() -> Option[LocaleId]` are all present. Display names correctly deferred. No `setlocale`-style process-global mutation. `sifr.locale`/`gettext` remain `deferred-to-adapter-phase` and bare CPython imports remain blocked.
- **Typed errors / no panics**: Runtime (`crates/sifr_runtime/src/i18n.rs`) routes every fallible ICU surface through `try_new`/`try_from_str`/`Decimal::from_str`/`Date::try_new_iso`/`Time::try_new` and integer `try_from`, mapping each to `Result<_, String>`. Codegen (`crates/sifr_codegen/src/intrinsics/registry/i18n.rs`) wraps these with `map_err` into `LocaleIdError`/`FormatError`/`PluralRulesError` struct literals. No data-dependent `unwrap`/`expect`/`panic!` reaches user-controlled locale/format strings.
- **Feature gating**: `crates/sifr_runtime/Cargo.toml` puts all 5 ICU deps behind `optional = true` and the `i18n` feature; `crates/sifr_runtime/src/lib.rs` `#[cfg(feature = "i18n")]`-gates the new module. `features.rs` `RuntimeFeatures` infers `i18n` correctly from `sifr.i18n` module use or any `IcuX` `StdlibFeature`, and `runtime_dependency_can_enable_unicode_and_i18n_together` verifies coexistence with M2's `unicode` feature.
- **Generated Cargo dependency behavior**: New tests `i18n_module_emits_runtime_and_icu_dependencies` and the unicode+i18n combination test prove deterministic, deduplicated generation and feature merging on `sifr_runtime`.
- **Public API shape**: `lib/sifr/i18n.sifr` exports the required surfaces (`LocaleId`, parse/canonicalize/maximize/minimize, formatters, `host_locale`) plus style/strength/rule-type constants. Object-scoped, no globals. The intrinsic table in `crates/sifr_stdlib/src/i18n_core.rs` matches.
- **`host_locale` host-limited semantics**: `host_locale` reads `LC_ALL`/`LC_MESSAGES`/`LANG`, skips `C`/`POSIX`, strips codeset (`.UTF-8`) and `@modifier`, normalizes `_`→`-`, and only returns a locale string after canonicalization succeeds. It is exposed solely through `sifr.i18n.host_locale()`; nothing in the M3 surface threads it into text-I/O defaults, preserving the M1 "no implicit locale encoding" guarantee.
- **Tests/docs**: Runtime unit tests cover canonicalize/maximize/minimize, Bangla decimal output, date/time medium, plural cardinal/ordinal, and Spanish-traditional vs English-primary collation. The e2e `text_i18n_locale_formatting.sifr` exercises happy-path + invalid-locale/number/plural error paths + tolerant `host_locale` assertion. `verification/stdlib/text_i18n_dependency_decisions.md`, `text_i18n_m3_traceability.md`, and the substrate inventory record the ICU4X 2.2 decisions and trace each backlog item to a fixture. The execution ledger records M3 PR-level validation (`cargo test -p sifr_runtime --features i18n`, codegen `i18n`, stdlib `features`, e2e fixture).
- **File sizes**: All touched first-party files are well under 900 lines (`registry.rs` ~663, `features.rs` ~685, `i18n.rs` runtime ~231, registry/i18n.rs ~150, `i18n_core.rs` ~82, `i18n.sifr` ~165).

## Non-blocking observations (not gating PASS)

1. **Locale errors inside formatters surface as `FormatError`/`PluralRulesError`** when `parse_locale` fails (e.g., `NumberFormatter(LocaleId("bogus")).format(...)`), not `LocaleIdError`. This is consistent with the dependency-decisions doc ("`FormatError`") and contract, but it does mean users can't distinguish "bad locale" from "bad value" without inspecting the message. Worth noting in M5 docs.
2. **Per-intrinsic ICU `additional_required_features` is overinclusive** — `i18n_format_number` only needs `IcuDecimal`+`IcuLocale` at the runtime call site, yet it requests all five `IcuX` features. Harmless (the runtime `i18n` Cargo feature unifies them anyway), but if a future encoding-expansion phase wants leaner generated manifests, this could be tightened.
3. **`clippy::unwrap_used` may not have been exercised with the `i18n` feature on**: the M3 ledger lists `cargo test -p sifr_runtime --features i18n i18n` and a workspace `cargo clippy --workspace -- -D warnings`, but the latter doesn't enable optional features. The two `.unwrap()`s in `i18n.rs` tests (line 228–229) are gated by `#![cfg_attr(test, allow(clippy::expect_used))]`, which does not cover `unwrap_used`. Consider either adding `clippy::unwrap_used` to the same `cfg_attr` line or running `cargo clippy -p sifr_runtime --features i18n --tests -- -D warnings` in M3 validation.
4. **Inventory status drift**: `verification/stdlib/text_i18n_substrate_inventory.md` and `.json` still say `Status: M0 baseline.` / `"status": "m0-baseline"`, despite M1–M2.5 closure and M3 in progress. The dependency-decisions doc is correctly stamped; the inventory should be too (probably a one-line update in M5).
5. **`Style`/`strength`/`rule_type` remain stringly-typed** at the Sifr surface (constants like `COLLATION_PRIMARY: str = "primary"`). The phase contract permits this — typed `LocaleId` and object-based formatters are what it requires — and the runtime rejects unknown values with typed errors. If future work wants enum-style values, the intrinsic interface is already string-based so the migration is local.

These can be addressed in M5 doc/validation work or follow-ups; none blocks M3 closure.
