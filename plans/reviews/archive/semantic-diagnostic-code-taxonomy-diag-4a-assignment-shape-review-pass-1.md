Branch: `codex/semantic-diagnostics-diag-4a-assignment-shape`

This is exactly the residual-risk #1 site the prior slice flagged in [reviews/…-type-mismatch-review-pass-1.md:37](../reviews/semantic-diagnostic-code-taxonomy-diag-4a-type-mismatch-review-pass-1.md:37).

## Residual risks (non-blocking)

1. **Sibling tuple-unpack-shape sites in for-loop context still on the bridge.** [crates/sifr_hir/src/lower/statements.rs:2105](../crates/sifr_hir/src/lower/statements.rs:2105) (`for loop tuple target expects {N} element(s), iterable yields {M}`) and [crates/sifr_hir/src/lower/statements.rs:2118](../crates/sifr_hir/src/lower/statements.rs:2118) (`for loop tuple target expects iterable elements of tuple type, got '{ty}'`) are the same conceptual `TYPE-0009` family ("Tuple or list unpacking shape mismatch") but in for-loop destructuring context. They currently fall through to `ctx.error(...)` and remain on the legacy bridge. The slice's framing was assignment-form-centric ("HIR reassignment type-mismatch and tuple-unpack shape diagnostics") so deferring is defensible, and no e2e fixture pins them today (verified via `grep -rn 'for loop tuple target' crates/sifr/tests/`), so this slice cannot regress them. Worth tracking explicitly for a follow-up slice; otherwise either bridge deletion or `check_diagnostic_code_coverage` will surface them late.

2. **Star-unpack list-shape site still on the bridge.** [crates/sifr_hir/src/lower/tuple_unpack.rs:169](../crates/sifr_hir/src/lower/tuple_unpack.rs:169) (`star unpacking requires a list type`) is the list-shape variant the registry description for `SIFR-TYPE-0009` explicitly covers ("Tuple **or list** unpacking shape mismatch"). It was not migrated in this slice. Same defense as #1: no e2e fixture pins it (grep confirms zero hits in `crates/sifr/tests/`), so no regression risk, but it's a natural part of the same conceptual scope and should be picked up next.

3. **Coverage gap on two migrated sites.** The fixtures cover the count-mismatch (`expected N values, got M`) and basic reassignment paths, but the migrated `cannot unpack non-tuple type 'X'` (`tuple_unpack.rs:75-79`) and per-element tuple-unpack reassignment (`tuple_unpack.rs:115-124`) are now `SIFR-TYPE-0009`/`SIFR-TYPE-0002` without representative e2e fixtures. The unit tests at [crates/sifr_hir/src/lower/expressions_tests.rs:1697-1704](../crates/sifr_hir/src/lower/expressions_tests.rs:1697) and the existing `TYPE-0002` fixtures (which all flow through `lower_ann_assign` or `lower_return`, not the tuple-unpack reassignment branch or the non-tuple unpack branch) do not exercise these paths through the harness pipeline. Future regressions on either of those branches would not be caught by the fail-corpus gate. Adding two more fixtures (a `cannot unpack non-tuple` case and a tuple-unpack-element-reassignment case) is small and would close the gap; non-blocking because the slice's framing required at least one representative fixture per code, which is satisfied.

4. **Registry `message_template` divergence carries forward for `SIFR-TYPE-0009`.** Active entry template is `cannot unpack {actual_count} value(s) into {expected_count} target(s)` ([crates/sifr_diagnostics/src/codes.rs:653](../crates/sifr_diagnostics/src/codes.rs:653)), but the preserved emissions render `tuple unpacking: expected {targets} values, got {elems}` and `cannot unpack non-tuple type '{ty}'`. The slice correctly preserves the rendered text per its scope, so this is not a regression. The phase issue still requires compact grouping and recovery limits to use `message_template` rather than rendered text; when that grouping work lands, the renderer will see the abstract template diverge from the human message, and the registry's representative fixture (`tuple_dynamic_list_shape.sifr` — currently a `tuple()`-constructor case still on `SIFR-TYPE-0001`) will need to be reconciled. This is the same kind of divergence flagged for `SIFR-TYPE-0003` in the prior slice's residual risk #2; resolution belongs to a registry-hygiene slice, not this one.

## Verdict

Satisfied / no blocking findings. Diagnostic taxonomy mapping is correct (`TYPE-0002` for assignment-shape `TypeMismatch`; `TYPE-0009` for tuple-unpack shape including the non-tuple-type sub-case), fixture coverage is sufficient for the slice's stated "preserve text + lock code" scope (two representative fixtures, both using the harness's joint code+substring contract), the diff is appropriately bounded, and explicitly out-of-scope surfaces (containers, `tuple()` constructor, CALL-family argument shape, annotation shape, bridge deletion) remain unperturbed. The for-loop tuple-unpack and star-unpack siblings are within the conceptual scope but defensibly deferred under the slice's assignment-form framing; flagged as residual for the next slice's pickup so they don't get forgotten before the bridge is finally deleted.
