# Review: Phase 40 site stable-release-facts rendering

Worktree unmodified (verified). Extra non-mutating validation I ran: a byte-exactness build check in a throwaway copy (public asset → `dist` is verbatim, confirmed), and a cross-runtime parity run of `render-stable-release-page.mjs` against canonical facts + `verify_public_stable_docs.py` + `release_governance.py validate --kind site-facts` (all pass; `wx` overwrite refusal exits 2).

## Blockers

**1. Page materialization is unconditional and breaks every non-GA (preview) site release.**
`release-site.yml:190` runs `generate-site-facts` on every dispatch, but `generate_site_release_facts` hard-fails when the index is not GA-active (`verification/areas/distribution_release/governance/release_plan.py:394-396`, "site facts require an active GA index"). The same workflow explicitly declares `preview:beta` a valid live state (`release-site.yml:397-403`), and `.github/workflows/release-publication.yml:431-434,692` dispatches this workflow with `dispatcher_default_channel=beta` while `ga_status == "preview"`. So an alpha/beta publication against a preview index fails the site job outright. Two knock-on failures under `set -u` in the same scenario: `${STABLE_PAGE_SHA256}` is unbound at `release-site.yml:339-341` and `453-454`. All three touchpoints need one explicit, attested condition (materialize/verify iff the live index is GA-active, cross-checked against `DISPATCHER_DEFAULT_CHANNEL == stable` and the pre-deploy `live_ga_status` re-check) — not a silent skip.

**2. The renderer runs on an unpinned Node in the release path.**
`node scripts/render-stable-release-page.mjs` executes at `release-site.yml:243`, before `actions/setup-node` at line 308. CI validates the renderer on `.node-version` (24); the release run uses whatever the `ubuntu-24.04` image ships. The attested `STABLE_PAGE_SHA256` therefore comes from an unpinned toolchain, and CI's guarantee doesn't cover it. The renderer only needs Node builtins, so moving the step after `setup-node` (before or after `npm ci`) is sufficient.

**3. The cross-repo contract does not govern this change, and is not updated.**
`verification/areas/distribution_release/fixtures/site_release_contract.json` still pins `workflow_commit: 07d88cc…` / `workflow_sha256: 7a27abaf…` — the pre-change bytes — so `verify_site_workflow_identity.sh` will reject the new workflow and this change is inert until the Sifr repo lands the new pin. Worse, the fixture's `stable_documentation` block names only the Sifr-side renderer (`scripts/distribution/render_stable_release_docs.py`, `docs/releases/stable.mdx`); nothing in the Sifr repo asserts that the site workflow renders `/releases/stable` from schema-v2 facts. The "no schema-v1 reader / no fallback / no raw rendering" guarantee is enforced only by the site repo's own CI, unlike dispatcher generation which is pinned by fragment assertions in `site_release_workflow_contract.sh`. Also note the protected tag `sifr-release-site-stable-distribution` sits under a ruleset whose rules are `deletion` + `update`, so repointing it at the new commit needs a new tag plus new ruleset id/`updated_at` — all of which must land in the fixture and the identity helper. The incident-publication finding cannot close on the site PR alone.

**4. `README.md` not updated.** It documents this workflow's contract precisely (lines 55-78: "regenerates the four public dispatchers… and never writes release metadata", the preview/stable default-channel rule, the fail-closed and post-deploy verification rules). It says nothing about the governed `/releases/stable` page, its facts source, its GA-state precondition, or the new mutation-boundary allowance.

## Medium

**5. The page bytes are never tied to the Sifr-side canonical facts.** Dispatch carries `publication_facts_sha256` but not the Sifr-side `site_facts_sha256`. The site re-derives facts, and they are in fact byte-identical (`incident_publish.py:87-96` uses `summary["successor"]["plan_sha256"]`, which is exactly the `--release-plan-sha256` the dispatcher passes for both rollback and roll-forward), but nothing asserts it. The only cross-repo tie is `verify_public_stable_docs.py`, a substring check that would accept a page containing arbitrary extra or contradictory content. Passing `site_facts_sha256` as a dispatch input and comparing the regenerated bytes would make the provenance exact.

**6. JS validator diverges from the canonical schema and the Python validator, with no parity test.** `validateFacts` omits the withdrawal-ordering rule Python enforces (`release_plan.py:469`), does not require canonical bytes (plain `JSON.parse`), and never cross-checks against the governed index. It is also stricter in ways that can fail closed wrongly: `withdrawals[].version` must be `X.Y.Z` though `stable_site_release_facts.schema.json` leaves it unpatterned and Python's `version_channel` accepts alpha/beta (latent today — `release_index.py:250` only permits withdrawing the live stable), and `INCIDENT` is a superset of the index's `^[a-z0-9][a-z0-9-]{2,63}$`. Derive the JS constraints from the schema, or add a test that runs the schema's fixtures through both.

**7. Self-test coverage gaps.** No coverage of: the empty-withdrawals `"none."` branch, the `--facts/--out` CLI path, the `wx` overwrite refusal, multiple withdrawals, or `escapeHtml` actually escaping — every input reaching `escapeHtml` is regex-restricted to safe characters, so the escaping is untested. Nothing exercises a facts file produced by the pinned `generate-site-facts`.

## Low

**8.** Withdrawals are ordered by `sorted(index["releases"].items())`, i.e. lexicographically, so `0.10.0` renders before `0.9.0` on a public page after multiple incidents. Pre-existing in the generator, newly public.

**9.** Duplicate public truth: `docs.sifr.sh/releases/stable` (Mintlify, from `docs/releases/stable.mdx`) renders the same governed facts from committed bytes while `sifr.sh/releases/stable` is now live-rendered, and the new page sets `rel=canonical` to itself. The two hosts can disagree after a rollback until the docs site redeploys.

**10.** Placement inconsistency: renderer in root `scripts/` with a root-`package.json` test, while the sibling `test:install-routing` lives in `apps/sifr-site/scripts` + the site workspace. The page also bypasses the Astro layout and is absent from `sitemap.xml.ts`.

## Verified sound

Step ordering relative to build; `public/` → `dist/` byte-verbatim (empirically confirmed); mutation boundary tightened to the one exact untracked path; permissions unchanged (`contents: read`, read-only `github.token`, no new secrets, no release-metadata write); index provenance re-fetched, `--require-canonical`-validated, and digest-pinned to the dispatch before use; fail-closed write (`wx`, exit 2 on any validation error); no schema-v1 reader, migration, fallback, or raw rendering anywhere; rollback and incident roll-forward both yield a truthful page from the exact activated index; deploy-time and public digest verification are exact; re-runs are deterministic.
