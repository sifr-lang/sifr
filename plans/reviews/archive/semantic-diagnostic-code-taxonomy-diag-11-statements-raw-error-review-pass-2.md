## Check 5: No Fallback Behavior — Non-Name Except Types ✓

In the `Stmt::Try` handler processing (statements.rs lines 401–439):

- When `h.type_` is `Some` and the expression is `Expr::Name`: `error_type` is set, `invalid_error_type_form = false` → normal validation path.
- When `h.type_` is `Some` but the expression is **not** `Expr::Name`: `invalid_error_type_form = true`, `error_type = None` → `RESULT_INVALID_EXCEPT_TYPE` is emitted **and no catch-all flag is set**.
- When `h.type_` is `None` (bare `except:`): `has_catch_all = true` by design — this is correct Python semantics, not a fallback for invalid forms.

Non-name except-type expressions (e.g., `except ValueError() as e:`) are rejected explicitly with `RESULT_INVALID_EXCEPT_TYPE` and do **not** silently become catch-alls. ✓
