## Production-grade acceptance checklist (for this phase and future gates)

For generated runtime code:

1. No emitted `.unwrap(`.
2. No emitted `.expect(`.
3. No emitted `panic!(`.
4. No emitted `unreachable!(` unless explicitly proven unreachable and approved as a documented exception.
5. No emitted lock poisoning panics (`.lock().unwrap()`).
6. All optional/result extraction lowered through explicit safe control flow:
   - `match` / `if let` / `ok_or_else` / `map_err` / typed diagnostics.
7. Full emit sweep across pass fixtures is required gate (not only one demo/main-body slice).
8. Gate must fail on any new emitted panic pattern in production runtime paths.

## Recommended remediation order

1. Remove lock unwraps in preamble/intrinsics (`file_handles`, `logging`) via poison-safe handling.
2. Replace narrowing/coercion unwrap emit sites in `lower_stmt.rs` and `intrinsic_method_emitters.rs` with explicit non-panicking lowering.
3. Replace `is_ok()+unwrap()` in `intrinsics/os.rs` with `match Ok/Err`.
4. Add a dedicated test gate in `sifr_driver`:
   - emit all pass fixtures (or a representative matrix) and assert no forbidden patterns.
5. Align phase docs/checklist language with enforced gate:
   - either keep "data-dependent-only" scope, or explicitly require "zero unwrap in generated runtime code".

## Conclusion

Phase 27 delivered improvements on the originally tested paths (especially indexing main-path emission), but a thorough codegen audit shows generated `unwrap` still exists in multiple runtime helper and intrinsic paths.  
Therefore, under a strict production safety bar of "no generated unwrap", the current state is incomplete.
