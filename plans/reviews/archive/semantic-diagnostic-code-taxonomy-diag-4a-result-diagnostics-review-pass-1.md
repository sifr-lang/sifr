## Findings

### F1 — Taxonomy choices are correct for all four migrated call sites

The three target codes are pre-allocated active registry entries at [codes.rs:88-90](../crates/sifr_diagnostics/src/codes.rs:88) and registered in `ACTIVE_DIAGNOSTIC_CODES` at [codes.rs:1356-1358](../crates/sifr_diagnostics/src/codes.rs:1356); their detailed registry entries at [codes.rs:1036-1068](../crates/sifr_diagnostics/src/codes.rs:1036) declare summaries `"Unused Result value."`, `"Invalid Result error type."`, and `"Invalid raise expression."`, with representative fixtures pointing at exactly the three pre-existing files re-keyed by this slice. Each migrated emission matches the registry slot exactly:

- **unused Result expression** ([statements.rs:189-197](../crates/sifr_hir/src/lower/statements.rs:189)). The check is `matches!(expr_ty, Type::Result(_, _))` against an `Expr` statement — the `#[must_use]` enforcement on `Result` values dropped at statement position. This is the canonical `RESULT-0001` site; the registry summary (`"Unused Result value."`) and message template (`"unused Result value"`) are direct prefixes of the emitted text.
- **invalid Result error type** ([typing_and_functions.rs:514-525](../crates/sifr_hir/src/lower/typing_and_functions.rs:514)). Inside the `Result` arm of `resolve_annotation_expr`'s `Subscript` `match`, after both type arguments resolve cleanly, the second is validated with `is_valid_error_type` ([diagnostics.rs:36](../crates/sifr_hir/src/lower/diagnostics.rs:36)) against the `error_types` set. Failure is a domain-semantic error about *which* type is allowed in the `E` slot, not about the annotation surface — this is exactly the `RESULT-0002` slot. Note that the sibling arity/syntax-shape errors at [typing_and_functions.rs:505-509](../crates/sifr_hir/src/lower/typing_and_functions.rs:505) and [typing_and_functions.rs:528-531](../crates/sifr_hir/src/lower/typing_and_functions.rs:528) correctly remain on `invalid_type_annotation` (`SIFR-TYPE-0007`) — those are annotation-surface errors (subscript shape), consistent with `tuple`/`Callable`/`dict` arity siblings in the same `match` arm and correctly outside this slice's `RESULT-*` scope.
- **string-literal raise** ([statements.rs:246-251](../crates/sifr_hir/src/lower/statements.rs:246)). `raise "msg"` and `raise f"…"` are explicitly disallowed; this is the canonical `RESULT-0003` site. Returns `None` so no further raise lowering happens — preserved from pre-migration behavior.
- **non-Error raise** ([statements.rs:256-264](../crates/sifr_hir/src/lower/statements.rs:256)). Raised value's static type is checked with the same `is_valid_error_type` predicate; failure emits as `RESULT-0003`. Same family as the string-literal case (both are "raise expression is not a valid Error class instance"), so sharing one code is taxonomically correct.

None of these belong to `TYPE-0007` (annotation surface), `NAME-0003` (unknown type), `TYPE-0004` (missing annotation), `TYPE-0002`/`TYPE-0003` (type mismatch), or `PROTO-*`. No sibling code is closer.

## Residual risks

### R1 — Registry `owner_module` for `RESULT-0001` and `RESULT-0002` is less precise than the actual call sites (pre-existing, not introduced by this slice)

[codes.rs:1043](../crates/sifr_diagnostics/src/codes.rs:1043) declares `RESULT-0001` `owner_module = "sifr_hir::lower"`, but the actual call site is in `sifr_hir::lower::statements`. [codes.rs:1054](../crates/sifr_diagnostics/src/codes.rs:1054) declares `RESULT-0002` `owner_module = "sifr_hir::lower"`, but the actual call site is in `sifr_hir::lower::typing_and_functions`. By contrast, `RESULT-0003` correctly says `"sifr_hir::lower::statements"` ([codes.rs:1065](../crates/sifr_diagnostics/src/codes.rs:1065)).

This is **not a regression introduced by this slice** — those owner strings were set when the registry entries were populated in milestone 3 (well before slice 2b.14). Tightening them to `"sifr_hir::lower::statements"` and `"sifr_hir::lower::typing_and_functions"` respectively would make the auto-generated [SIFR-RESULT-0001.md](../docs/errors/SIFR-RESULT-0001.md:12) and [SIFR-RESULT-0002.md](../docs/errors/SIFR-RESULT-0002.md:12) point reviewers/IDE-tooling at the precise file. Cosmetic only — flag for a follow-up registry-hygiene slice (paired with the pre-existing `internal_docs/diagnostic_emission_inventory.md:19,21` rows that already list `statements.rs` and `typing_and_functions.rs` as the owners).

### R2 — Registry `declared_args`/`dedupe_args` for `RESULT-0002` (`error_type`) and `RESULT-0003` (`actual`) are not actually populated by the migrated call sites

[codes.rs:1055-1056](../crates/sifr_diagnostics/src/codes.rs:1055) declares `RESULT-0002` with `declared_args: [arg!("error_type")]` and `dedupe_args: ["error_type"]`. [codes.rs:1066-1067](../crates/sifr_diagnostics/src/codes.rs:1066) declares `RESULT-0003` with `declared_args: [arg!("actual")]` and `dedupe_args: ["actual"]`. The migrated call sites use `error_with_code(code, format!(...))` to inline the value into the message string; they do not populate any structured-arg map. The registry's `declared_args` therefore reach the JSON schema and docs, but the structured args at emission time remain empty.

This is **not unique to this slice** — it is the broader pattern across every other migrated call site in slices 2b.1–2b.13 (the structured-args-at-emission flow is not yet wired through `error_with_code`; the `LoweringError` type only carries `code` + `message`, per [mod.rs:228-235](../crates/sifr_hir/src/lower/mod.rs:228)). The registry's `declared_args` mechanism is consumed by `apply_diagnostic_recovery_limits` for grouping and by docs generation; it doesn't break this slice's correctness, but it does mean dedupe-by-args is currently dedupe-by-message-string. Flag as a phase-wide future-work observation, not a slice-2b.14 blocker.

### R3 — No new HIR unit tests with dual-condition (`code` + `message`) assertions, breaking the slice 2b.13 cadence

Slice 2b.13 ([reviews/semantic-diagnostic-code-taxonomy-diag-4a-generic-annotation-arity-review-pass-1.md:62-70](../reviews/semantic-diagnostic-code-taxonomy-diag-4a-generic-annotation-arity-review-pass-1.md:62) F5) tightened pre-existing `expressions_tests.rs` / `type_alias_tests.rs` assertions to also pin `e.code == Some(DiagnosticCode::TYPE_INVALID_ANNOTATION)`. This slice does not add any `_tests.rs` coverage for the three Result-family codes. A `grep` for `unused Result`, `is not a valid error type in Result`, and `raise requires an Error class instance` across `crates/sifr_hir/` finds matches only in the source files (no pre-existing unit tests to tighten).

The four e2e fixtures are the sole regression anchors for the structured `code` field, and they assert both `code` and message-substring via the harness. So nothing is structurally untested. But the cadence convention (e2e + unit-test dual-condition) is broken here. **Not a blocker** — the slice scope statement does not promise unit tests, and the e2e gate is the canonical contract — flagging as a follow-up if the team wants the cadence preserved (suggest a small `result_diagnostics_tests.rs` or co-located tests in `statements.rs`/`typing_and_functions.rs` asserting `e.code == Some(DiagnosticCode::RESULT_*)` for each of the four call sites).

### R4 — `error_raise_non_error.sifr` and `error_raise_str.sifr` surface a secondary unrelated diagnostic alongside the primary

Both raise-failure fixtures emit, after the primary `RESULT-0003`, a secondary `function 'broken' must return a value of type 'Result[int, ValueError]' on all control-flow paths` diagnostic — because the `return None;` after the raise diagnostic skips the rest of the body, leaving the function with no return path. The harness uses `errors.iter().any(...)` so the primary code+substring still matches and the test passes. Same cosmetic pattern called out in slice 2b.13's R3 ([reviews/semantic-diagnostic-code-taxonomy-diag-4a-generic-annotation-arity-review-pass-1.md:101-103](../reviews/semantic-diagnostic-code-taxonomy-diag-4a-generic-annotation-arity-review-pass-1.md:101)). A future cleanup could swap the raise-only `def broken()` body for a body that also returns a valid Ok value on a non-raise branch, isolating the diagnostic stream. Cosmetic only — not a behavior gap, not a code-coverage gap.

## Recommendation

Merge as-is. The slice cleanly closes the Result-domain emission half of the HIR migration: every Result-family raw `ctx.error` call site within scope is now on the structured `RESULT-*` channel, with one fixture per call site (two for `RESULT-0003`'s two branches), zero collateral damage to the bridge-keyed fixture corpus, and no message-text drift. The remaining unmigrated `ctx.error` sites in `statements.rs` (bare-raise, except-handler shape, exhaustiveness) are correctly out of scope for the `RESULT-{0001,0002,0003}` slot and belong to future slices once their target codes are allocated. After this slice merges, the Result family is fully on the active channel, and the `CompilePhase::TypeCheck => "SIFR-TYPE-0001"` bridge has one fewer family-domain blocking its eventual deletion.
