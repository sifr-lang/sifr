## Findings

### F1 — Taxonomy choice: `SIFR-TYPE-0007` is the correct active code for all seven sites

`SIFR-TYPE-0007` ("Invalid type annotation shape.", [codes.rs:625-635](../crates/sifr_diagnostics/src/codes.rs:625)) carries the family-level meaning "an annotation/type expression *was provided* but is structurally malformed". Each migrated emission is exactly that semantic — the user wrote *something* in the bound/constraint position, but the expression shape is unsupported (not a `Name`, not a `Tuple` of `Name`s, or two mutually exclusive forms specified at once). The split against the adjacent diagnostics is clean:

- "TypeVar bound is a known-name but doesn't conform" → "type 'X' does not implement protocol 'Y' required by type parameter 'T'" stays on the bridge ([typevar_unknown_bound_rejected.sifr](../crates/sifr/tests/e2e/fail/typevar_unknown_bound_rejected.sifr:1) currently pinned to `SIFR-TYPE-0001`) — out of scope per the slice statement.
- "TypeVar constraint is a valid type but the concrete instantiation type doesn't satisfy them" → "type 'float' does not satisfy constraints (int, str) required by type parameter 'T'" stays on the bridge ([typevar_constraints_violation.sifr](../crates/sifr/tests/e2e/fail/typevar_constraints_violation.sifr:1)) — out of scope per the slice statement.
- "TypeVar bound/constraint expression has the wrong *shape* (not a name, not a tuple-of-names)" → `SIFR-TYPE-0007` (this slice).
- "TypeVar declared both `bound=` and constraints simultaneously" — neither shape error in the strict tree-walking sense nor a conformance failure, but the "declaration form is mutually exclusive" semantic still fits cleanly under "invalid type annotation shape" (the *declaration shape* of TypeVar disallows the combination). Bundling it with the rest of the shape errors is reasonable; it can't fire alongside any of the six expression-shape sites because reaching it requires both `bound` and `constraints` to have type-checked their own kw value paths first.

This taxonomy choice is the slice 2b.8 reviewer's R4 recommendation ([reviews/semantic-diagnostic-code-taxonomy-diag-4a-invalid-annotations-review-pass-1.md:126](semantic-diagnostic-code-taxonomy-diag-4a-invalid-annotations-review-pass-1.md:126)) realized verbatim: *"Conceptually these are 'annotation-shape' errors in the broader sense — the user wrote a TypeVar argument whose expression shape is malformed."* The implementation aligns the TypeVar declaration grammar with the 11 sites slice 2b.8 already migrated inside `resolve_annotation_expr`, completing the `SIFR-TYPE-0007` family-level "invalid type/annotation expression shape" coverage.

Each migrated site preserves the prior recovery behavior (positional/keyword Name elements continue to be encoded into `specs`, malformed elements are dropped, the function returns whatever `specs` it has built). The diagnostic identity is the only behavior change.

## Residual risks

### R1 — Site 7 ("bound + constraints conflict") is not strictly an *expression-shape* error

[mod.rs:358](../crates/sifr_hir/src/lower/mod.rs:358) emits `"TypeVar cannot declare both 'bound' and 'constraints'"` — this fires *after* both kw-arg branches have already validated their individual expression shapes. Conceptually it's a "declaration form is mutually exclusive" error, not a "the expression you wrote is malformed" error. Bundling it with the six pure-shape sites under TYPE-0007 is a defensible choice (a TypeVar's *declaration shape* fundamentally disallows the combination, and the alternative would be inventing a new code for a single emission), but a strict reading of the registry's summary line ("Invalid type annotation shape.") doesn't perfectly cover "two valid forms specified together". This is a taxonomy judgment call worth surfacing — non-blocking; the slice statement explicitly enumerates this site as in-scope, and reading "shape" as "structural well-formedness of the TypeVar declaration grammar" makes the bundling consistent. No fixture impact either way.

### R2 — Registry `message_template` for `SIFR-TYPE-0007` does not match any of the seven new emitted format strings

The registry at [codes.rs:631](../crates/sifr_diagnostics/src/codes.rs:631) declares `"invalid type annotation for {annotation_kind}"` with `declared_args = ["annotation_kind"]`. None of the seven migrated emissions follow that template; they each render their own free-form text — the same structural drift slice 2b.8 R2 flagged for the 11 invalid-annotation sites also bundled under TYPE-0007. The current emission API at [mod.rs:228](../crates/sifr_hir/src/lower/mod.rs:228) takes only a pre-formatted `String`, so declared args are documentation-only at this state. The fixtures correctly assert on the rendered text rather than the template, so e2e contracts remain stable. Non-blocking, but the question of how the now-18 distinct emission shapes (11 from slice 2b.8 + 7 from this slice) bundled under TYPE-0007 should fold into a single `{annotation_kind}` placeholder is now larger by ~64% — the future builder-migration slice that resolves [issues/...](../issues/ad-hoc-semantic-diagnostic-code-taxonomy-and-structured-hir-diagnostics.md) will need to enumerate ~18 `annotation_kind` values (e.g., `"typevar-bound"`, `"typevar-constraints-tuple"`, `"typevar-positional-constraint"`, `"typevar-keyword-constraint-element"`, `"typevar-keyword-constraint"`, `"typevar-bound-and-constraints"`, plus the 11 from 2b.8). ### R5 — TypeVar-shape errors will fire twice per site if reached during the dual lowering pass
