## Actionable findings

### 1. Low — publication secrets are exported into third-party and network-fetched executables in the mutation step

`GH_TOKEN` is job-level (`release-publication.yml:116-117`, `contents: write`), and the stable step adds `SITE_TOKEN` and `VSCE_PAT` (`:871-874`). Because step/job `env:` are exported, all three reach every descendant process of `run_stable_publication.sh`:

- `publish_marketplace_extension.sh:88` — `VSCE_PAT="${VSCE_PAT}" "${VSCE_BIN}" publish …`. The third-party `vsce` process inherits the repo-write `GH_TOKEN` and the website deploy `SITE_TOKEN`, neither of which it needs.
- `run_stable_public_smoke.sh:136-137` — `sh "${out}/stable-dispatcher"` and then the freshly installed `sifr` binary run with the same three tokens present.

Both targets are integrity-pinned (the `vsce` tree comes from the approved candidate submodule lockfile installed with `--ignore-scripts`; the dispatcher is `cmp`-verified against the locally generated bytes before execution), so there is no exploit path without first compromising approved evidence — this is defense-in-depth, not a live hole. But it is inconsistent with the boundary this wave deliberately established one step earlier: pass-1's remediation set `GH_TOKEN: ""` on `npm ci` for exactly this reason, then leaves the token in the environment of the actual publish and smoke invocations. Fix is one-line-per-site: prefix the `vsce` call and the dispatcher/`sifr` calls with `GH_TOKEN="" SITE_TOKEN=""` (and `VSCE_PAT=""` for the smoke), the same way `SITE_TOKEN` is already scoped per-command for the site scripts.

### 2. Low — the two schema constraints this wave adds have no negative parity test

`schema_contracts.py:27-150` follows a consistent pattern: every governed conditional gets an explicit rejection test (invalid expiry, incident completed-attempt count, bootstrap stage/`public_smoke` duplicates, drill scenario/duplicate test, mutation transition and `previous_index.generation`, prepare unknown artifact). This wave adds two constraints and tests neither:

- `stable_publication_prepare.schema.json:146-153` — the new `allOf` `if publication_state == "activated" then mode == "resume"`. This is the schema's encoding of a security-relevant invariant (an `initial` run must never be interpreted as post-activation). The Python side *is* covered — `test_resume_after_activation` flips `mode` back to `initial` and asserts rejection — so the gap is schema-only, and a regression that dropped the `allOf` (or mis-nested it, which is easy with `if/then`) would pass the whole gate.
- `stable_release_signoff.schema.json:45-55` — the new required `site_publication` object with `const` repository/workflow. `validate_release_signoff` enforces the same in `release_plan.py:357-367`; the schema's copy is unasserted.

Two `copy.deepcopy` + `validate_instance` blocks in the existing style close this.
