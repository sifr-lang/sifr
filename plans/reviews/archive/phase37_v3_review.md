# Phase 37 v3 Review: Cargo-Backed Package Management

**Reviewer**: agent
**Date**: 2026-05-19
**Document**: `internal_docs/phases/37_package_management_v3.md`
**Status**: Viable with specific blockers requiring exact doc changes

---

## Overall Assessment

v3 is a significant improvement over v1 (Sifr-native lock) and v2 (uv/PyPI-primary). Making Cargo the primary substrate for a compiled Rust-target language is architecturally sound and avoids the fundamental impedance mismatch of v2. The design is **viable** but has **blockers** that must be resolved in the document before implementation begins.

The critical failure mode v3 avoids: Cargo does not understand Sifr import/export semantics, but Sifr does not need Cargo to understand them. Cargo owns the dependency graph; Sifr owns the import graph. This separation is correct.

---

## Architecture Validation: Can Cargo Serve as Primary Package Manager?

**Yes, with constraints.** The design correctly identifies that Cargo already owns the infrastructure Sifr needs, and that Sifr's import semantics are orthogonal to Cargo's dependency resolution. The critical insight in v3 that v2 lacked: **Sifr does not need a package resolver**. Cargo is the resolver. Sifr needs a package graph derived from Cargo's output plus Sifr metadata.

The argument for Cargo-as-primary is stronger than the argument for uv-as-primary in v2 because:
- Sifr compiles to Rust and generates Cargo projects. Cargo integration is native.
- Cargo's multiple-version support (while complex for Rust) is directly reusable for Sifr's scoped import model.
- `cargo metadata --format-version 1` is a stable, well-documented JSON surface.
- Cargo's registry, Git, path, and workspace support covers Sifr's source-distribution model.
- Cargo's lock/offline/frozen semantics are mature and directly mappable to Sifr command modes.

The argument against uv-as-primary in v2 was structural: uv resolves Python wheels/sdists, which are not Sifr packages. Sifr needs `.sifr` source, not Python bytecode. Cargo packages can carry `.sifr` source natively.

## Critical Blockers

These must be fixed in the document before implementation proceeds.

### Blocker 1: `cargo metadata` schema is insufficient for Sifr metadata retrieval

**Problem**: The design relies on `[package.metadata.sifr]` in Cargo manifests, but `cargo metadata` output does not include manifest file contents. Cargo's JSON output includes manifest path, package metadata keys, but the value of `[package.metadata.sifr]` is not serialized in `cargo metadata --format-version 1` output by default.

**What happens**: When Sifr parses `cargo metadata` JSON, it gets `manifest_path` for each package. To read `[package.metadata.sifr]`, it must parse the `Cargo.toml` file directly. But:
1. `cargo metadata` does not guarantee the Cargo.toml is readable (e.g., when package is fetched from a registry and only the source tarball is available).
2. Parsing Cargo.toml files ad hoc breaks the abstraction boundary — Sifr should not need to parse Cargo manifests except where Cargo itself parses them.
3. Registry-fetched packages may have their Cargo.toml inside the `.crate` tarball, not at a filesystem path.

**Required doc change**: Add a section explicitly specifying how Sifr retrieves `[package.metadata.sifr]` from `cargo metadata` output. The options are:
- Option A: Sifr parses `Cargo.toml` at `manifest_path` from metadata JSON. Requires the manifest to be on the local filesystem.
- Option B: Sifr invokes `cargo pkgid` or `cargo read-manifest` to retrieve serialized metadata for a package.
- Option C: `[package.metadata.sifr]` is not used; instead, Sifr requires a companion `sifr.toml` at a predictable location relative to the Cargo package root, discoverable from `cargo metadata` via manifest path.

**Recommended**: Option C is most robust. `cargo metadata` gives `manifest_path` for each package. Sifr looks for `sifr.toml` in the same directory as `manifest_path`, or at a path derived from `manifest_path`. This works for filesystem packages, cached registry packages, and vendored packages. It does not require parsing Cargo.toml.

### Blocker 2: Pure Sifr package marker `src/lib.rs` requirement is underspecified

**Problem**: The design states "Pure Sifr packages still include a minimal Rust target because Cargo requires at least one target." This is true, but the generated `src/lib.rs` is called a "marker" that "must not become a second source of truth." This creates an implementation ambiguity:
1. What exactly goes in `src/lib.rs`? Empty file? `mod sifr;`? A re-export?
2. Who generates it — the package author, a `sifr init` scaffold tool, or Sifr itself during package compilation?
3. If `src/lib.rs` is auto-generated by Sifr, does it modify the user's package source tree?
4. If `src/lib.rs` is not auto-generated, how does a pure Sifr package satisfy Cargo's target requirement without author intervention?
5. Cargo's `cargo package` command packs the crate. Does `src/lib.rs` get included in the package archive? The `include` field in the example manifest includes `src/lib.rs`, so yes. But the content of `src/lib.rs` for a pure Sifr package is undefined.

**Required doc change**: Add a subsection under "Core Decision" that specifies:
- The required content of `src/lib.rs` for pure Sifr packages (one-line minimal placeholder, e.g., `// Sifr package — see sifr.toml`)
- Whether Sifr generates this file automatically during packaging/compilation or whether the package author must provide it
- Whether `src/lib.rs` participates in Sifr compilation or is ignored by Sifr's compiler pipeline

### Blocker 3: Package archive inclusion verification is undefined

**Problem**: The design says `cargo package` is used for packaging, but:
1. `cargo package` creates a `.crate` tarball. Sifr needs to verify that `.sifr` source files and `sifr.toml` are included.
2. `cargo package` respects the `include`/`exclude` fields in `Cargo.toml`. If a package author incorrectly configures `exclude`, the package will be incomplete.
3. The design does not specify how Sifr validates the package archive before publishing or during `sifr package --dry-run`.
4. The design mentions "Sifr package verification additionally compiles/checks Sifr source packages" but does not say how Sifr accesses the `.crate` tarball contents for a registry-published package.

**Required doc change**: Add a section "Package Archive Validation" that specifies:
- How Sifr retrieves and inspects a package archive (crate tarball) for validation
- Whether Sifr uses `cargo package --list` to enumerate included files, or reads the tarball directly
- The validation steps for `sifr package --dry-run` before publishing
- Whether Sifr validates `include`/`exclude` field correctness or trusts Cargo's packaging behavior

### Blocker 4: Cargo package vs Sifr package classification is underspecified for the common case

**Problem**: The design says "A dependency is a Sifr source package if its selected package exposes `[package.metadata.sifr]` and valid `sifr.toml`." But in the classification pipeline:
1. When `cargo metadata` returns packages, some will be pure Rust crates (e.g., `tokio`, `serde`) with no `sifr.toml`.
2. Some will be Sifr packages with `sifr.toml`.
3. Some may be hybrid packages (Rust + Sifr) — the design correctly identifies these.
4. The classification rule "A dependency is a Sifr source package if its selected package exposes `[package.metadata.sifr]` and valid `sifr.toml`" requires that Sifr can retrieve and validate `sifr.toml` for every package, including registry-fetched ones.

**Required doc change**: Add explicit classification flow with these cases:
- Package has `sifr.toml` on local filesystem → Sifr source package
- Package is registry-fetched, `sifr.toml` is inside the `.crate` tarball → Sifr source package (Sifr must extract and parse the tarball)
- Package has no `sifr.toml` → backend Rust crate only
- Package has `sifr.toml` AND Rust deps → hybrid Sifr source + backend crate

Also clarify: is the absence of `sifr.toml` a hard error or a warning for packages that declare Sifr deps in their `Cargo.toml`? The current language suggests it should be an error (`SIFR-PACKAGE-0102`: "selected Cargo package expected to be Sifr-capable but has no Sifr metadata").

## Contradictions and Inconsistencies

### Contradiction 1: `[package.metadata.sifr]` location assumption

The design uses `[package.metadata.sifr]` in the Cargo manifest for Sifr metadata. But the "Sifr Metadata In Cargo" section says:

> `manifest` is relative to the Cargo package root.

If `manifest` points to `sifr.toml` relative to the package root, then why does the example also include `[package.metadata.sifr]` inline with the `name`, `exports`, etc.? The example shows both the inline `[package.metadata.sifr]` block AND `sifr.toml` as the canonical metadata file.

**Resolution needed**: Clarify whether `[package.metadata.sifr]` contains:
- A pointer to `sifr.toml` (Option: `manifest = "sifr.toml"` plus nothing else), or
- Duplicated metadata (name, exports, etc.) plus a manifest pointer

The current design appears to duplicate metadata in both places, which is error-prone. The validation rule says `name` must match `sifr.toml`'s `[package].name` and `exports` must match `sifr.toml`'s `[exports].modules`. This creates a consistency burden that must be maintained in two places.

**Recommendation**: `[package.metadata.sifr]` should contain only `manifest = "sifr.toml"`. All other Sifr metadata lives in `sifr.toml`. The validation rule "name must match `[package].name` in `sifr.toml`" should be understood as "Sifr loads `sifr.toml` and uses its content" not "Sifr validates consistency between two files."

### Contradiction 2: Multiple-version type identity section is incomplete

The design says:

> Type identity is package-instance-specific: `sifr-math@1.4::math.Vector != sifr-math@2.1::math.Vector`

But it does not address:
1. What happens when a package that was compiled against `sifr-math@1.4` is used as a dependency by a package that was compiled against `sifr-math@2.1`? Do cross-version type errors arise at link time or at compile time?
2. Sifr compiles `.sifr` source to Rust. If two different dependency versions produce two different generated Rust modules for the same logical namespace, how does Cargo's linker resolve this? Cargo handles this for Rust packages via distinct crate names, but Sifr's generated Rust may not follow the same naming discipline.
3. The example shows the valid case where `image-lib` and `physics-lib` each have their own scope. But what about a package that transitively depends on both `sifr-math@1.4` and `sifr-math@2.1` through different paths, and then tries to pass a `math.Vector` from one scope to code expecting the other scope? This is not a simple import ambiguity — it's a type identity conflict that may only surface at codegen or link time.

**Recommendation**: Add a "Cross-version Type Identity" section that specifies:
- The Sifr-level rule (types from different package instances are incompatible)
- The generated Rust naming convention that preserves this (e.g., `sifr_math_v1::math::Vector` vs `sifr_math_v2::math::Vector`)
- The detection point (compile-time Sifr type error vs link-time failure)
- The diagnostic code for type identity mismatch (`SIFR-PACKAGE-0204` is already listed but needs more detail on when it fires)

### Contradiction 3: `include` field in Cargo manifest vs. Sifr source roots

The example manifest shows:

```toml
include = ["Cargo.toml", "sifr.toml", "sifr/**/*.sifr", "src/lib.rs", "README.md", "LICENSE"]
```

But this assumes the Sifr source is in a `sifr/` directory, which matches the example layout. However:
1. `sifr.toml` has `[source].roots = ["sifr"]`. The `include` field must match the actual source roots.
2. If a package uses `roots = ["src"]` or `roots = ["."]`, the `include` field must be updated accordingly.
3. The design does not specify whether Sifr validates that the `include` field in Cargo.toml matches the actual `[source].roots` in `sifr.toml`.

**Recommendation**: Add validation rule: `sifr build` and `sifr package --dry-run` must verify that all `.sifr` files under `[source].roots` are included in the Cargo package archive (via the `include`/`exclude` fields or via Cargo's default inclusion rules). A mismatch between `sifr.toml` source roots and the actual included files in the package archive is `SIFR-PACKAGE-0401`.

## Missing Details That Create Implementation Risk

### Missing 1: Registry discovery for Cargo packages

The design says Sifr packages can be published to crates.io and alternate Cargo registries. But:
1. How does Sifr discover available Sifr packages from a Cargo registry? Cargo's sparse index protocol returns all crate metadata, but Sifr metadata is not part of the standard Cargo index.
2. Does Sifr need to build its own registry index that augments Cargo's sparse index with Sifr-specific metadata (exports, compiler version requirements, Sifr edition)?
3. Or does Sifr rely on a naming convention (e.g., `sifr-` prefix) to filter Sifr packages from the Cargo registry?

**Recommendation**: Add a "Sifr Registry Discovery" section. The initial approach should be naming-convention-based: packages with names starting with `sifr-` or registered in a Sifr-specific sparse index are candidates. Sifr then downloads and inspects their `sifr.toml` to confirm Sifr capability.

### Missing 2: Version compatibility between Sifr edition and Cargo edition

The example shows:
- `edition = "2024"` in Cargo.toml (Rust edition)
- `edition = "2026"` in sifr.toml (Sifr edition)

These are independent. But what about compiler version compatibility?
- If a Sifr package declares `sifr-version = ">=0.3,<0.4"` and a user is on Sifr 0.2, what happens?
- Does Sifr validate compiler version requirements at graph derivation time?
- Cargo's resolver does not understand Sifr version requirements.

**Recommendation**: Add a section on Sifr version requirement validation. Sifr must validate, at graph derivation time, that the active Sifr compiler version satisfies each selected package's `sifr-version` requirement. If not, `SIFR-PACKAGE-0003` (compiler version mismatch) should fire.

### Missing 3: Feature resolution for Sifr packages

The design references "Cargo features" but does not specify how Sifr handles Cargo feature flags on Sifr packages. For example:
- A Sifr package declares `[features]` in its `Cargo.toml`
- A dependent Sifr package enables some of those features
- How does Sifr validate that the enabled features produce a compatible import graph?

**Recommendation**: Add a "Cargo Features And Sifr Packages" section. Sifr should either:
- Support a parallel feature system in `sifr.toml` that maps to Cargo features, or
- Defer Cargo feature support to a later milestone and document it as out of scope for Phase 37

The current design does not specify which approach is taken.

### Missing 4: Workspace membership and Sifr package graph derivation

The design says "Cargo workspace membership is the package selection source of truth in Phase 37." But:
1. A Cargo workspace can have members that are pure Rust crates (no `sifr.toml`) and members that are Sifr packages.
2. The derived `SifrPackageGraph` includes only Sifr source packages, not backend Rust crates.
3. How does Sifr handle a Cargo virtual workspace where the root is not a package?

**Recommendation**: Add explicit rules for:
- Virtual workspace handling: Sifr discovers members from `cargo metadata` workspace members, filters to those with `sifr.toml`, and derives the Sifr graph from those filtered members.
- Non-package root workspaces: Sifr uses workspace members only.
- Mixed members: Pure Rust members are excluded from the Sifr graph but their backend dependencies participate in Cargo's backend resolution.

### Missing 5: `cargo add` behavior for Sifr packages

The design says `sifr add <package>` maps Sifr package name to Cargo package name. But:
1. If a user runs `sifr add json`, what Cargo package name does Sifr look up? Is there a naming convention (`sifr-json`)? A registry search? A configured mapping?
2. Does `sifr add` delegate to `cargo add` directly, or does it perform its own lookup?

**Recommendation**: Add a "Package Name Resolution" section specifying:
- The naming convention (e.g., `sifr-` prefix or registry-specific mapping)
- How `sifr add` maps from user-facing Sifr package name to Cargo package name
- Whether `sifr add` directly calls `cargo add` or implements its own coordination

## uv Deferral: Is It Justified?

**Yes, but the deferral should be explicit about what is being deferred.**

The current language says:
> `pyproject.toml`, `uv.lock`, and uv are not part of the Phase 37 core. They remain future Python interop and CLI-distribution concerns.

This is vague. The review in v2 was: "whether uv really can be deferred" — and the answer is yes, but for a specific reason: **Sifr packages are not Python packages**. A pure Sifr package has no Python runtime. It does not need PyPI, wheels, sdists, `requires-python`, PEP 508 dependencies, or uv lock semantics. The `pyproject.toml` / `uv.lock` layer adds zero value for a compiled Rust-target language.

The actual deferred concern is:
1. **Sifr CLI distribution**: If Sifr is installed via `pip install sifr` or `uv tool install sifr`, then Sifr itself has a Python package dependency. That is uv's concern, not Sifr's.
2. **Python interop packages**: Phase 43 mentions `sifr-numpy` and similar packages that need Python runtime. These need `pyproject.toml` for the Python side, but the Sifr side still uses `sifr.toml`.
3. **Hybrid projects**: A workspace that has both Sifr and Python source code.

The deferral is justified. The documentation should say: "uv is not the Sifr package substrate because Sifr packages are Cargo packages, not Python packages. uv remains relevant only for Sifr's own CLI distribution and for future Python interop packages."

## Milestone Assessment: Are They Production-Grade?

**Yes, with one gap.** The seven milestones are well-scoped and have clear definitions of done. The sequencing is logical:
- m37.1 → m37.2 → m37.3 builds from metadata to graph to compilation
- m37.4 adds Cargo command integration
- m37.5 adds workspace and filtering
- m37.6 adds packaging and publishing
- m37.7 is validation and guardrails

**The gap**: None of the milestones explicitly address **package archive extraction and validation for registry-fetched packages**. m37.1 derives the graph from `cargo metadata`, but `cargo metadata` does not give Sifr access to the actual source files for registry packages (those are inside `.crate` tarballs). m37.3 ("Package-Aware Source Compilation") requires that Sifr can read `.sifr` source files from dependencies. For registry packages, this means extracting from the crate tarball.

**Recommendation**: Add to `milestone_37_3` scope:
> "Extract `.crate` tarball contents for registry-fetched Sifr packages and validate `sifr.toml` and `.sifr` source files from the archive. Cache extracted source for repeated compilations."

Or add a new `milestone_37_2.5: Package Archive Extraction` between m37.2 and m37.3.

## Concrete Doc Changes Required

The following exact changes are required before implementation:

### Change 1: Add "Sifr Metadata Discovery" section (resolves Blocker 1)

```markdown
## Sifr Metadata Discovery

Sifr locates package metadata through `cargo metadata` output plus local filesystem access.

1. `cargo metadata --format-version 1` returns `manifest_path` for each selected package.
2. For each package, Sifr checks for `sifr.toml` in the same directory as `manifest_path`.
3. For registry-fetched packages, `cargo metadata` resolves `manifest_path` to the unpacked crate directory in the Cargo registry cache. Sifr reads `sifr.toml` from there.
4. `[package.metadata.sifr]` in `Cargo.toml` is not used for metadata retrieval. It may optionally contain a `manifest` field pointing to a non-default location for `sifr.toml`, but the default is the same directory as `Cargo.toml`.

Classification:
- Package with `sifr.toml` at manifest-path directory → Sifr source package
- Package without `sifr.toml` → backend Rust crate only
- Package with `sifr.toml` AND `[dependencies]` containing Rust crates → hybrid
```

### Change 2: Add "Pure Sifr Package Marker Rust Target" section (resolves Blocker 2)

```markdown
## Pure Sifr Package Marker Rust Target

Cargo requires at least one target (library or binary) per package. Pure Sifr packages include `src/lib.rs` as a required marker file.

Content of `src/lib.rs` for pure Sifr packages:

```rust
// Sifr package — compiler-facing package metadata is in sifr.toml
// This file is not compiled as part of the Sifr source graph.
// Cargo requires this file to satisfy package target requirements.
```

This file is:
- Included in the Cargo package archive via `include = ["src/lib.rs"]` in `Cargo.toml`
- NOT compiled by Sifr's frontend/HIR/codegen pipeline (Sifr uses `sifr.toml` source roots, not `src/`)
- NOT a second source of truth for Sifr behavior
- NOT modified by Sifr during compilation (it is a static marker)

Package authors using `sifr init --lib` get this file scaffolded automatically.

For packages with Rust backend code (hybrid packages), `src/lib.rs` contains actual Rust implementation and participates in the normal Rust compilation pipeline.
```

### Change 3: Add "Package Archive Validation" section (resolves Blocker 3)

```markdown
## Package Archive Validation

Sifr validates package archive contents before publishing and during `sifr package --dry-run`.

### Validation Steps

For a package at `manifest_path`:

1. Run `cargo package --list` to enumerate files that would be included in the package archive.
2. Verify that every `.sifr` file under each `[source].roots` in `sifr.toml` appears in the package file list.
3. Verify that `sifr.toml` itself appears in the package file list.
4. Verify that no `..` path traversal entries exist in the package file list.
5. For registry packages, `cargo package` operates on the cached crate. For local packages, it operates on the source tree.
6. Extract and validate the package archive contents match the enumerated files.

### Archive Structure Requirements

Published packages must contain:
- `Cargo.toml` (at archive root)
- `sifr.toml` (at archive root, adjacent to `Cargo.toml`)
- All `.sifr` source files under each declared `[source].roots`
- No entries with `..` path components, absolute paths, or symlinks outside the package root

Validation failure emits `SIFR-PACKAGE-0401`.

### Publishing Validation Flow

`sifr publish --dry-run`:
1. Validate local `sifr.toml` and source roots
2. Run `cargo package --list` and verify Sifr files are included
3. Validate `[exports].modules` against actual `.sifr` source
4. Check backend trust policy
5. Report diagnostics without uploading

`sifr publish`:
1. Run `sifr publish --dry-run`
2. If dry-run succeeds, delegate to `cargo publish`
3. Verify index round-trip after publishing
```

### Change 4: Add "Cross-Version Type Identity" section (resolves Contradiction 2)

```markdown
## Cross-Version Type Identity

Sifr enforces that types from different package instances are incompatible.

### Rule

For any import root `R`, all symbols imported from `R` within one package's direct dependency scope have compatible types. Types from `R` in different scopes are always incompatible.

```text
sifr-math@1.4::math.Vector   ≠   sifr-math@2.1::math.Vector
```

### Generated Rust Naming

Sifr codegen generates distinct Rust module paths for each package instance:

```rust
// Generated Rust for image-lib's dependency on sifr-math@1.4
pub mod sifr_math_v1 {
    pub mod math {
        pub struct Vector { ... }
    }
}

// Generated Rust for physics-lib's dependency on sifr-math@2.1
pub mod sifr_math_v2 {
    pub mod math {
        pub struct Vector { ... }
    }
}
```

The mapping from import root to Rust module name uses the Cargo package id as a namespace disambiguator. This prevents link-time symbol collisions.

### Detection Point

Type identity mismatch is a compile-time Sifr error, detected during type checking when:
1. A value of type `PackageInstanceA::T` is passed to a location expecting `PackageInstanceB::T`
2. `PackageInstanceA` and `PackageInstanceB` resolve to different Cargo package ids (same or different package name)

Diagnostic `SIFR-PACKAGE-0204` fires with the full import path, Cargo package identity, and version for both instances.

### Scope Boundary

The type identity rule applies within one package's direct dependency scope. Between scopes, no type compatibility is assumed. A parent package that transitively depends on both versions must explicitly alias one of them to a different import root to use both in the same scope.
```

### Change 5: Add "Package Name Resolution" section (resolves Missing 5)

```markdown
## Package Name Resolution

When a user runs `sifr add http`, Sifr resolves the name `http` to a Cargo package.

### Naming Convention

Sifr packages use the `sifr-` prefix convention by default:
- Sifr package name `http` → Cargo package name `sifr-http`
- Sifr package name `json` → Cargo package name `sifr-json`

This allows Cargo's registry to distinguish Sifr packages from Rust packages.

### Resolution Steps

1. Check if `sifr-<name>` exists in Cargo registry (sparse index lookup)
2. If found, use `sifr-<name>` as the Cargo dependency
3. If not found, check if `<name>` exists and has Sifr metadata (hybrid packages)
4. If not found, emit `SIFR-PACKAGE-0101` with suggested name variants

### Custom Naming

Packages may declare a custom Cargo name mapping in `sifr.toml`:

```toml
[distribution]
cargo-name = "sifr-http"  # maps Sifr package name "http" to Cargo package "sifr-http"
```

This overrides the default `sifr-` prefix convention.

### `sifr add` Behavior

`sifr add http`:
1. Resolves to `sifr-http` via naming convention or custom mapping
2. Adds `sifr-http = "..."` to `Cargo.toml`
3. Derives Sifr package graph from updated metadata
4. Does NOT modify `sifr.toml` (Sifr package name stays as "http")

`sifr add sifr-http` (direct Cargo name):
1. Accepted directly as a Cargo package name
2. Sifr checks if it has Sifr metadata after resolution
```

### Change 6: Clarify `[package.metadata.sifr]` to single-pointer (resolves Contradiction 1)

Update the "Sifr Metadata In Cargo" section:

```markdown
## Sifr Metadata In Cargo

Every Sifr package must expose Sifr metadata location in Cargo metadata.

```toml
# Cargo.toml
[package.metadata.sifr]
manifest = "sifr.toml"
```

The `manifest` field points to `sifr.toml` relative to the Cargo package root. All other Sifr package metadata (name, edition, source roots, exports, trust policy) lives in `sifr.toml` only.

Rules:
- `manifest` must point to a file that exists and is parseable as `sifr.toml`
- Missing `manifest` field or unresolvable path is `SIFR-PACKAGE-0001`
- `sifr.toml` is the single source of truth for Sifr package semantics; no metadata is duplicated in `Cargo.toml`
- A Cargo package without `[package.metadata.sifr]` is not a Sifr source package

## Cargo/Sifr Name Distinction

- Cargo package name: distribution name used by Cargo (e.g., `sifr-http`)
- Sifr package name: compiler-facing import root (e.g., `http`)
- These may differ. Sifr uses the Sifr package name for imports; Cargo uses the Cargo package name for dependency resolution.
```

## Summary

**Verdict: Viable with edits.**

The v3 design is architecturally sound and represents a clear improvement over v1 and v2. Cargo is the correct primary package substrate for a compiled Rust-target language. The scoped import model with multiple-version support is well-designed.

The seven blockers identified above are addressable with specific doc changes. None of them require fundamental redesign — they are completeness gaps that would create ambiguity during implementation.

**Must-fix before implementation** (any of these being unaddressed blocks the phase):
1. Blocker 1: How Sifr discovers and retrieves `sifr.toml` from `cargo metadata` output for both local and registry packages
2. Blocker 2: Specification of the pure Sifr package marker `src/lib.rs` content, who generates it, and whether Sifr modifies the source tree
3. Blocker 3: Package archive validation flow for `sifr package --dry-run` and `sifr publish`
4. Blocker 4: Explicit classification pipeline for packages (Sifr source / backend Rust / hybrid) including registry package handling

**Strong recommendations** (design is viable without these, but implementation will face ambiguity):
- Contradiction 1: Remove metadata duplication — `sifr.toml` is the sole source of truth
- Contradiction 2: Add cross-version type identity spec with generated Rust naming convention
- Missing 2: Add Sifr version requirement validation at graph derivation time
- Missing 3: Add Cargo features handling decision (support or defer with explicit rationale)
- Missing 4: Add virtual workspace and mixed-member handling rules
