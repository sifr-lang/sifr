## Finding

**Minor 1 — the freshness guarantee's suite-name→command→report binding is unvalidated for three of the five owning suites (fail-closed gap, same pattern as pass-1 Minor 3).**
Freshness is enforced by `run_case` deleting the report keyed by *command* (`runner.py:323-325`, `_command_report_path`), while the ledger keys acceptance by *suite name* (`certification_ledger.py:31`, matrix `report` pinned to `<suite>.latest.json`). The link between the two — manifest suite name → dispatched command — is validated only for `buffer-examples`/`buffer-cpython311` (`runner/run.py:647-668`) and `dlpack-examples`/`dlpack-cpython311` (`runner/dlpack_evidence.py:79-101`), and only inside the self-test suite's fixture validation; `callback-examples`, `arrow-examples`, and `async-declaration-examples` have no binding check anywhere (repo-wide grep: their command names appear only in their `COMMAND_ARGS` definitions). *Failure scenario:* an in-repo manifest edit rebinds, say, suite `arrow-examples` to a different known passing command (a plausible copy-paste drift); the arrow report is then never deleted nor rewritten, yet the ledger sees suite `arrow-examples` with zero failures and accepts the **stale** `arrow-examples.latest.json` from a prior run — certification stays `complete` in any warm workspace or cached CI target directory. My earlier probe (synthetic suite result + real on-disk report accepted as `passing`) demonstrates the ledger has no invocation-local freshness proof of its own. This is exactly the trust class pass-1 Minor 3 treated as actionable — an advertised guarantee ("stale output cannot promote a capability", docs/python-interop.mdx:372-374, README, internal docs) resting on a validator that is partial and not guaranteed to run on the certification path (the self-test suite is absent from the demo's five-suite invocation). *Remediation (cheap, invocation-local):* in `build_compiled_certification`, assert for each selected required suite that one of its recorded cases' `argv` contains the pinned `<suite>.latest.json` report argument (suite results already carry `argv`); or equivalently, in `runner.py` verify `_command_report_path(command)` of each required suite's case equals the pinned path. Either covers targeted runs and full gates uniformly.

**Non-actionable notes**: matrix/design validation runs after the suites (runner.py:197-198), so an invalid matrix is discovered only after full suite wall-time — moving the load before `run_suite` would fail faster and would also supply the required-suite set for the remediation above; `_compiled_evidence_suites` in profiles.py shallow-parses the matrix rather than reusing the area validator — acceptable since any derivation error fail-closes at either the profile or the area layer; the pass-1 notes (4000-char stdout tail, `failed_suites` schema asymmetry, first-`--report`-occurrence) remain non-actionable, and each owning suite has exactly one case with exactly one `--report`.
