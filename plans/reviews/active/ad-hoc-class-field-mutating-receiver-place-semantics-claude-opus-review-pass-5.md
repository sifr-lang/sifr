## Remaining findings

**1. Classifying `with` targets as `EphemeralLocal` breaks the `open()` idiom and two existing pass fixtures.** §3 lists "`with` targets" under `EphemeralLocal`, declares ephemeral bindings deliberately unsupported mutable places, and the check-fail matrix mandates a `SIFR-OWN-0014` fixture for "`with` … target mutable receivers". But `TextFile.write` is a stdlib Sifr class method emitted as `fn write(&mut self, text: &String)` (confirmed in `emit` output), i.e. a resolved `MutableBorrow` receiver, and it is called on a `with` target in two current pass fixtures:

- `crates/sifr/tests/e2e/pass/open_context_manager.sifr:7-8` — `with open(path,"w",…) as f:` / `f.write("hello from context")`
- `crates/sifr/tests/e2e/pass/cpython_io_subset.sifr:96-97` — same shape with `out.write("ctx")`

Under the stated rule these become `SIFR-OWN-0014` errors. Emitted Rust shows the `with` target is in fact a stable owned local (`let mut f = __guard_0.ctx.__enter__();`) — it has none of the properties that make a loop element unemittable, which was pass-4's actual concern. The plan needs to narrow `EphemeralLocal` to iteration/comprehension element bindings (and `match` captures), classify `with` and `except` targets as stable owned locals, and drop them from the `SIFR-OWN-0014` matrix row — or, if the rejection is intended, say so explicitly and specify how those two fixtures migrate. As written this contradicts the goal of preserving existing accepted behavior. (Corpus check: no loop-variable-rooted mutating receiver exists in `demos/`, `stdlib/`, or `tests/e2e/pass/` — the loop-element rejection itself carries no migration cost.)

**2. §5's "every operator-protocol bridge consumes `HirFunction.receiver`" is not implementable at those sites, and no diagnostic covers the mismatch.** `operator_protocol_emitters.rs` emits `impl std::ops::Add`/`PartialEq`/`PartialOrd` items whose receivers are fixed by the Rust trait: `SelfParam { mutable: false }` at `:194`, `:237`, `:291` and `SelfValue` for unary ops at `:158`. If a dunder body mutates a field, the new lowering-owned inference will mark it `MutableBorrow`, place validation will accept `self` as a proven mutable root (`BindingKind::Receiver` + `MutableBorrow`), and the emitter must then either ignore the convention (contradicting the "sole source for Rust `self` signature" acceptance criterion) or emit `&mut self` into a fixed-signature trait impl and leak `E0053`. Today this shape ICEs instead (verified: a `__eq__` that assigns `self.hits` produces `SIFR-INTERNAL-0001` from `function_like_lowering.rs:100`), so it is a pre-existing hole — but the plan explicitly claims these sites and gives no rule. Add an explicit carve-out: Rust-std-trait operator bridges have fixed receivers, and a dunder inferred `MutableBorrow` is a check-time error (a `SIFR-PROTO-0005` sibling or a named reuse), with a fail fixture.

**3. "match/destructuring pattern targets" is ambiguous and, read broadly, over-rejects plain tuple unpacking.** §3 classifies "match/destructuring pattern targets" as `EphemeralLocal`. In-tree these are two different paths: `bind_pattern_vars` (`patterns_and_assignments.rs:249`) handles `match` captures, while `a, b = expr` routes through `lower_tuple_unpack_assign` (`control_flow.rs:38-44`) and chained assignment (`patterns_and_assignments.rs:568,598`), both of which emit stable `HirStmt::Let { is_mutable: true }`. If tuple-unpack targets are swept into `EphemeralLocal`, `a, b = f()` followed by `a.append(x)` newly reports `SIFR-OWN-0014`. No corpus case breaks today, but the plan should say "`match` case captures only" and state that tuple-unpack and chained-assignment targets remain stable owned locals.

Findings 1 and 2 are material semantic choices, not implementation detail: finding 1 mandates a fail fixture for code that currently works and is the documented file-writing idiom, and finding 2 leaves an unchecked receiver path at a site the plan claims to close.
