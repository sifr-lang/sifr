## agent High Minimalism Review: Stdlib Rust Interop Bridge Adapter Design — Pass 1

### Verdict: **PASS** (no blocking findings; five trim recommendations)

The **design** is minimal in exactly the way the lens demands: one binding mechanism (`@rust(...)` with a single validated target per declaration), one place adaptation may live per context (package `bridge.*` / shared bridge crate / `sifr_stdlib`), one global error rule (`E: Display` → message-shaped construction) instead of per-declaration converter metadata, and zero fallback paths. Nothing in the v1 contract can be removed without losing a real invariant. The **prose**, however, carries removable weight — mostly deferred-feature specification and repeated statements of the same rule.

### Blocking minimalism findings

None. The one candidate — the Future Callee Injection section — is explicitly labeled future/bridge-versioned, changes nothing in the v1 contract, and its core sentences (no Rust function values cross Sifr; any callee injection requires a new bridge-versioned design) protect a real invariant. Prose length in a correctly-fenced deferral section is not grounds to block a design that two prior passes confirmed sound.

### What should be removed or shortened

**1. `internal_docs/rust_interop_architecture.md:547-576` ("Future Callee Injection") — cut roughly in half.** This is the clearest instance of premature future design. The section simultaneously defers the feature to "a separate design" and pre-designs it: concrete `@rust.via(bridge.regex.compile_adapter, target=regex.Regex.new)` decorator syntax (line 553), a generated-Rust sample (line 566), and a first-supported-shape constraint ("should be limited to non-generic function items or function pointers with probe-checked signatures", lines 571-573). Note the self-inflicted cost: the syntax example uses a path shape (`regex.Regex.new`) that v1's resolution grammar doesn't define, which forced the two-line disclaimer at lines 557-558 whose only job is to un-mislead readers about the example. Delete the example and the disclaimer deletes itself. Keep: (a) the invariant paragraph — Sifr source must not store, return, capture, or dynamically dispatch Rust functions; (b) one sentence deferring any callee injection to a new bridge-versioned design; (c) the closing paragraph (lines 578-583), which is the normative statement of how migrated stdlib actually binds. The eight-item rejection list and the "first supported shape" clause belong in the future design document, where they can be evaluated rather than inherited.

**2. `internal_docs/sifr_sysroot_and_stdlib_architecture.md:132-139` — merge two consecutive "future callee-injection form" paragraphs and drop the advocacy clause.** Lines 132-135 ("A future callee-injection form such as `@rust.via(adapter, target=...)` may be useful for diagnostics and dependency reporting, but it is not required...") and lines 137-139 ("A future callee-injection form requires a new bridge-versioned design...") say the deferral twice in adjacent paragraphs. Worse, "may be useful for diagnostics and dependency reporting" is speculative advocacy for the deferred feature — and the earlier agent pass already established that for the sysroot case those motivations are fully served by the sysroot lockfile, `SysrootDependencyPlan`, and compiler-owned trust. Keeping the clause invites re-litigation. One merged sentence suffices: "M9-M13 migrations are committed to `bridge-version = 1`; any future callee-injection form requires a new bridge-versioned design and must not add fallback conversion behavior to existing sysroot interop declarations."

**3. `internal_docs/sifr_sysroot_and_stdlib_architecture.md:146-153` ("Migration guidance") — delete the first two bullets.** They restate paragraph one of the same section (lines 121-127): "stateless leaves with exact signatures → direct" is the direct-binding rule again; "fallible leaves → adapter when errors need shaping" is the adapter rule again. The third bullet duplicates the certification-gate constraint already stated at lines 106-117 of the same document, but it carries one genuinely new clause — lifecycle behavior must be *executable evidence, not just adapter code* — which is worth keeping as a single sentence appended to the first paragraph rather than a list.

**4. `docs/rust-interop.mdx:106-108` — drop the forward-looking sentence.** "If generated glue ever supports passing a compile-time-known Rust callee into an adapter, it will be a separate bridge-versioned feature..." advertises an unshipped mechanism in public user documentation. Public docs should state the contract that exists: keep "Rust functions are not Sifr values. Sifr source cannot pass Rust closures, `impl Fn`, or `Box<dyn Fn>` into generated glue." (also dropping the hedge "today"). Roadmap speculation is internal-doc material at most.

**5. `plans/issues/active/ad-hoc-sifr-sysroot-stdlib-toolchain.md:48-55` — shorten to a pointer.** The tracker paragraph re-explains the entire policy that the anchor link two lines below already targets. Duplicated normative wording in a tracker is exactly the kind of copy that drifts. Two lines do the job: "The [stdlib Rust interop adapter policy][stdlib-interop-adapter-policy] is locked: direct binding for exact-shape `sifr_stdlib` signatures, `sifr_stdlib` adapters for everything needing reshaping or error mapping; callee injection deferred behind a future bridge version."

### What should NOT be removed

To be explicit under this lens, these additions all protect real invariants and are already minimal: the `E: Display` error-position rule (`rust_interop_architecture.md:447-454`) — normative, load-bearing, and correctly framed as a single wrapper rule; the message-shaped probe example (`:403-415`) — closes the probe-shape gap the rule would otherwise leave; the sysroot root-table row (`:211`); the sysroot trust/no-panic paragraph (`sifr_sysroot_and_stdlib_architecture.md:141-144`) — this is the one sentence where "no user-triggerable panics" rests on a trust assertion, and it must be written down; and the mdx adapter-boundary paragraph (`docs/rust-interop.mdx:74-80`) — public restatement for a different audience, not duplication.

### Judgment: is the design minimal enough for the stdlib rewrite?

**Yes.** The contract the stdlib rewrite will actually consume is as small as it can be while preserving the safety guarantees: every `_sifr.*` declaration validates exactly one bridge-compatible Rust signature; adapter-vs-exact-shape is invisible to the compiler; error mapping is one global typed rule with a probe, not per-declaration metadata; there is no `bridge.*` module for the synthetic sysroot package, no converter fallback, no compatibility shim, and no half-shipped `@rust.via`. Nothing left to take away is in the *design*. What remains to take away is ~40-50 lines of prose — deferred-feature specification and rule restatement — none of which changes what gets built, which is why the trims are recommendations rather than blocks.
