## Findings

1. **`sifr.secrets.choice` now delegates to `sifr.random.choice` (secrets.sifr).** Semantically identical to the pre-change behavior -- the old path also used the non-cryptographic `random_choice` intrinsic -- but this pre-existing weakness (secrets built atop Mersenne Twister) is now more visible in the call graph and is out of scope for M4b. Worth tracking separately, not blocking.
2. **Nothing in the diff re-adds `random_choice`/`random_shuffle`/`random_sample` as private declarations in `_sifr/crypto.sifr`.** That is intentional per the brief (generic `list[T]` interop unsupported) and consistent with their inclusion in `RETIRED_INTRINSICS` in `check_stdlib_migration_closure.py`. Confirmed the retained intrinsics module no longer surfaces `_sifr.crypto`, so the retired names cannot be reached via the fallback path. Not a defect.
3. **`crates/sifr_stdlib_manifest/src/features.rs`** collapses `sifr.random` and `_sifr.crypto` to `&[]`. Correct -- random pulls `rand`/`rand_distr` transitively through the `sifr_stdlib` "random" feature, and non-random crypto entries flow through their own stdlib feature-gates. The new `random_module_emits_only_sysroot_stdlib_dependency` test asserts exactly this. Not a defect.
4. **`RandomModuleState` runtime need and preamble emission fully removed** in `lib_emitter_state.rs`, `lib_modules_and_codegen.rs`, and `preamble/io_logging_random.rs`. `needs_mutex` no longer forces on random; that is safe because the Mutex now lives inside `sifr_stdlib::random`, not in the generated preamble. Not a defect.

## Validation Assessment

The listed local gates cover the surfaces touched: registry tombstone test guards the compiler side; `random_helpers_and_module_state_round_trip_without_panicking` covers `random_int`/`random_float`/`random_randrange` including the `step=0` error path and Mersenne-length (624) validation on `random_module_set_state`; the manifest test locks the dependency shape (`sifr_stdlib` with feature "random", no direct `rand`/`rand_distr`); e2e fixtures for `random`, `secrets`, `tempfile`, and `stdlib_random` exercise the end-to-end generated call sites; closure/allowlist/schema/file-size guards catch accidental resurrections. Absence of a concurrency stress test on module state is acceptable -- the Mutex ownership is straightforward and unchanged in semantics, only relocated. Validation coverage is adequate.

## Residual Risks

- **`random_module_state_index()` returns bare `int` with no explicit "unset" sentinel.** If a caller reads state before `random_module_set_state` has ever been invoked, they get the default (0). The api_behavior test sets state first, so this codepath isn't exercised. Not a change from the prior compiler-owned state (same behavior, new home), so not blocking, but worth a targeted test if you want to lock it.
- **`sifr.random.choice` (unseen in this diff) is now load-bearing for both `sifr.random` and `sifr.secrets`.** If a future refactor changes its return type from `Result[T, ValueError]` to `T`, `sifr.secrets.choice` still compiles (auto-wrap), but the error-propagation semantics diverge silently. Consider a snapshot test pinning `sifr.random.choice`'s type before further consolidation.
- **The `stdlib_retained_compiler_intrinsics.toml` row for `_sifr.crypto::random` is `closing`, not `retired`.** That is correct per the doc convention (retention row records closure until proven absent), but the removal criterion -- "delete this closing row after the migrated random registry names are proven absent by closure guards" -- is now the only tracked follow-up. Track this to actual deletion once the guard has landed in main for at least one cycle.
