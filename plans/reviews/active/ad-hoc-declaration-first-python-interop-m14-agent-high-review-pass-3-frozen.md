## Findings

### Minor 1 (actionable) — `bind` authors declarations with conversion types outside the direct-conversion set; ordinary `check` rejects them while `bind` exits 0 and `bind --check` reports ok

- **Files**: `crates/sifr_driver/src/python_binding.rs:228-230` (the `validate_type` allowlist admits bare `dict`, `list`, `set`, `tuple` and any subscripted form of them) and `crates/sifr/src/python_binding_probe.py:59-60,75-79` (bare container names pass the `identifier(leaf)` fallthrough; `set[T]` and `dict[K, V]` with any key type convert without restriction).
- **Proof (reproduced live against the frozen binary)**: in a scratch package, an override `def frexp(value: float) -> list: ...` → `sifr python bind math --symbols sqrt,frexp` exits 0 and checks in `def frexp(value: float) -> Result[list, PythonError]: ...`; `sifr check --frozen` then fails with `SIFR-NAME-0003: unknown type: 'list'` plus `SIFR-PYCONV-0001: return type `Any` is not in the synchronous direct-conversion set`, while `sifr python bind --check` on the same snapshot reports `Python bindings: ok`. Identically for `def ceil(values: set[int]) -> dict[int, str]: ...` — bind succeeds, check fails with `SIFR-PYCONV-0001` on both the `set[int]` parameter and the `dict[int, str]` return, `bind --check` says ok.
- **Why it matters**: this is the same defect family as pass-1 Minor 3 (bind commits a package state that cannot compile; the tool's own read-only checker disagrees with ordinary check), which was judged actionable and remediated in this PR for positional-only defaults. Bare containers, `set[...]`, and non-`str`-key dicts are at least as common in real stubs as positional-only defaults. It also contradicts contract text: the durable architecture contract requires "Generation must stop or emit an explicit unresolved marker for … unsupported conversion types" (`internal_docs/python_interop_declaration_architecture.md:577-580`, wording that predates this PR), and the public docs added by this PR claim "Generation fails closed on … unresolved types" (`docs/python-interop.mdx:196-197`). Fail-closed integrity is preserved — no runtime hole, no mutation hazard, and recovery is a corrected `--override` plus re-bind — which is why this is minor, not major.
- **Remediation**: constrain `validate_type` (or the probe's `convert_annotation`) to the actual direct-conversion grammar — parameterized `list[T]`/`tuple[…]`/`dict[str, T]`, scalars, `| None` options, and bound class names — rejecting bare containers, `set`, and non-`str` dict keys with the existing "unresolved type" error shape.
- **Tests required**: unit tests in `python_binding.rs` for bare `list`, `set[int]`, and `dict[int, str]` failing closed, plus a suite fixture mirroring the `frexp`/`ceil` scenario asserting `bind` itself fails with zero mutation.

### Note 2 — the probe's introspection path can die with an unhandled `SyntaxError` instead of a structured per-symbol error

`introspected_symbol` parses runtime annotation strings with `ast.parse` (`python_binding_probe.py:267,281`), but the surrounding handler catches only `(AttributeError, ImportError, TypeError, ValueError)` (`:318`). An annotation string that is not parseable Python crashes the whole probe; `bind` still fails closed (`python_binding_cli.rs:412-417` surfaces the traceback), so this is diagnostics quality only.

### Note 3 — stub-package file selection uses suffix matching

`normalized.endswith("/" + item)` (`python_binding_probe.py:208`) could select a same-named `.pyi` nested under an unrelated subdirectory of the stub distribution. The choice is deterministic, the consumed file's identity and digest are recorded in the artifact and fingerprint, and drift is caught — no integrity impact.
