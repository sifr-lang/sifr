## Non-blocking observations (worth recording, none block Wave 1)

1. **`merge-red-blocker` extends the spec's seven-value `profile_assignment` enum.** The issue plan lists `merge`, `nightly`, `release`, `internal`, `performance`, `test-fixture`, `unsupported` (line 122 of the plan). `coverage_matrix.py:47-56` adds an eighth: `merge-red-blocker`, used only for `sifr_codegen` in `cargo_metadata_classification.json`. This is internally consistent — `red-blocker` is already a valid matrix `status`, and the runner relies on the membership row, not the assignment string — but the spec text and the enforcement vocabulary disagree. Either accept this as a clarifying addition (and update the plan text), or fold `sifr_codegen` to `profile_assignment: "merge"` and rely solely on `status: "red-blocker"` to flag the suite. Picking explicitly now avoids drift for any future red-blocker.

2. **Doctest profile assignment isn't represented.** The Wave 1 exit criteria call out "Cargo features, bins, examples, doctests, and targets have profile assignments or explicit unsupported entries." The classification file enumerates `lib`/`bin`/`test`/`custom-build` targets and named features, but says nothing about doctest execution per crate, and `validate_targets` only ranges over `cargo metadata`'s `package.targets` (which never contains a "doctest" entry — doctest enablement is a property of `lib` targets in metadata, surfaced as `doctest: true`). No crate currently runs `cargo test --doc`. The omission isn't introducing risk today (Sifr's library doctests are minimal), but the exit-criteria sentence is not technically satisfied. Worth either declaring doctests "explicitly disabled" with a reason in the classification (the path the plan permits) or threading `doctest: true/false` from metadata into the guardrail.

3. **`crate_test_membership` is duplicated across all four profile files.** `create-pr.json`, `merge.json`, `nightly.json`, `release.json` each carry an identical 19-suite block (the only legitimate per-profile variance would be `modes`/`status`). The plan allowed this shape ("Replace the hard-coded crate test membership in `ProfileRunner.run_crate_tests` with profile-owned data, **or extend the profile schema with an explicit crate test list** while preserving the current facade behavior"), so the duplication isn't a violation. But: (a) drift between the four files is silently legal — `_crate_membership_self_test` (`selftest.py:85-178`) only loads `merge`, not the others; (b) the schema does not require crate_test_membership for v2 profiles, but `crate_test_suites_for_mode` errors at run time if it's missing; (c) a future "remove a crate from merge" change has to be repeated four times. A single shared file referenced by name (or a strict equality assertion between profiles) would harden this; either is reasonable Wave-2-or-later cleanup.

4. **`first_party_compiler`-only enforcement.** `validate_cargo_metadata_classification` only requires merge membership for packages classified `first_party_compiler` (`coverage_matrix.py:378-386`). `first_party_runtime` (`sifr_runtime`, `sifr_stdlib`) and `first_party_tooling` (`sifr`, `sifr_lsp`, `sifr_package`) are not enforced. Today all are present, so no gap exists, but if a future PR accidentally drops `sifr_runtime` from membership it would not be caught here. Spec language ("every first-party compiler crate with tests runs in merge") matches the implementation, so this is consistent with the letter of Wave 1; tightening to "any first-party crate with tests" would harden future regressions.

5. **`sifr_cli_bin` carries `status: "blocking"` + `executed_in_merge: false`.** The schema and validator permit this combination, and it's semantically correct (the suite is blocking *for create-pr*, where it runs in smoke mode, while merge runs the broader `sifr_cli_full`). But there is no rule preventing a future addition that sets `status: "blocking"`, `modes: ["full"]`, and `executed_in_merge: false` — the runner would still execute the suite (because the gate is only `status == "red-blocker" and not executed`), while the data would claim it isn't. A targeted schema check ("if `executed_in_merge` is false and modes contain `full`, status must be `red-blocker`") would close this. Optional.

6. **Two duplicate `cargo metadata` invocations per validation run.** `workspace_package_names` (`profiles.py:170-194`) and `load_cargo_metadata` (`coverage_matrix.py:389-410`) each shell out to `cargo metadata --locked --no-deps --format-version 1` under `CARGO_NET_OFFLINE=true`. They share no cache. The Wave 0 doctor lane and area `manifest.json` already give a 60-second timeout headroom; the duplicate call is wasteful, not incorrect. Caching the parsed metadata once per process would be a small ergonomic win.

7. **Two suites can share a `package` in the merge dict.** `validate_cargo_metadata_classification` builds `merge_packages` by `suite.get("package")` (`coverage_matrix.py:363-367`). Today `sifr_cli_bin` is smoke-only so the `sifr` key resolves to `sifr_cli_full`; `sifr_runtime`/`sifr_runtime_http` both contain `"full"` but only one wins. Practically the surviving entry has `executed_in_merge: true`, so the assertion passes. If anyone later adds a second `full`-mode suite per package, the silent overwrite could mask a misconfigured entry. A simple "collect, then assert at-least-one executed" pass over a list-of-suites-per-package would be more robust.

8. **Merge wall time exceeded the warm budget (986.72s vs. 900s warm / 1500s cold).** The execution checklist documents this and defers batching/cache-budget work outside Wave 1 scope. The Wave 1 plan text says "If the merge lane exceeds the documented budget, ship sharding or profile execution parallelism in the same PR" — interpreted strictly against warm budget, that didn't happen; interpreted against cold budget, the merge is fine. The plan's own checklist entry resolves this ambiguity by classifying the warm-budget excess as Wave-2-or-later batching work, which is consistent with the existing warm-budget advisory predating this PR. Flagging here only so future readers don't re-discover it.
