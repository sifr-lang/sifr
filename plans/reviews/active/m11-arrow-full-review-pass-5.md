## Blocking finding

### NB-D — Async loops never run the moved-across-loop check; check-clean per-iteration move of an owned Arrow value (reproduced live in four shapes; pre-existing for Buffer on main)

```python
def consume(own a: python.ArrowArray) -> int: ...

async def readings() -> AsyncGenerator[int, GeneratorCloseError]:
    yield 2

async def run(own v: python.ArrowArray) -> Result[None, GeneratorCloseError]:
    async for i in readings():
        x: int = consume(v)                                  # check-clean!
    xs: list[int] = [consume(v) async for i in readings()]   # check-clean!
    s: set[int] = {consume(v) async for i in readings()}     # check-clean!
    d: dict[int, int] = {i: consume(v) async for i in readings()}  # check-clean!
```

Each shape individually passes `sifr check` with no errors (all four reproduced live at HEAD, plus the `python.Buffer[uint8]` variant). `sifr emit` shows the moved value inside a real loop — for the list comprehension: `loop { ... Some(i) => { __sifr_async_list_comp.push(consume(v)); } ... }` with `consume` taking `PythonArrowArray` by value — a guaranteed rustc E0382 on any program that reaches codegen. The sync counterparts of all four shapes are correctly OWN-0004-rejected (verified live in the NB-C matrix above), so this is precisely the unremediated half of NB-C.

Root cause: the snapshot mechanism was added to the sync paths only. A repo-wide grep shows `save_moved_state` in `statements/control_flow.rs` (sync `for`/`while`), `methods_lambdas_and_comprehensions.rs`, and `generator_expression.rs` — and nowhere in `lower_async_for` (`crates/sifr_lowering/src/lower/async_for.rs:173`) or any of the async comprehension lowerings (`crates/sifr_lowering/src/lower/async_comprehensions.rs` — `lower_list_comp`, `lower_set_comp`, `lower_dict_comp`, `lower_single_async_generator`), which are dispatched *before* the fixed sync paths (`methods_lambdas_and_comprehensions.rs:552`, `core_and_calls.rs:76-78`). Async generator *expressions* happen to fail closed today (ASYNC-0001 in my probe), but the statement and all three comprehension forms are open.

Classification: both async files are untouched by this branch (`git diff origin/main..HEAD` on them is empty; `async_comprehensions.rs` was last modified by the M10 buffer activation, `0179378b1`), and the Buffer variant is check-clean at HEAD — so this is a pre-existing M10 hole inherited by all five Arrow kinds. That is **exactly the situation pass 1 classified blocking for B3 and pass 4 classified blocking for NB-C** ("pre-existing for `python.Buffer`, now inherited by all five Arrow kinds"), it violates the acceptance item "Ownership transfers once and remains moved even if a consumer later fails" and the check⇒compile contract every prior pass enforced, it contradicts the pass-4 re-verified claim that loop statements reject this shape (true only of sync loops), and async pipelines consuming Arrow batches per iteration are a realistic delivery shape for a milestone whose consumers are Python data producers (M8 delivered async contexts as a first-class surface). Holding the line here is required for consistency; waving it through would apply a weaker standard to `async for` than pass 4 applied to `[... for ...]`.

**Remediation (narrow):** run the same `save_moved_state`/`moved_since`→OWN-0004 snapshot over the async-for statement body (`async_for.rs`) and the async comprehension element/filter bodies (`async_comprehensions.rs`, all four entry points), mirroring the sync placement (snapshot after the once-evaluated iterable lowering, report after body lowering); extend `comprehension_and_generator_bodies_cannot_repeat_affine_moves` (or a sibling) with async-for-statement and async list/set/dict fixtures for Arrow and Buffer.
