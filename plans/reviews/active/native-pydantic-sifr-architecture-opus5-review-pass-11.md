### B-1 — The string node's fixed pipeline (630–634) is refuted by two mandatory anchor parameters

> **631–634:** "Its fixed pipeline is **input conversion, length checks, pattern check, whitespace stripping, then case conversion**"

Upstream strips **first**. `pydantic-core/src/validators/string.rs:110-166`:

```rust

if self.strip_whitespace { str = str.trim(); }        // :113-115
let str_len = ... Some(str.chars().count()) ...       // :117-121  min/max on the TRIMMED str

let py_string = if self.to_lower { ... } else if self.to_upper { ... }  // :158-162
```

Two parameters of `validators/text_bytes::test_constrained_str` (row **1236**, ps_5) fail under the document's order:

- `tests/validators/test_string.py:87` — `({'max_length': 5, 'strip_whitespace': True}, '1234  ', '1234')`. `'1234  '` is 6 characters. Document order checks length before stripping → `string_too_long`. Upstream strips to `'1234'` (4) → **success**.
- `tests/validators/test_string.py:90` — `({'strip_whitespace': True, 'pattern': r'\d+$'}, 'foobar 123 ', 'foobar 123')`. The trailing space defeats `\d+$`. Document order checks the pattern before stripping → `string_pattern_mismatch`. Upstream strips first → **success**.

The upstream inline comments at `:86` and `:88` say the opposite of the code; the code and the expected values agree with each other, and `:76`/`:89` (case conversion last) are consistent with both readings, so those two parameters are the only discriminators — and they discriminate against the document.

*Fix (subtractive reorder):* "input conversion, whitespace stripping, length checks, pattern check, then case conversion."

### B-2 — Smart-union clause 1 (847) is over-broad: it makes clause 2 unreachable, diverges from the pin, and the anchor chosen for field-count ranking cannot exercise it

> **847:** "1. an exact successful candidate short-circuits,"
> **848–849:** "2. otherwise record-like candidates rank first by the internal count of successfully validated declared fields,"

Upstream's short-circuit arm is `(Some(Exactness::Exact), **None**)` — exact **and no field-count data**. `pydantic-core/src/validators/union.rs:121-129`:

```rust
Ok(new_success) => match (state.exactness, state.fields_set_count) {
    (Some(Exactness::Exact), None) => { /* exact match with no fields set data, return immediately */ }
    _ => { /* fall through to ranking at :144-156 */ }
```

A record-like candidate always populates `fields_set_count` (`state.add_fields_set`, `:176`), so an exact record candidate **never** short-circuits. Three independent consequences:

1. **Internal contradiction.** As written, clause 1 short-circuits on the first exact record candidate, which makes clause 2's field-count ranking unreachable in exactly the case it exists for.
2. **Pin divergence.** `tests/validators/test_union.py:1000-1021 test_td_smart_union_by_fields_set`: `td_a = {x:int}`, `td_b = {x:int, y:int}`, run through `permute_choices` in **both** orders, asserting `validate_python({'x':1,'y':2}).keys() == {'x','y'}`. With order `[td_a, td_b]`, td_a succeeds `Exact` with `count=1` (extra `y` ignored). Clause 1 as written returns td_a → `{'x'}` ✗. Upstream ranks `1 < 2` at `:150` → td_b → `{'x','y'}` ✓. Same divergence for `{'x':1,'y':'2'}` and `{'x':'1','y':2}`. `TestSmartUnion::test_fields_set_ensures_best_match` (`:885`), `test_nested_unions_bubble_up_field_count` (`:1194`), and `test_smart_union_extra_behavior` (`:1300`) are the same class. These are collected `same` nodes, binding under **1187–1190**.
3. **The capability has no discriminating anchor.** Row **1252** names `test_smart_union_does_nested_typed_dict_field_counting` for this, but it cannot discriminate: `td_a={sub:{x:int}}` / `td_b={sub:{y:int}}` with `typed_dict_total` defaulting to `True` (`python/pydantic_core/core_schema.py:51,89`) means the nested required key makes exactly one candidate succeed per input. `test_smart_union_model_field` also cannot (counts tie at 1; exactness decides). So clause 2 and ps_7's "Implement deterministic smart-union ranking" (**1697**) have **no** anchor that exercises them — against ps_0's gate requirement at **1569–1570**.

Clauses 3–5 are correct as written: `:150-151` uses exactness only on equal/absent counts; `:154` requires *strictly* better, so first-declared wins ties; `:160-163` records errors only while `best_match.is_none()`, giving declaration-order candidate errors on total failure.

*Fix:* clause 1 → "an exact successful candidate with no field-count data short-circuits"; add `test_td_smart_union_by_fields_set` (or `TestSmartUnion::test_fields_set_ensures_best_match`) to row 1252.
