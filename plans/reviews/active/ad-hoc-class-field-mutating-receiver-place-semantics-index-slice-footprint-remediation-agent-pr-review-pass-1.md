### What I verified (all clean)

**1. The two additions close exactly the unchecked-base hole, with no weakening or new root-only over-rejection.**
`root_binding_id` (`method_receiver_places.rs:614-622`) only walks `Name`/`FieldAccess`/`Index`/`Slice`, so for a base like `self.pick().values` it returns `None` and pre-fix both arms pushed *nothing* for the object — the base's nested reads/calls/moves vanished entirely. The `Dynamic(root)` push is retained ahead of the recursion and is still load-bearing: for a `Name` base the recursion yields `Place(root, [])` (equal reach), but for a resolvable `FieldAccess` base it yields the *narrower* `Place(root, fields…)`, so removing the explicit `Dynamic` push would weaken sibling-disjoint collapse. Conversely the recursion cannot widen a name-rooted base beyond `Dynamic(root)` for that root, since `Footprint::Dynamic(root)` (`footprint.rs:20`) matches any place with the same root and therefore subsumes every same-root `Place`. New footprints therefore appear only in two genuinely-previously-dropped cases: non-name-rooted bases, and inner index/slice operands of nested subscripts (`a[i][j]` previously dropped `i`). Both are real evaluations, so this is the pre-existing conservative policy applied uniformly, not a new policy.

### Findings

**1. Non-blocking — no positive (accepted) coverage for the newly-widened index/slice base shape, and pass-side green is not claimed at this commit.**
`crates/sifr_lowering/src/lower/method_receiver_places/footprint.rs:108`, `:121`

The change adds footprints in precisely one shape — an argument subscript whose base is not name-rooted (`f().field[…]`, `self.pick().values[:1]`) or a nested subscript's inner operand. Grepping the whole first-party corpus, that shape appears *only* in the three artifacts added by this commit: no `demos/*.sifr`, no `crates/sifr/tests/e2e/pass/*.sifr`, and no lowering unit test exercises `call().field[…]` or `x[i][j]` in argument position and asserts it still **compiles**. So there is currently no regression guard proving the widening does not over-reject a *disjoint* base, e.g. `self.update(other.snapshot().values[0])` (footprint `Place(other)`, root ≠ `self` → must still lower) or `self.update(other[0][1])`.

This matters more than usual here because the reported evidence at `ad655b23d` covers the negative side (`sifr_lowering` 950 pass, annotated fail corpus 566/566) but explicitly does **not** claim a green e2e pass suite / create-PR profile — both attempts were invalidated by the shared-host Python doctor timeout. The immediately preceding analogous footprint-widening commit in this same workstream, `ac31b0908` ("fix callable field invocation overlap footprints"), handled this by adding a dedicated positive fixture `class_field_callable_invocation_disjoint_sibling.sifr` plus its entry in `verification/areas/core_language/data/create_pr_e2e_manifest.json`. No such guard accompanies this commit. (The manifest itself needs no edit for a fail-only fixture, and `test_e2e_fail` discovers `tests/e2e/fail/` by directory scan — those are correct as-is.)

Suggested closure: add one pass fixture (or one `lower_module(...).expect("should lower")` unit test in the new module) covering a disjoint non-name-rooted subscript base under a mutable receiver, register it in the create-PR manifest if it is a pass fixture, and land the uncontended create-PR retry so pass-side non-regression is actually claimed rather than inferred.
