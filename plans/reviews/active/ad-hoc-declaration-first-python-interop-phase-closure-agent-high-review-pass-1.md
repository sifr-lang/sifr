## BLOCKER

**B1 — The ellipsis-only body rule is not enforced; a real body on a `@python` declaration is silently discarded.**
`crates/sifr_lowering/src/lower/python_interop/stub_syntax.rs:35-66` — `classify_python_interop_stub_body` errors only when a body *mixes* an ellipsis with other statements; a decorated function whose body contains **no** ellipsis falls through to `PythonInteropStubBody::Normal` with no diagnostic, the declaration metadata is still attached (`annotations_and_function_lowering.rs:633-661`), and codegen unconditionally replaces the body (`crates/sifr_codegen/src/python_interop_direct.rs:32-58`).
**Reproduced by me:** `@python(json.dumps)` on `def dumps(...) -> Result[str, PythonError]: return "sifr-body"` — `sifr check` prints `no errors found`; `sifr emit` shows the generated `fn dumps` calling `json.dumps`; the user's body is gone. Also reproduces for `@python.coroutine` on a real `async def` body and for `@python(Self.*)` methods.
This violates the locked End-State Decision "Declaration bodies are ellipsis-only" and the M3 task "Accept ellipsis only as the complete body", and breaks M0's "every public syntax form maps to one HIR/runtime contract" — the same decorated `def` means two things, resolved silently in Python's favor. The only existing negative test covers the ellipsis-plus-statement mix (`python_interop_tests.rs:763-781`); no no-ellipsis negative exists anywhere.
**Remediation:** emit `SIFR-PYCALL` invalid-shape when a python-decorated body lacks the exact single ellipsis; add function/coroutine/method negatives to the compile-fail corpus.

## MAJOR

**M1 — Nested `dispatch=current` callback creation/close panics (`BorrowMutError` → `PanicException`).**
`crates/sifr_runtime/src/python/callbacks/current.rs:178-187` holds the `CURRENT_TARGETS` `RefCell` shared borrow across the entire user handler invocation (the `Ref` temporary lives for the `map_or_else` expression). Creating a second current callback (`current.rs:154-156`, emitted via `current_callback_with_owner`, `sifr_codegen/src/python_interop_callbacks.rs:78`) or closing a *different* current callback (`current.rs:74-76`) from inside a handler takes `borrow_mut` on the same thread → panic. No lowering diagnostic forbids calling a callback-taking declaration inside a handler (the only static code is `SIFR-PYCB-0001`, declaration shape), and the runtime reentrancy guard rejects only the same owner. This is a user-triggerable panic escaping the checked `PythonError` model — a breach of the core "no user-triggerable runtime panics" guarantee and M9's "fails deterministically" acceptance. There is no nested-current-callback test.
**Remediation:** copy the `Copy` target pointer out of the registry and drop the `Ref` before invoking (safety unchanged: `!Send` + drain-gated removal); add a nested test.

**M2 — `async with` honors Python truthy suppression for Sifr-origin errors; `with` correctly refuses.**
`crates/sifr_codegen/src/stmt_support_emitter/python_context/async_context.rs:380-418` (`python_error_exit`) classifies a no-replay `PythonError` as `PythonAsyncExitCause::Sifr` but then feeds both cause branches through one match whose `Ok(PythonExitDecision::Suppress) => {}` arm swallows the error. I verified the runtime provides no cause gating: the loop-thread terminal derives the decision purely from `__aexit__` truthiness (`async_declaration.rs:267-270` → `context_ops.rs:213-220`). The sync adapter routes the same case to an unsuppressible path with `record_context_ignored_suppression` evidence (`python_context/sync.rs:545-640`). Every user-constructed `raise PythonError("…")` has `__sifr_python_error = None`, so: `async with` a manager whose `__aexit__` returns truthy + a body raising a user-constructed `PythonError` → silently swallowed, no evidence, while the identical `with` propagates. Direct violation of M8's "suppression only for originating Python exceptions … attach ignored truthy decisions as evidence".
**Remediation:** split the decision handling per cause branch to mirror sync; add the async truthy-exit/Sifr-cause fixture (the existing truthy-exit matrix covers cancellation/timeout/fault but not the no-replay `PythonError` shape).

**M3 — Consuming-close obligations are bypassed by reusable closure captures; `sifr check` accepts a double close.**
Verified by compiler probes: a `cleanup=close` opaque whose consuming `close(own self)` is called **twice** through a nested `def`/`lambda` defined inside `try:` passes `sifr check` with no errors, while the direct double close and the outside-`try` closure shape are both correctly rejected. Root cause: `affine_reusable_callable_capture` (`crates/sifr_lowering/src/lower/ownership_diagnostics.rs:102-134`) keys on `contains_affine_resource` (`sifr_type_system/src/types/type_queries.rs:29-85`), which covers only Buffer/Arrow/DLPack — opaque `cleanup=close|async_close|context|async_context` obligations are excluded, and the must-use side table doesn't model closure-mediated consumption. Today the accepted program cannot actually build (it trips an unrelated pre-existing `compile_error!` for nested defs in `try`), so there is no compiled double-free — but `check` reporting "no errors" for an ownership violation is a soundness gap in the analysis the phase claims closed, and it becomes a real double close the moment that emission gap is fixed.
**Remediation:** extend the capture rejection (or must-use table) to opaque cleanup obligations.

**M4 — Stale `SIFR-PYRES-0002` reservation gates survive full activation, including one permanently half-activated surface.**
Reproduced by me: `@python.attr(Self.name)` misplaced on a top-level function errors `SIFR-PYRES-0002: … belongs to a later phase` (`crates/sifr_lowering/src/lower/python_interop.rs:132-135`, `334-337`, `761-770`) — factually false after M17; these are placement-misuse shapes owed stable `PYCALL`/`PYCTX` diagnostics. Worse, `@python.opaque(type=bridge.…)` at `python_interop.rs:573-585` is *permanently* reserved: bridge targets are active for functions and buffers but bridge-defined opaque classes are neither activated nor given a terminal unsupported-by-design contract — exactly the intermediate state the Delivery Rule forbids at closure. `docs/errors/diagnostic-codes.md:252` still documents PYRES-0002 as "no active production lowering yet".
**Remediation:** re-key misuse shapes to stable diagnostics; either activate bridge-opaque or make it a terminal documented rejection; retire/rescope PYRES-0002 and its dead scrub (`callbacks.rs:383-386`).

**M5 — `sifr python certify --check` mutates `Cargo.lock`.**
`crates/sifr/src/python_cli.rs:527-538` builds the certification context with `CargoLockMode::Normal` for both authoring and the `--check` recheck (reached from `:504-510`); `Normal` omits `--frozen` (`sifr_package/src/cargo/lock_modes.rs:14-23`). Live-reproduced: in a package with no `Cargo.lock`, `certify --check` created one even while failing on a missing venv — while `python check` and `bind --check` (Frozen) correctly refused with `SIFR-PACKAGE-0101` and wrote nothing. Violates M14's read-only recheck contract.
**Remediation:** use `CargoLockMode::Frozen` on the `--check` path (as `python_binding_cli.rs:246-250` does); extend the non-mutation fixture to a lockfile-less checkout.

**M6 — `bind` / `bind --check` / `certify` interpreter invocations omit `-B` and write `.pyc` into the package's venv.**
`crates/sifr/src/python_binding_cli.rs:407-410`, `crates/sifr/src/python_cli.rs:722-727` and `:782-789`, `crates/sifr/src/python_dlpack_certification_cli.rs:130-135`, `crates/sifr_driver/src/build/python_certification.rs:23-29` — all spawn `-I` without `-B` while importing third-party distributions. **M7 — `bind` silently rebinds cross-module class annotations to a same-named local opaque class.**
