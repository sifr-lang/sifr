## New findings

### MAJOR 1 — Ownership election over unanalyzable documents persistently suppresses all package-scoped Python diagnostics (empirically reproduced)

`is_python_package_diagnostic_owner` (`crates/sifr_lsp/src/python_declarations.rs:298-308`) elects the minimum URI over **all open store documents** whose path resolves to the package root — but the pre-existing analysis layer cannot serve every such document. The project loader is a flat scan (entrypoint + top-level `*.sifr` of the manifest directory, `crates/sifr_frontend/src/graph_cache_and_queries/loaders.rs:144-162`); any open `.sifr` under the package root but outside that set (e.g. a module in a nested directory — a layout the CLI supports, see `verification/areas/project_workspace/fixtures/project/workspace_dotted_helper_run/helpers/value.sifr`) is dropped from `files_by_uri` with **empty** load diagnostics (`analysis_workspace.rs:348-355`) and removed from the standalone-document map on open (`analysis_workspace.rs:52`), so `document_diagnostics` for it fails with an internal "analysis is unavailable" error before ever reaching `python_declaration_snapshot`. If that document's URI sorts below every analyzable document, it wins the election; `for_document` (`python_declarations.rs:96-114`) then excludes all `file: None` package diagnostics from every sibling, and the "owner" can never publish them. Reproduced against HEAD: with the stale-certification fixture, opening nested `a/aux.sifr` made `SIFR-PYZC-0001` disappear from both `src/main.sifr` and `z.sifr` while `aux` errored — **persistent** for as long as the document is open, healed by no lifecycle event except closing it, with zero user-visible indication. This is the anti-conservative direction pass 4 graded major: `sifr check` reports the package error; the editor silently reports nothing, package-wide, and the trigger is mundane (any nested/excluded `.sifr` whose URI sorts first — `src/api.sifr` vs `src/main.sifr` already does it, since every non-entrypoint `src/` module is loader-excluded). Remediation direction: elect the owner among documents the analysis layer can actually publish for (e.g. project `files_by_uri` membership, with a standalone-document fallback), plus a discriminating regression for the excluded-document shape, and a ledger sentence if any residual remains. The unanalyzable-document behavior itself is pre-existing and out of M15 scope; what is new and in scope is the election that couples sibling documents' package diagnostics to it.

### Nits (no individual remediation demanded; ledger at next touch)

- **Relative-import aliases are invisible to the hover-identity map**: `callable_definitions` (`crates/sifr_frontend/src/editor_semantics.rs:545-561`) records the raw `ImportFrom` module and ignores `import_from.level`, while the compiler resolves level-1 relative imports through candidate expansion (`crates/sifr_lowering/src/lower/import_resolution.rs:9-27`). In nested-module layouts, hover status enrichment through `from .helpers import f` silently drops (`hover_symbol_file` matches `module_name` exactly, `semantic_editor.rs:96-123`), or — only under an additional top-level name collision — attaches the wrong module's status. Flat layouts agree with the compiler; completion is unaffected (its `symbol_file` comes from the symbol index, `host/implementation.rs:198-208`). The ledgered "single-hop" alias scope should say "absolute single-hop".
- **Hover enrichment is structurally function-only**: semantic entries get a `definition` only for `Function` kinds (`editor_semantics.rs:505-507`) and `hover_symbol_file` filters `kind == "function"`, so an `@python.opaque` class never shows Python status/policy on hover, while completion does attach it. Consistent with the function-scoped hover-identity design reviewed since pass 2, but never itemized.
- **Symlinked bridge sources are fingerprint-invisible**: `hash_python_bridge_inputs` (`python_declarations.rs:636-646`) hashes only `is_symlink` for non-file/non-dir entries, so content edits behind a symlinked bridge `.py` never invalidate; validation reads through symlinks, so diagnostics go stale until external invalidation. Same accepted family as watcher-dependent manifest invalidation.
- **Member layouts: the fingerprint never observes the governing workspace-root `Cargo.lock`** (`python_declarations.rs:588` hashes the member-root path, a constant NotFound in member layouts) — a concrete instance of the ledgered watcher-dependent residual, sharpened by the fact that the server never registers file watchers (`client/registerCapability` absent from `crates/sifr_lsp/src`), so the "watcher" channel fires only for clients that send `didChangeWatchedFiles` unprompted.
- **Lane-wrapper vacuity**: all four commands in `verification/areas/python_interop/runner/lsp_declaration_authoring.py` are name-filtered `cargo test` invocations, which exit 0 on zero matched tests; renaming the covered tests away would leave the blocking lane green. Latent only — all filters currently match.
- **`workspace_member_python_requirements_are_validated`** asserts the `SIFR-PYTRUST-0005` code but not that the message names `numpy`/the member, so wrong-attribution regressions would pass.
- **Gate-paragraph lane enumeration**: the post-pass-5 paragraph (`:2238-2244`) omits `analysis 48/48` where the pass-3/4 paragraphs listed it (pass-4's mirror-image omitted driver). The enumeration was never exhaustive and the lane demonstrably runs and passes (re-verified in this pass's gate re-run), so the headline "passes every blocking lane" stays true.
- **"Caches shrink only on watcher invalidation"** (`:2230`) is over-broad: the plan-snapshot `entries` cache clears on every source lifecycle event (`python_declarations.rs:75-77`); the sentence is exact only for `environments`/`target_inspections`.
- Duplicated bridge-marking/dedup logic between `probe_python_interop_plan` and the LSP's `probe_python_targets` (`python_interop.rs:127-155` vs `python_declarations.rs:247-296`) keeps the "single interpretation" invariant by copy-parity rather than structure — byte-equivalent today.
