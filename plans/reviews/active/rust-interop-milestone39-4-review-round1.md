## M39.4 review

### Blocking findings

1. **`GeneratedGlueToken` constructor breaks the architectural capability invariant.** `crates/sifr_runtime/src/interop.rs:189` exposes `pub const fn new_for_generated_glue() -> Self`. The arch (`internal_docs/rust_interop_architecture.md:454-462`) is explicit: "Only generated glue can construct `GeneratedGlueToken`, so only generated wrappers can call `mark_closed` and `mark_poisoned`. Package-local bridge code may borrow or consume handles through the accessors but must not manipulate state flags directly." With a freely-callable `pub const` constructor, any user bridge file (or shared bridge crate that depends on `sifr_runtime`) can mint a token and flip handles to `Closed`/`Poisoned(redacted)` — the documented trust boundary is purely nominal. M39.4 owns `Handle<T>` representation, so this is part of the milestone deliverable. Fix: gate the constructor behind a sealed path (e.g., `#[doc(hidden)] pub mod __generated_glue { pub fn new_token() -> super::GeneratedGlueToken { ... } }` plus a doc comment marking it unstable / generator-only) or move both `Handle::mark_closed`/`mark_poisoned` and the token under one `#[doc(hidden)]` `__generated_glue` namespace that the architecture references. Whatever is chosen has to be reflected in the architecture doc too if the seal is by convention.

2. **`crate::__sifr_bridge::<module>::<Name>Bridge` types are recorded in the plan but never emitted into the user crate.** The M39.4 DoD says "Generate explicit bridge types for records, closed enums, and errors under `crate::__sifr_bridge::<sifr_module_path>::<Name>Bridge`." The codegen builds `RustBridgeContractPlan.generated_types` and signature contracts referring to those paths, but a grep over `crates/sifr_codegen/src` and `crates/sifr_driver/src` for `mod __sifr_bridge`/`__sifr_bridge` shows the only emitters are the *probe* (`rust_interop_probe.rs:183`) and unit-test fixtures. No `__sifr_bridge` module is materialized into `GeneratedBinaryProject::main_rs`/`support_modules`. So bridges that try to `use crate::__sifr_bridge::main::TokenBridge;` cannot compile, and there is no roundtrip surface for the "Supported type mappings roundtrip through Rust bridge calls" DoD bullet. Fix: extend project_codegen to emit a deterministic `mod __sifr_bridge { pub mod <module> { pub struct <Name>Bridge { ... } /* From/Into to/from Sifr generated types */ } }` per non-empty `bridge_contracts.generated_types` entry — paired with the existing `RustGeneratedBridgeModule` registration so cargo_inputs already accounts for it.

3. **Cross-module references in `generated_field_rust_type` and `bridge_type_contract` collapse to the declaration's own module.** `crates/sifr_codegen/src/rust_interop_bridge_contract.rs:680` calls `generated_bridge_type_path(&None, name)` for any nested `Type::Class { name, .. }`/`Type::Enum { name, .. }` inside a record field. `&None` always renders to `crate::__sifr_bridge::__sifr_binary_entry::<Name>Bridge`. And in `bridge_type_contract` (`rust_interop_bridge_contract.rs:339-377`), the path uses the *declaration's* `module_name` rather than the class's defining module. This means a record/enum referenced across modules will resolve to a non-existent path, and the BTreeMap key `(Option<String>, String)` in `GeneratedTypeCollector` may collide between two different modules that happen to define a class with the same name (a record in module `a` and a record in module `b` would both file under `(None, "Foo")` via `insert_record(module_name=&None, ...)` if `generated_field_rust_type` ran — though currently it doesn't directly mutate the collector, so the immediate collision is contained). Fix: thread the *definition* module for `Class`/`Enum` types — either by carrying it on the `Type` (most invasive) or by consulting all `ModuleCatalog` entries to locate which module owns `name` and using that for the path. Until this is fixed, multi-module record/enum bridges silently produce wrong paths instead of stable `SIFR-RUST-TYPE-*` diagnostics.

4. **Closed-enum discriminant handling silently relabels invalid discriminants instead of rejecting them.** `crates/sifr_codegen/src/rust_interop_bridge_contract.rs:626-661`: when the Sifr enum declares an explicit `i64` discriminant that doesn't fit `u32` (e.g., `RED = -1` or `BIG = 1 << 33`), `u32::try_from(value).ok().unwrap_or(next)` falls back to the running counter — and `next = discriminant.saturating_add(1)` then continues from there. The architecture (`rust_interop_architecture.md:434`) says "Closed enum bridge types use explicit numeric discriminants assigned by declaration order unless the Sifr enum declares stable discriminant values. The default representation is `repr(u32)`." Silently rewriting a *declared* discriminant violates the "no silent behavior downgrades" rule (phase file line 333) — an explicit `-1` becoming `0`/`1`/... is a downgrade. Fix: emit `SIFR-RUST-TYPE-0001` when an explicit discriminant is negative or exceeds `u32::MAX`, instead of `.ok().unwrap_or(next)`.

5. **`bridge_type_matrix` fixture-matrix status overstates current coverage.** `verification/areas/rust_interop/data/rust_interop_fixture_matrix.json:60-63` now claims `supported_type_roundtrips: probe-only` and `unsupported_container_rejections: passing`, but the matrix entry requires the canonical pinned crates `serde, serde_json, thiserror, bytes, indexmap` (architecture matrix `plans/phases/39_rust_interop.md:271-274`) and the DoD requires roundtrip evidence. The `bridge_type_matrix/README.md` evidence pointer is to *unit tests on the contract struct* — none of the listed crates are linked, no roundtrip is exercised, and `serde_json`/`thiserror`/`bytes` aren't even direct dependencies of the workspace. A `probe-only` status is acceptable for a row that has *some* probe coverage of the listed crates, but here it has none. Fix options: revert this row's `positive_evidence.status` to `planned`, or constrain the README's claim to only the `unsupported_container_rejections` negative and keep the positive as `planned` until at least the `bytes`/`indexmap` direct-binding probe lands. The negative `passing` claim is borderline-defensible because the Sifr-side `set[T]`/`tuple[...]` rejection is genuinely wired and tested — but the row as a whole shouldn't claim positive coverage.

### Non-blocking concerns

- **Conversion-runtime variants are dead code today.** `RustInteropConversionError::{Width, Overflow, InvalidUtf8, RecordLayoutMismatch, InvalidEnumDiscriminant, UnsupportedContainer}` is defined (`crates/sifr_runtime/src/interop.rs:84-107`) but never produced anywhere. That's expected while generated glue is still unimplemented (blocker #2), but flag in the milestone notes so it isn't mistaken for live conversion coverage.

- **`Handle<T>` Send/Sync opt-in mechanism not designed.** `PhantomData<Rc<()>>` correctly makes the default `!Send + !Sync`, matching the architecture default — but there is no path forward for `@rust.opaque(send=True)` to lift that without either an `unsafe impl Send` or a different type. That's M39.6 work; just note that the current type signature locks future Send opt-in into a wrapper rather than the same `Handle<T>` (`crates/sifr_runtime/src/interop.rs:194-198`).

- **Signature-shape probe synthesizes empty stubs for any path containing `…Bridge`.** `rust_interop_probe.rs:196-214` heuristically extracts identifier-like substrings ending in `Bridge` and emits `pub struct <Name>Bridge;` in the probe crate. That works for the current test (record return), but: (a) the stubs have no fields and no `From`/`Into`, so the moment generation lands and the contract refers to a concrete user-side definition with fields, the probe will diverge from the real type; (b) the heuristic relies on the literal suffix `Bridge` — any future helper named `…Bridge` would be silently struct-stubbed too. Plan to switch the probe to reuse the same generated bridge sources, not heuristic stubs.

- **`probe_cargo_toml` bakes the source-tree `sifr_runtime` path via `env!("CARGO_MANIFEST_DIR")` plus `parent().join("sifr_runtime")`** (`rust_interop_probe.rs:90-99`). Fine for local dev but it points at `<repo>/crates/sifr_runtime` from a *compiled* `sifr_driver` binary. A shipped compiler will reach a path that doesn't exist on the user's machine, so the probe will fail with "no such file" rather than a clean diagnostic. Out of scope for M39.4 milestone gate but worth filing.

- **`unique_probe_nonce` collisions.** `SystemTime::now()`-derived nanos plus `std::process::id()` is fine in practice, but if two probes inside the same compiler run hit the same nanosecond the temp dirs collide. The `fnv1a64_hex` of `(package_id, dotted_path)` is already in the dir name, so as long as the same probe isn't run twice in a tick this is moot — note for the record only.

- **Implementation summary listed `crates/sifr_driver/src/build/rust_interop_tests.rs` as changed**, but `git diff` shows no edits there — only the new `rust_interop_contract_tests.rs`. The summary is mildly inaccurate; the existing test file is untouched.

- **Stale review file in tree:** `plans/reviews/active/rust-interop-milestone39-4-review-round1.md` is untracked. If it's the prior round's artifact for this same milestone, normal practice is to either commit it or move it under `plans/reviews/archive/` before the milestone PR lands.

### M39.4 verdict

Not yet satisfied. The contract *plan* (signatures, generated bridge type metadata, cache-key fragment, unsupported-type diagnostic before final build, signature-shape probe) is in. But two milestone-level deliverables are missing or under-enforced: the `crate::__sifr_bridge::<module>::<Name>Bridge` types are not generated as Rust source (blocker #2), and the `GeneratedGlueToken` capability seal is open (blocker #1). The cross-module path bug (#3) and silent discriminant relabel (#4) are correctness gaps within work the milestone explicitly owns, and the `bridge_type_matrix` evidence claim (#5) overstates what's actually covered.
