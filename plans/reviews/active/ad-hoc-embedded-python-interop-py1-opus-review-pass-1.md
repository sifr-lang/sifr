## Code review — milestone_py_1 (Python environment discovery & probe)

### Blocking findings

1. **Probe + resolver are never invoked from production code paths.** `probe_python_environment` and `resolve_python_environment` (and `digest_python_environment_probe`) have no callers outside of unit tests (`grep` across `crates/sifr_driver/`, `crates/sifr_codegen/`, `crates/sifr/` returns nothing). `PackageBuildCacheInputs::python_probe_digest` (graph/digest.rs:41) is a struct field that no production site populates. The milestone DoD says "probe output deterministic and *part of build cache keys*" — the field exists and the canonical digest functions exist, but no build flow computes and feeds it. Either wire it through `derive_package_graph`/build planning before claiming the DoD, or rewrite the milestone status (issue file currently says this is done).

2. **`path_is_within` compares a *resolved* sys.prefix against an *unresolved* `venv_root`.** environment.rs:202–213 normalizes both sides via `normalize_path` (curdir/parentdir collapsing only — no symlink resolution), but the probe canonicalizes `sys.prefix` via Python `Path(...).resolve()` (environment.rs:454). If the configured `venv` traverses a symlink (very common when uv places `.venv` under a worktree mounted via symlink, or on macOS `/var → /private/var`), every probe will spuriously raise `PYENV_VENV_PREFIX_MISMATCH`. Canonicalize `request.venv_root` with `std::fs::canonicalize` before comparison, or apply the same `.resolve()` normalization on both ends.

3. **No enforcement that `[python].venv` is declared by the root application.** Core decision says "the root Sifr application selects exactly one uv-created Python environment", and the `SIFR-PYENV-0001` help text already says "configure the root application [python] table". But `python_environment_selections` (environment.rs:279) accepts a venv from *any* package, library or binary. A dependency declaring `[python].venv` will silently become the selection (or trigger `PYENV_MULTIPLE_SELECTIONS` if combined with the root's). Either reject library `[python].venv` declarations at manifest parse time, or filter selections to the root in `resolve_python_environment`. There is also no test covering this.

### Non-blocking findings

4. **Architecture validation gaps.** The probe captures `pointer_width`, `libpython`, `soabi`, `extension_suffixes`, and `cpython_version_tuple` (environment.rs:42–46) but `validate_python_environment_probe` validates none of them. A 32-bit interpreter on a 64-bit Sifr binary, a CPython 2.7/3.6 install, or a wildly mismatched `soabi` would all pass. They do feed the cache digest, but the milestone explicitly includes "reject unsupported interpreters". Add at least a minimum-version check and a `pointer_width == usize::BITS` guard.

5. **Verification fixtures are stub-level relative to DoD.** `verification/python_interop/fixtures/env_probe/positive_probe.json` carries 4 fields; `negative_rules.json` is just a flat list of rule names. `validate_fixture_contract` (env_probe.py:48) only asserts those names are present — it does not feed any negative-case JSON into the Rust validator path to confirm each `SIFR-PYENV-000x` actually fires. The Rust unit tests cover the validator separately, but the *fixture-based* coverage the milestone claims isn't really there. Either include per-rule probe-JSON cases that the runner can feed back into the validator (e.g. via a thin Rust binary or by structuring the negative JSON as full probe payloads), or scope the claim down.

6. **Test coverage gaps.** No test asserts (a) two packages selecting the *same* venv root deduplicate cleanly into a single selection, (b) `optional_import_root_list` rejects invalid identifiers (only the absolute-venv-path case is covered for `PYENV_INVALID_CONFIG`), (c) `*` wildcard handling in `trust.python-native` doesn't poison `native_python_imports`, (d) a non-root package's `[python].venv` gets rejected (see finding 3).

7. **Probe subprocess env hygiene.** `Command::new(&request.interpreter).arg("-I")` covers `PYTHONHOME`/`PYTHONPATH`/`PYTHONSTARTUP`/user-site, but inherited `PYTHONIOENCODING`, `PYTHONUTF8`, `PYTHONHASHSEED`, `PYTHONNOUSERSITE`, locale vars can still perturb output. For "probe output deterministic", consider `.env_clear()` plus an allowlist (PATH, locale) and explicit `PYTHONIOENCODING=utf-8`.

8. **Diagnostic conflation.** `probe_script.digest()` collapses missing file / permission denied / EISDIR all into `OSError → None`, which then surfaces as `PYENV_LOCK_OR_PROJECT_STALE` with the generic "run `uv sync`" hint. A pre-check distinguishing missing/unreadable vs. read-but-different would route users better; at minimum mention "or check permissions" in the help.

9. **`validate_configured_digest_inputs` only fires on `is_file()`.** A symlink to a missing target, or to a directory, will return `false` here — fine. But `request.lock.is_file()` returns `true` for a *directory entry that is actually a regular file*. If the configured lock path points at something that's not a TOML/lock at all, the probe will pass (digest captured) and silently cache the wrong content. Not a milestone-stopper, but consider validating extension or content shape.

10. **Silent error swallowing.** `json_array` falls back to `"[]"` on serde failure (environment.rs:417). For `Vec<String>`, serialization is infallible — use `expect` to surface a real bug rather than mute it.

11. **Native-import side effects.** `import_probe(root, do_import=True)` runs full module init in the probe subprocess for every `trust.python-native` root. This is by design (trust), but worth a one-line note in `internal_docs/diagnostic_codes.md` or the SIFR-PYENV-0009 doc, so users understand why the probe can write files or open sockets.

12. **Determinism of `selected_by`.** When several packages legitimately point at the same `venv_root`, `selections.into_iter().next()` picks whichever lands first in `BTreeMap<SifrPackageId, ...>` order — deterministic but not necessarily the root. Since `selected_by` flows into diagnostics, it can confuse users. Prefer the root package or the lexically-smallest binary target explicitly.
