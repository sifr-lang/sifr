I've completed a full repository-grounded review of commit 82fec1296 against main, the M15 plan section, AGENTS.md rules, and the surrounding compiler/package/LSP code. I re-ran the new focused tests locally (7/7 pass), plus the file-size and HIR guardrails (pass). The delivered mechanism is sound in its core idea — the LSP reuses the compiler's lowered `PythonInteropPlan` and the driver's exact probe (`probe_python_interop_plan`), so status *meaning* has one authority — and the driver refactor is behavior-preserving (bridge-marking order and `selected_by` change verified equivalent). However, I found three major parity/attribution defects and several actionable minors.

## Findings

**MAJOR 1 — Python status is attributed to symbols by name/substring matching, so unrelated symbols get certified labels.**
`crates/sifr_lsp/src/python_declarations.rs:52-62` (completion match: label equals `function_name` *or its last dotted segment*) and `crates/sifr_lsp/src/python_declarations.rs:377-384` (hover match: `rendered.contains(&insight.name)` — plain substring). Consequences, directly from the string semantics:
- A pure-Sifr function named `sqrt` in another module produces a completion item labeled `sqrt`, and `enrich_completion_item` stamps it `"pythonStatus": "verified"` with detail `Python Sync · verified · math.sqrt`, even though it is not a Python declaration at all.
- Protocol methods are recorded as `Class.method` (`crates/sifr_codegen/src/python_interop_plan.rs:218`), so the last-segment rule matches any completion item named `close`, `take`, `read`, etc.
- Hover is worse: hovering `sqrt_table` produces hover text containing the substring `sqrt`, so the hover gains "Python target: `math.sqrt` / Status: **verified**".

This contradicts the milestone acceptance ("Completion never offers an untyped or unsupported declaration as certified" — here a *non-declaration* is offered as certified) and the new architecture text itself ("it is not inferred from Python hints or completion text", `internal_docs/python_interop_declaration_architecture.md:604-605`). Remediation: attribute insights by symbol identity (module + declaration name from the plan's `module_name`/`function_name`, resolved against the completion/hover symbol), not by label equality or substring containment; first-match on colliding names is also wrong when two declarations share a short name.

**MAJOR 2 — Artifact "drift" validation is self-referential: environment drift can never be detected.**
`crates/sifr_lsp/src/python_declarations.rs:289` and `:310` call `load_python_bindings(root, &artifact.environment_digest)` / `load_python_certifications(root, &artifact.environment_digest)` — passing the artifact's **own** stored digest as the expected digest. The only digest check in the loader is `artifact.environment_digest != environment_digest` (`crates/sifr_package/src/python/binding_validation.rs:44`), which is a tautology here. The compiler computes the expected digest from the **live** environment probe (`crates/sifr/src/python_runtime_context.rs:106,127`, `crates/sifr_driver/src/build/python_runtime.rs:53-54`) and rejects environment-drifted artifacts. So after an environment replacement (venv rebuilt, distributions changed), `sifr check` fails with "environment digest does not match the selected environment" while the LSP reports the artifact clean — the exact "stale authoring/certification artifacts" scenario this review was asked to verify. The watcher test only proves *malformed* artifact detection (writes `{}`), not digest drift. Typing/generated-source drift is still caught (per-binding file digests), but the diagnostic text "invalid or drifted" overclaims. Remediation: validate against an authoring digest derived from the current environment (the probe can be run and cached under the existing `external_fingerprint`), or explicitly scope the LSP check and stop claiming environment-drift parity.

**MAJOR 3 — Missing-environment error diverges from check's final-application deferral policy.**
`crates/sifr_lsp/src/python_declarations.rs:122-137` unconditionally emits Error `SIFR-PYENV-0003` when declarations exist and no environment selection is discoverable. But `sifr check` allows deferral for packages with no runnable applications (`crates/sifr/src/check_and_package_commands.rs:117-118`; `crates/sifr_package/src/python/environment.rs:187-209`) and passes cleanly — the docs added in this very PR say so (`docs/python-interop.mdx:85-89`). For a library package the editor shows an error `sifr check` never produces, violating the acceptance "LSP results agree with compiler/check results for the same package snapshot". Remediation: mirror the deferral rule (runnable-app discovery is available via the package session) and present deferred statuses without an error.

**MINOR (actionable) 4 — Environment-resolution split-brain: nearest-manifest selection bypasses graph-level validation.**
`crates/sifr_lsp/src/python_declarations.rs:216-236` walks to the nearest `sifr.toml` and calls `select_root_python_environment` directly, skipping the compiler's root-owned resolution: multiple-venv rejection, non-root `[python]` rejection, and trust validation (`crates/sifr_package/src/python/environment.rs:131-190`). The LSP can therefore probe with an interpreter that check rejects (e.g., non-root `[python]`, untrusted required imports) and show "verified" while `sifr check` errors. Relatedly, missing/mismatched Arrow/DLPack protocol certifications produce check errors via `validate_protocol_certifications` (`crates/sifr_driver/src/build/python_interop.rs:101-102`) that the LSP never surfaces even though it loads the certification artifact. Remediation: route through (or replicate the validation rules of) package environment resolution, and either surface certification diagnostics or document that scoping explicitly.

**MINOR (actionable) 5 — Synchronous per-target subprocess probes on the latency-sensitive path, no mid-loop cancellation, and a cache that misses after every edit.**
The cache key includes the source revision (`crates/sifr_lsp/src/python_declarations.rs:96-103`), and `change_document` clears the cache anyway (`crates/sifr_lsp/src/session.rs:111`), so after any edit the next completion/hover/diagnostics request re-executes one `python -I -c` per non-bridge target, sequentially, on the single-threaded session; `probe_python_interop_plan` checks cancellation only before/after the whole loop, never between subprocesses (`crates/sifr_driver/src/build/python_interop.rs:123-208`; checks at `python_declarations.rs:69,139`). A package with dozens of declarations stalls the entire server for seconds per keystroke burst. Remediation: memoize probe output per (external fingerprint, target path) so unchanged targets don't respawn interpreters, and/or accept a cancellation callback between probes. (Wave 3's "cancellation around external probes" is met literally, but the review scope explicitly flags synchronous subprocess behavior and request cancellation.)

**MINOR (actionable) 6 — Package-level diagnostics are anchored at 0:0 of every open document, including files that don't contain the declaration.**
All new diagnostics are built with `spans: Vec::new()` (`crates/sifr_lsp/src/python_declarations.rs:340`), rendered at the default 0:0 range (`crates/sifr_lsp/src/conversion.rs:415,508-513`), and appended to *each* document's diagnostics (`crates/sifr_lsp/src/diagnostics.rs:146-153`) — so an invalid target in `a.sifr` shows as an error at line 0 of `b.sifr`, duplicated per open file. The plan carries `module_name`/`function_name` and HIR declarations have spans; target diagnostics should anchor at the `@python(...)` declaration, and package-scoped diagnostics should not be replicated per document.

**MINOR 7 — Evidence overstatement in the plan and verification runner.**
The M15 "Focused evidence" claims `cargo test -p sifr_analysis` covers the compiler plan query (`plans/issues/active/ad-hoc-declaration-first-python-interop.md:2104-2106`), but no sifr_analysis test exercises `python_interop_plan` — coverage is only transitive through sifr_lsp. And `verification/areas/python_interop/runner/lsp_declaration_authoring.py:24-28` prints a hard-coded success line ("completion=verified navigation=compiler diagnostics=parity … unsupported_certified=0") that reads as measured evidence but is a constant string; the suite's real signal is only the re-run unit tests. Tighten the claims to what is actually measured.

## What checked out

- Driver refactor is behavior-preserving: bridge-marking moved but ordering relative to `validate_protocol_certifications` is inert (it reads declarations/certifications, not probe statuses), and the `selected_by: root_package_id` change in `environment.rs:215` is identical to the old `selection.package_id` value. Verified/runtime-checked/deferred semantics remain single-authority via the shared probe; invalid targets keep `Planned` → "deferred", never verified.
- Compiler-error non-promotion works: any workspace error skips probing, statuses stay deferred; the unsupported-type test confirms no verified label.
- Cache invalidation covers source/lifecycle/watcher/manifest/pyproject/lock/artifact/interpreter inputs (fingerprint reads file contents plus interpreter len/mtime); the fingerprint unit test proves selected-path tracking. Analysis module graph is user-source-only, HIR lowering is revision-cached, and `Value` mutation in enrichment is panic-safe (`data` is always an object).
- File-size guardrail (largest touched hand-maintained file: 883 lines, pre-existing), HIR guardrails, and the focused LSP tests (7/7) pass locally; all four verification profiles select the new blocking suite; the dirty `third_party/ruff` submodule was untouched.

Findings 1–3 are majors against the milestone's own acceptance criteria (status attribution correctness and compiler/check parity), and findings 4–7 are actionable minors.
