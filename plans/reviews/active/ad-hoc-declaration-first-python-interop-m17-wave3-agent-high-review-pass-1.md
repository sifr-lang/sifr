## Findings

**Minor 1 — enforcement claimed for the demo is not implemented (reporting truthfulness).**
`verification/areas/python_interop/reports/python_interop_exit_evidence.md:169` states the demo "requires a complete result with seven passing capabilities, ten compiled evidence records, and four resource-zero records", and `demos/python_ecosystem_certification/README.md:15-24` states the final line *is* the `complete:7:10:4` string — but `demos/python_ecosystem_certification/run.sh:18-21` only formats the report with `jq -r` and asserts nothing. Today the printed line can only be that string (any evidence problem raises `SystemExit` before the report is written, and `set -e` aborts), so nothing is currently false — but if the matrix later legitimately changes evidence counts, the demo prints new numbers, exits 0, and both documents go silently stale, with the "requires" claim never having been true. *Remediation:* add a `jq -e` assertion in `run.sh` that `status == "complete" and summary.passing == 7 and summary.compiled_evidence == 10 and summary.resource_zero_evidence == 4` (or soften "requires" to "reports").

**Minor 2 — no gate-level completeness assertion; profile-selection drift silently downgrades certification to partial (fail-closed gap).**
Nothing in any blocking profile or in `sifr_verify` asserts `compiled_certification.status == "complete"`; `profiles.py:132-154` only validates that selected suites *exist*. The manifest-rename direction fail-closes (unknown filter → `SystemExit`), but the inverse does not: removing e.g. `"arrow-examples"` from `verification/profiles/merge.json:104` would make every full gate run report `status: "partial"` (`certification_ledger.py:87-93`) while exiting 0 — a green merge gate with the ecosystem certification quietly not established. No stale evidence is *promoted* (the row is visibly `not-selected`), but the milestone's certification guarantee would evaporate without any red signal. *Remediation:* validate in `profiles.py` that blocking profiles selecting the `python_interop` area include all `COMPILED_EVIDENCE_SUITES`, or add a runner flag (set by the gate invocation) that fails when certification is not `complete`.

**Minor 3 — certification path consumes an unvalidated matrix; path-safety guards are bypassable on that path (schema validation / path safety).**
`runner.py:194-199` loads `declaration_capabilities.json` with a bare `json.loads` and feeds it straight to `build_compiled_certification`. The matrix-side guards — report path pinned to `target/verification/areas/python_interop/<suite>.latest.json`, `sifr_source` traversal/absolute-path rejection, marker prefix, duplicate-ID rejection (`runner/declaration_capabilities.py:195-240`) — run only inside the `self-test` suite subprocess, which is absent from targeted invocations such as the demo's five-suite run. On the certification path itself, `certification_ledger.py:120` does `repo_root / report_name` with no containment check, so a malformed matrix entry would cause the ledger to read an arbitrary file (or crash with a raw `KeyError` instead of a clean fail-closed diagnostic). The matrix is checked-in and reviewed, so this is defense-in-depth inside the repo trust boundary, not an exploit — but the ledger's advertised path safety currently depends on a validator that is not guaranteed to have run in the same invocation. *Remediation:* invoke the compiled-evidence shape validation (or full `load_and_validate_capabilities`) in `runner.py` before `build_compiled_certification`.

**Non-actionable notes** (recorded for awareness, no change requested): the ledger re-checks `marker in case["stdout"]` against a 4000-char stdout tail (`example_packages.py:607`, `certification_ledger.py:157`) — a verbose future example could false-*fail* certification (fail-closed, so safe); `failed` capability records carry a `failed_suites` key that `passing`/`not-selected` records lack (schema asymmetry in the emitted section); `_command_report_path` uses only the first `--report` occurrence (all current commands have exactly one).
