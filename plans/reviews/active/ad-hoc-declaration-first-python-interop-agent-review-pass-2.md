I have enough context — both prior review artifact files (`ad-hoc-declaration-first-python-interop-agent-review-pass-1.md` and `-pass-2.md`) are empty (0 lines), so this is a fresh independent pass. Findings below.

# Verdict

The declaration-first architecture is directionally sound and preserves every hard invariant of the implemented embedded interop (root env authority, explicit trust, `Result` at every boundary, non-send `Object`, `@blocking_io`, explicit zero-copy). The two-level model, signature-driven conversion, `close=drop`/`close=close`/`close=async_close` split, uv discovery convention, and "no matrix-only `supported`" gate are elegant and consistent with the Rust interop precedent. However, several load-bearing pieces are asserted without a specification: the sealed handle representation has no counterpart in current Sifr class syntax, bridge source embedding is asserted feasible without describing the CPython importer mechanism, kwargs/positional-only argument mapping is entirely absent, M5 promises decorator surfaces the grammar section explicitly defers, and the `allow-imports` removal lacks a migration story that leaves the existing `SIFR-PYTRUST-0002` diagnostic well-defined. Fix these, and the doc is ready to lock.

# Blocking Findings

1. **M5 activates a decorator surface the grammar section defers.** `internal_docs/python_interop_declaration_architecture.md:106-123` limits initial grammar to `@python`, `@python.opaque`, `@python.attr`, and `@python.item`, and defers "callback, context, async, and advanced-data metadata" to later bridge versions "only after their ownership contract is independently specified and verified." Yet M5 (`plans/issues/active/ad-hoc-declaration-first-python-interop.md:239-241`) says "Route existing callback, context-manager, buffer, Arrow, and DLPack contracts through typed declarations." With no decorators specified, M5 either becomes another design phase or ships without the routing it claims. Split M5 into an explicit protocol-decorator design phase (grammar, ownership contract, verification) and a subsequent implementation phase — do not treat protocol routing as "closeout" work.

2. **Package-local Python bridge embedding is asserted but not specified.** The declaration doc (`python_interop_declaration_architecture.md:211-219`) requires bridges to be embedded into the binary, registered under a reserved namespace, and shielded from `sys.path` shadowing, but does not say how. CPython imports go through `sys.path_hooks`/`sys.meta_path`; the only correct mechanism is a runtime-installed `MetaPathFinder` that loads bridge source from an embedded resource table before user `main`. The plan must nominate that mechanism, state where the finder lives in `sifr_runtime::python`, describe the reserved module namespace (`_sifr_bridges.<pkg>.<mod>`?), and specify how it composes with `[trust].python` — bridge modules themselves import trusted Python roots (e.g., `import biip`), and whether `importlib.import_module("dynamic_name")` inside a bridge is accepted, rejected, or requires explicit annotation is unaddressed. Without this, M3 acceptance ("Local bridge deployment does not depend on the source checkout or ambient `sys.path` ordering") cannot be verified.

3. **Kwargs/positional-only mapping is unspecified.** Compiler probing in `python_interop_declaration_architecture.md:312` claims to validate "inspectable positional-only and keyword-only compatibility," but the conversion table (`python_interop_declaration_architecture.md:133-146`) and the ownership section never describe how a Sifr declaration expresses kwargs at the call site. Most target Python APIs (`pandas.DataFrame(data, index=..., columns=...)`, `httpx.get(url, headers=...)`) rely on keyword arguments. Options: (a) Sifr keyword-only parameters after `*` become Python kwargs; (b) a `**kwargs` marker maps to a variadic Python kwargs container; (c) a closed record parameter marked `Kwargs[T]` expands as kwargs. The doc must pick one and reject the others; today record → `dict[str, T]` conflicts with "record is kwargs" without a marker.

4. **`allow-imports` removal has no migration or diagnostic story.** `python_interop_declaration_architecture.md:243-245` proposes "the long-term manifest model removes the redundant root `allow-imports` list." That is a breaking configuration change: `docs/python-interop.mdx:20-27` still documents it, `internal_docs/python_interop_architecture.md:127-128` binds `SIFR-PYTRUST-0002` to "allowed-but-untrusted imports," and current fixtures under `verification/areas/python_interop/` use it. The M4 task list (`plans/issues/active/ad-hoc-declaration-first-python-interop.md:203-205`) mentions the removal but not: what happens to `SIFR-PYTRUST-0002`, whether trust must now be root-scoped or can be library-declared, whether `python = ["*"]` local-control wildcard remains, and how the docs/tests migrate in the same PR. Root authority is preserved in principle (dependencies still cannot self-authorize), but the plan needs an explicit `SIFR-PYTRUST` recoding step and a doc/fixture migration list.

5. **Sealed compiler-owned Python handle has no counterpart in current Sifr class syntax.** The doc (`python_interop_declaration_architecture.md:157-160`) says the declaration layer "uses a sealed compiler-owned Python handle backed by an owned PyO3 reference." Today `stdlib/sifr/python_core.sifr` exposes `class Object(NonSend)` with public `_handle: int` and `_token: int` fields — consumers can inspect them. There is no `sealed`/`extern`/`opaque` class-kind that makes a Sifr class un-inspectable while still `NonSend` and destructible. M1 tasks list "compiler-owned sealed Python references with no-panic automatic decref" but do not describe the language mechanism. Either introduce the class-kind explicitly (`@python.opaque` classes and the internal handle it wraps compile to `extern class` with private fields) or state that opaque handles never surface as Sifr class values (they exist only inside the generated wrapper). M5 further requires the raw `sifr.python` API to be rebuilt "over the same sealed ownership model," which forces the migration of today's `Object` — that migration is currently unplanned.

# Actionable Refinements

1. **Nail down `@python(class_path)` factory vs. opaque linkage.** `python_interop_declaration_architecture.md:83-95` shows `@python(schwifty.BIC)` on a function returning `Result[Bic, PythonError]` where `Bic` is declared `@python.opaque(type=schwifty.BIC, ...)`. Overloading the same decorator target position with "call this Python callable" and "construct an opaque tied to this class" is compact but ambiguous when the factory is not the class itself (e.g., `@python(schwifty.BIC.from_string)` returning `Bic`). Spec the resolution rule: the factory target must be a Python callable whose observable return type matches (or is a subclass of) the `@python.opaque(type=...)` target — verified by probe where inspectable, treated as a runtime `PYCONV` failure when not.

2. **Reserve concrete first codes for each declaration diagnostic family** (as the Rust interop does — see `internal_docs/rust_interop_architecture.md:918-931`). Today the doc leaves `SIFR-PYIMP`, `SIFR-PYCALL`, `SIFR-PYCONV`, `SIFR-PYRES`, `SIFR-PYZC`, `SIFR-PYCB` as prefix reservations only. M0 should reserve `SIFR-PYIMP-0001` (unresolved static target), `SIFR-PYCALL-0001` (unsupported callable shape), `SIFR-PYCONV-0001` (unsupported conversion type), `SIFR-PYRES-0001` (invalid close/opaque policy), `SIFR-PYZC-0001` (invalid view/copy-fallback declaration), and `SIFR-PYCB-0001` (invalid callback lifetime).

3. **Clarify record vs. dict on the input side.** The conversion table conflates them: `dict[str, T]` and "closed record" both become "string-keyed Python mapping." Pick — records → Python object with attributes (via a small `SimpleNamespace`/`dataclass` builder) is often what target APIs want, and `dict[str, T]` remains a plain dict. Alternatively, mark records as strictly mapping-shaped and require adapters for object-shaped consumers. Whichever wins, state the reverse (Python → Sifr) rules for both explicitly.

4. **Address the milestone count.** The task brief says "the five milestones," but `plans/issues/active/ad-hoc-declaration-first-python-interop.md:78-267` lists six (M0–M5). Trivial, but if the plan intends "the five substantive milestones," say so explicitly and label M0 as documentation-only scaffold.

5. **State ellipsis-only body semantics for `@python(...)` declarations** the same way Rust interop does at `internal_docs/rust_interop_architecture.md:99-104`: "Ellipsis is public Python interop declaration syntax, not a general Sifr function body form."

6. **Give M2 an explicit "opaque handle closed on all exit paths" fixture requirement**, mirroring the way Rust's `PoisonOnPanic` guard is specified. The declaration doc says drop-on-error is a compiler responsibility, but M2 acceptance (`plans/issues/active/ad-hoc-declaration-first-python-interop.md:158-163`) does not require a fixture that exercises "opaque created, then declaration returns error mid-body, then confirm outstanding-reference count is zero." Add it.

7. **Native extension trust remains valid but flag its interaction with import inference.** Under M4, dependency-declared `requires-imports` implicitly contribute Python imports, but native-extension trust must remain root-only. Spell this out in the trust section — a dependency listing `requires-imports = ["numpy"]` must not implicitly claim `[trust].python-native = ["numpy"]`.

8. **Stub-assisted authoring section should reject not just `Any` but also `object` and `Callable[..., Any]`**, both of which are common Python stub escape hatches for otherwise-typed APIs (`python_interop_declaration_architecture.md:283-286`).

9. **`sifr python bind --check` in M4** should be defined as reading a per-package stub-source digest (SOABI, distribution version, stub file hash) stored in the generated declaration. Otherwise "drift detection" is not testable.

10. **Live-verification claim in M5**: the current architecture doc (`internal_docs/python_interop_architecture.md:83-92`) already runs testcontainers-backed live cases, but M5's acceptance criterion "Actual compiled Sifr service/callback execution for representative live cases" (`plans/issues/active/ad-hoc-declaration-first-python-interop.md:264-265`) does not name which live cases must switch from Python-client-only consumption to compiled-Sifr consumption. Enumerate them (e.g., Redis roundtrip, SQS send/receive, Kafka publish/consume) so M5 has a concrete exit gate.

# What Is Already Strong

- **Two-level user model** (`python_interop_declaration_architecture.md:50-61`): declaration-first for consumers, `sifr.python` as escape hatch. Matches Rust interop precedent and lets the raw API remain a valid, non-deprecated tool for exploration.
- **Signature-driven conversion contract** (`python_interop_declaration_architecture.md:75-78`): removing `returns=`/`copy=`/per-argument converter fields eliminates the drift-between-decorator-metadata-and-Sifr-types class of bug entirely. This is the single cleanest improvement over prior interop drafts.
- **Distinguishing `close=drop` from semantic `close`/`aclose`** (`python_interop_declaration_architecture.md:161-171`): correctly separates ordinary reference release (automatic) from correctness-critical resource cleanup (declared, ownership-checked). Buffer/Arrow/DLPack/callback contracts stay verbatim.
- **Import inference + explicit trust** preserves the authority split: dependencies request roots, the root authorizes execution and native extensions. Trust cannot be inferred from source.
- **Stub-assisted generation is non-authoritative** (`python_interop_declaration_architecture.md:265-268`): Python `.pyi` and `py.typed` are inputs, not proof — this is the correct posture for a language that C-extension callables routinely defeat.
- **No matrix-only "supported" claims** (`python_interop_declaration_architecture.md:337-347`): the compatibility matrix categories with executable positive+negative evidence are consistent with Rust interop's certification model.
- **Blocking-effect inference** (`python_interop_declaration_architecture.md:253-256`): `blocking_io` as declaration metadata, no hidden offload, no hidden event loop. Explicit `@python.async` deferred behind its own design.
- **Diagnostic family alignment**: `SIFR-PYIMP`, `SIFR-PYCALL`, `SIFR-PYCONV`, `SIFR-PYRES`, `SIFR-PYZC`, `SIFR-PYCB` were reserved during the implemented phase (see `internal_docs/python_interop_architecture.md:130`); the declaration doc activates the same families rather than inventing new prefixes.

# Recommended Final Contract

1. **Grammar/protocol split.** Freeze the initial grammar at `@python`, `@python.opaque`, `@python.attr`, `@python.item`. Split M5 into: **M5 (protocol decorator design)** — spec `@python.callback`, `@python.buffer`, `@python.arrow`, `@python.dlpack`, `@python.async` with ownership, lifetime, and diagnostic contracts, no implementation; and **M6 (implementation + closeout)** — implement + verify + migrate docs. Do not activate M5 tasks until M5's decorator contracts are individually accepted.

2. **Bridge embedding spec.** Add a subsection under "Package-Local Python Bridges" naming: (a) the reserved runtime `sifr_runtime::python::bridge_loader` responsible for installing a `MetaPathFinder` before `main`; (b) the reserved module namespace `_sifr_bridges.<pkg>.<module>` unable to be shadowed by `sys.path`; (c) bridge source lives in the generated binary's embedded resource table keyed by digest; (d) bridge imports are parsed at declaration-check time — dynamic `importlib` calls inside bridges are rejected unless the bridge itself carries an explicit `@trust_python_dynamic` annotation.

3. **Kwargs/positional rule.** Add "Argument Passing" subsection stating: Sifr parameters after `*` become Python keyword-only arguments; parameters before `/` become positional-only; a parameter typed `Kwargs[dict[str, T]]` (or spelled `**kwargs: T`, whichever the parser supports) becomes variadic kwargs; closed records remain positional dict-mapped and must not be silently expanded as kwargs. Reject conflicts (`Kwargs` combined with keyword-only) at declaration check.

4. **`allow-imports` deprecation plan.** In M0, mark `[python].allow-imports` deprecated in `docs/python-interop.mdx` and add a stale-draft check. In M4, remove parsing, redirect existing `SIFR-PYTRUST-0002` semantics to the "declared static import outside `[trust].python`" case (renumber or reuse), migrate every fixture under `verification/areas/python_interop/` in the same PR, and update `internal_docs/python_interop_architecture.md` accordingly. Do not ship M4 with dangling docs.

5. **Sealed handle mechanism.** Add "Handle Representation" subsection: declaration-layer opaque handles compile to a compiler-owned Rust `Handle<PyObject>` analogous to `sifr_runtime::interop::Handle<T>` (see `internal_docs/rust_interop_architecture.md:490-539`) with private state, no Sifr-side field access, and a `GeneratedGlueToken` capability. State the migration path for today's `stdlib/sifr/python_core.sifr::Object`: either (a) mark its `_handle`/`_token` fields private via a new `@python.raw_object` class-kind, or (b) reunify raw and declaration handles under a single Rust representation exposed differently at the Sifr surface. Whichever wins, the change belongs in M1 (not M5).

6. **First diagnostic codes reserved in M0.** Reserve `SIFR-PYIMP-0001`, `SIFR-PYCALL-0001`, `SIFR-PYCONV-0001`, `SIFR-PYRES-0001`, `SIFR-PYZC-0001`, `SIFR-PYCB-0001` with concrete meanings, matching the Rust interop precedent in `internal_docs/rust_interop_architecture.md:918-931`.

7. **Factory/opaque linkage rule.** Add: "When a `@python(target)` return type is an `@python.opaque(type=X)` Sifr class, `target` must be a Python callable whose statically-inspectable return is `X` or a subclass; when introspection is unavailable (C-extension factories), a runtime `SIFR-PYCONV` check enforces the same on the returned handle."

8. **M5/M6 live verification enumeration.** Enumerate the live testcontainers cases that must invoke compiled Sifr binaries (not merely Python-client + Sifr source): Redis round-trip, LocalStack SNS→SQS delivery, LocalStack SQS send/receive, Kafka publish/consume, Postgres query. Currently `internal_docs/python_interop_architecture.md:85-92` describes Python-client-consumption + `threadsafe_callback` handler; M6 must specify which of these switch to compiled Sifr invocation and which intentionally remain client-driven.

With those seven adjustments applied, the declaration-first architecture is ready to lock, and M1 can begin.
