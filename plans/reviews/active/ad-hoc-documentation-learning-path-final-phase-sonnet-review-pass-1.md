### Accuracy Issues — Follow-Up, Not Phase Blockers

#### 1. `docs/errors/SIFR-OWN-*.mdx` — `= own items` is not a valid Sifr expression

All 13 OWN-family error pages use this pattern as the erroneous example:

```python
items: list[int] = [1, 2]
taken = own items      # <- appears to use own as an expression operator
count = len(items)
```

The actual test fixtures (`use_after_move.sifr`, `use_after_move_list_assign.sifr`) show that moves happen via passing to an `own`-parameterized function or via plain assignment (`l2 = l1`). No test fixture uses `= own expr` as expression syntax, and `own` appears exclusively as a parameter prefix in all `.sifr` files in the codebase.

If `= own items` is a parse error rather than an ownership error, the erroneous code in these pages would fail at syntax analysis, not at ownership analysis — making the examples inaccurate. These pages were generated by template, so the fix is consistent across all 13 OWN pages. Worth a follow-up PR, not a blocker.

#### 2. `docs/errors/SIFR-IMPORT-0008.mdx` — Generic "Why It Happens" text

The text reads: "The module graph cannot be resolved safely. Use explicit `sifr.*` imports…" This is the generic IMPORT family boilerplate. For 0008 specifically the reason is a namespace policy rejection (CPython stdlib names are reserved), not a resolution failure. The downstream content (erroneous/fixed code, Details table) is accurate; only the "Why It Happens" paragraph misleads.

#### 3. `docs/errors/SIFR-PACKAGE-0703.mdx` — Example doesn't illustrate "pointer drift"

The erroneous TOML is a minimal manifest missing `[sifr]`. The error name — "Sifr-managed Cargo projection manifest pointer drift" — implies a drift between an existing Sifr-managed projection file and the canonical state, not a blank manifest. A developer encountering 0703 in a real project (where a manifest already exists) may not connect the example to their situation. Low priority but worth a targeted fix.
