## Blocking findings

### 1. HIGH — Declared union error channels are dropped from try-carrier discovery; `check` passes, native build fails
- **Files:** `crates/sifr_lowering/src/lower/statements/patterns_and_assignments.rs:384` (same pattern at `statement_dispatch.rs:423`); consumed by the new carrier selection in `crates/sifr_codegen/src/stmt_support_emitter/loops_try_finally.rs:219-231`.
- **Repro (verified):**
  ```python
  from sifr.csv import Error as CsvError
  from sifr.configparser import Error as CfgError
  def blow(flag: bool) -> Result[int, CsvError | CfgError]: ...
  # in main: try: v: int = blow(flag)  except CsvError ... except CfgError ...
  ```
  `sifr check` → "no errors found". `sifr build` → rustc E0277: the try closure's error type is `__SifrStdlib_sifr_x2ecsv_x2eError` (first handler only) while `blow(flag)?` propagates the `__SifrUnion_…` carrier, and no `From<union> for CsvError` exists. Same failure with builtin members (`ValueError | KeyError`).
- **Rationale:** when a fallible call's error is recorded into `try_block_error_types`, the guard `matches!(err_ty.resolve_alias(), Type::Class { .. })` silently discards `Type::Union` error channels. The try's `body_error_types` comes out empty, so `try_error_carrier()` falls back to the first handler's resolved type, and the new per-member conversion/dispatch machinery never engages. Direct raises work correctly (verified: same-basename `CsvError`/`CfgError` route to the correct handlers at runtime — the flagship M10 behavior is good); only channel-declared unions from called functions break. The milestone text claims "exact discriminated carrier with exhaustive nested-raise discovery, per-member conversions, identity-aware handler dispatch" — union channels (the exact shape of Python callback error unions) are the missing quadrant. On the pre-M10 installed release this program is rejected at `check` (SIFR-RESULT-0002), so the accept-then-fail behavior is at best left unresolved and at worst a parity regression relative to what shipped last.
- **Remediation:** at both recording sites, when `err_ty.resolve_alias()` is a `Type::Union`, insert each class member (or the resolved union itself) into `ctx.try_block_error_types`; `exact_try_error_carrier` already dedups by variant name and `consuming_value_upcast_for_ir` already handles Union→Union member mapping, so the existing codegen then produces the correct carrier and dispatch. Add a pass fixture mirroring the repro (union channel + per-member handlers) and a driver check/compile parity regression.

### 2. HIGH — Any user class named `PythonError` breaks the native build in programs with no Python interop; `check` passes
- **Files:** `crates/sifr_codegen/src/class_emitter.rs:358` and `:514`, `crates/sifr_codegen/src/class_method_emitter.rs:483` and `:603` (basename-keyed glue injection); feature detection at `crates/sifr_codegen/src/lib_modules_and_codegen.rs:747` scans only `::sifr_stdlib::python::`, never `::sifr_runtime::python::`.
- **Repro (verified):** `class PythonError(Error): message: str; code: int` plus a plain try/raise. `check` → "no errors found"; `build` → E0433 `could not find 'python' in 'sifr_runtime'` because the struct is emitted with a hidden `__sifr_python_error: Option<::sifr_runtime::python::PythonError>` field while the runtime's `python` feature is off. The exact five-field contract shape fails identically. The installed pre-M10 release compiles and runs both programs correctly (no hidden field injected).
- **Rationale:** M10's own passes deliberately replaced basename matching with the shared `is_python_error_contract()` predicate in lowering and in `rust_interop_error_mapping.rs`, but the class emitters still key on `class.name == "PythonError"` alone. This is precisely the "source-name collision resistance" class of defect this milestone exists to close, and it violates the check/compile diagnostic parity the milestone's own review passes established as the bar.
- **Remediation:** gate the `__sifr_python_error` injection (all four sites) on the module actually containing Python interop declarations (the emitter already tracks interop usage, e.g. the state consulted by `uses_async_python`/python-context emission), not on the class basename; classes named `PythonError` in non-interop modules must emit as ordinary error records. Independently, make `needs_python_runtime` detection also recognize `::sifr_runtime::python::` references so any emitted runtime-python glue always enables the matching crate feature. Add a native regression: non-interop program declaring `class PythonError` (both arbitrary-field and exact-contract shapes) builds and runs.

## Non-blocking findings (fix-forward suggestions)

3. **MEDIUM — catch-all `except Error` is matched by source spelling, not identity.** `crates/sifr_lowering/src/lower/statements/statement_dispatch.rs:574` (`et == "Error"` sets `has_catch_all`) and `crates/sifr_codegen/src/try_error_carrier.rs:34` (`error_type.as_deref() == Some("Error")`). After `from sifr.csv import Error`, a handler `except Error` (the csv class) is treated as the builtin catch-all: exhaustiveness checking is skipped and codegen attempts a wrong-target conversion. Today this fails closed at build (E0277; the pre-M10 release also fails this program), so no unsound runtime behavior — but it is the same basename-keying M10 eliminated elsewhere. Remediate by resolving the handler type and testing identity against the builtin `Error` declaration rather than the spelling.

4. **MEDIUM — basename "tail match" fallback survives in inheritance upcasts.** `crates/sifr_codegen/src/stmt_support_emitter/class_upcasts.rs:143-161`: when the exact ancestor identity is absent from the parent chain, a unique *basename* match selects the conversion target — this produced `Into::<__SifrStdlib_sifr_x2ecsv_x2eError>::into(ValueError)` in the finding-3 repro. It currently fails closed only because the `From` impl doesn't exist; if a same-basename `From` ever exists, this silently converts to the wrong nominal type. Since M10 canonicalizes parent chains to full identities, the tail-match fallback should be deleted (or restricted to identity-less legacy chains) with a unit test asserting no conversion is emitted on basename-only matches.

5. **LOW — two touched files sit at exactly the 900-line cap.** `crates/sifr_runtime/src/python.rs` and `crates/sifr_codegen/src/class_emitter.rs` are both at 900 lines (guardrail passes at `> 900` only). The next change to either forces a refactor; doing the responsibility split now (class emitter is an obvious candidate given finding 2 touches it) avoids a rushed one later.

## Areas reviewed with no actionable finding

- **Source-name escaping** (`source_names.rs`): the `__`/`_xHH` escape is decodable (prefix-unambiguous), hence injective; prefixes (`__SifrSource_`, `__SifrStdlib_`, `__SifrUnion_`, `__SifrUnionVariant_`) are pairwise non-confusable. Verified end-to-end: classes named `std`, `sifr_runtime`, and `__SifrIoTextFileHandle` coexist with `open()` file handles and run correctly.
- **Union identity keys** (`union_identity.rs`): length-prefixed structural keys are collision-free; nominal members key on emitted Rust identity so canonical/local views agree; conventions/params included for callables.
- **Exact carrier + handler dispatch**: verified same-basename `sifr.csv.Error` vs `sifr.configparser.Error` route to the correct handlers natively, both single-error and direct-raise union carrier cases. The "raise a subclass of a user error class" hazard I probed is closed by the language itself (SIFR-RESULT-0003 rejects it), so the exact-name dispatch cannot silently swallow via inheritance.
- **Render-time path absolutization** (`render_paths.rs`): token-boundary scan correctly skips strings, raw strings, byte strings, char literals, lifetimes, and nested block comments; already-absolute and qualified segments aren't double-rewritten; allocation only on rewrite (matches the perf claim); good test coverage in `render_helpers.rs`.
- **Stdlib sealing / DCE / direct runtime-dependency detection**: sealing excludes exact global identities; the canonical-name restore before item filtering keeps DCE sound; `needs_sifr_runtime` is now tracked separately from `needs_sifr_int` including absolute paths (with unit coverage), fixing the `sifr test` manifest gap.
- **HIR canonicalization** (`type_visit.rs` + `bootstrap.rs`): traversal covers all `HirExpr`/`HirStmt`/pattern type slots I cross-checked against `hir_nodes.rs` (exhaustive matches, class `parent_type`/`newtype_inner` handled at the bootstrap layer); in-place mutation with the empty-class fast path matches the perf rationale. The `class Error(Error)` parent-chain rewrite I suspected is benign in practice (verified csv `Error` raising/catching and inheriting work natively).
- **Carrier vs ordinary-union trait retention** (`union_type_helpers.rs`): dual registration keeps `PartialEq`/`Eq`/`Hash` on reused ordinary unions and minimal traits on carrier-only enums, per the pass-14 fix.
- **LSP RSS recalibration** (`budgets.json`): justified, not masking a regression — unmodified main already measured ~67.2 MiB against the stale 64 MiB ceiling; the branch adds ~1.7 MiB (+2.5%), and the new 80 MiB ceiling stays inside the documented baseline+32 MiB policy.
- **Vendor/ignore changes**: tracking vendored `Cargo.lock`/`build/`/`.vscode` files is required for checksum-complete clean checkouts; correct.
- **Runtime bridge** (`declaration_object_bridge.rs`): no panics; handle-state errors map to `PythonError`.
- **Pre-existing, out of scope** (identical on the pre-M10 installed release): `raise` in a non-`Result` function and `with open(...)` outside `try` pass `check` but fail the Rust build. Worth a separate issue; not introduced or claimed-fixed by M10.
