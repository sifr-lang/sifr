# M8b TLS Native-Boundary Migration — Round 1 Review

## Summary of what I checked

- Every compiler-owned TLS surface is removed:
  - `crates/sifr_codegen/src/intrinsics/registry/tls.rs`, `crates/sifr_codegen/src/preamble/tls_runtime.rs`, and `crates/sifr_retained_intrinsics/src/tls.rs` are all deleted, and all their `mod`/`use`/dispatch entries are gone from `intrinsics/registry.rs`, `intrinsics/registry/requirements.rs`, `preamble.rs`, `lib_modules_and_codegen.rs`, and `retained_intrinsics/lib.rs`.
  - `needs_tls_runtime` gating in `lib_modules_and_codegen.rs` (both preamble-scan and `intrinsic_functions` starts-with `tls_`) is removed; nothing else emits `__sifr_tls_*` names. Confirmed by the reported `rg "__sifr_tls_"` emit check.
  - `starts_with("tls_")` in registry lowering and requirements is gone; the only remaining TLS mention in `sifr_codegen` is the `TlsError` alias in `rust_interop_error_mapping.rs`, which is exactly the shape M8a established.
- All 25 exact intrinsic names from the old retained manifest surface (client/server config x5, close x2, connect/accept x2, stream ops x9, split x1, alpn/version x2, read-half x2, write-half x5) appear once in `stdlib/_sifr/tls.sifr` as `@rust(sifr_stdlib.tls.…)` declarations, once as `pub fn` wrappers in `crates/sifr_stdlib/src/tls.rs`, and once in `check_stdlib_migration_closure.py`'s `RETIRED_INTRINSICS`.
- Signatures match end-to-end:
  - `bytes` → `&[u8]`, `list[bytes]` → `&[Vec<u8>]`, `bytes | None` → `Option<Vec<u8>>`, `str | None` → `Option<String>`, `list[int]` → `Vec<SifrIntBridge>`, `Result[..., TlsError]` → `Result<..., String>` (mapped via `is_message_error_alias` = `TlsError`, already present from M8a).
  - Async ops all return `TlsFuture<T> = Pin<Box<dyn Future<Output=Result<T, String>> + Send>>`, matching M8a's `NetFuture<T>` shape.
  - `SifrIntBridge` bridging goes through `bridge_i64` inside the async block for `tls_stream_write`, `_write_all`, `_flush`, `_close_notify`, `_close`, and both write-half write ops — so the `i64` conversion is polled inside the returned future, not eagerly at call time. Same shape as `net`.
- Cargo dependency inference is complete:
  - `harness_model.rs:418` detects `sifr_stdlib::tls::`, `fixture_dependency_paths.rs:135` adds the `tls` feature, `fixture_cargo_toml.rs:333-334` keeps the sifr_stdlib module dependency, and `needs_sifr_runtime_module_dependency` (line 269) still lists `sifr.tls`/`_sifr.tls` (substrate still lives in `sifr_runtime::tls`). New unit test at `network_http_dependency_rules_tests.rs:80` asserts sifr_stdlib+"tls"+sifr_runtime.
  - `sifr_stdlib_manifest::features::…` chain — `runtime_features::needs_sifr_runtime_tls`, `generated_stdlib_features::features_for_module`, `features::runtime_features_for` — all already handled `sifr.tls`/`_sifr.tls` from M8a; no gap.
  - `sifr_stdlib`'s `tls` feature (Cargo.toml:65-72) enables `dep:rustls`, `dep:rustls-pemfile`, `dep:rustls-platform-verifier`, `dep:tokio-rustls`, and `net` (which pulls `sifr_runtime` + `sifr_runtime/net`), plus `sifr_runtime/tls`. That matches the substrate needs.
  - `sifr_driver::build::materialize::sysroot_trusted_native_links` still trusts `aws_lc_0_41_0_crypto` when TLS is selected via any sifr_stdlib/sifr_runtime dependency carrying `tls`/`http` features. No manifest-level `retained_direct_dependency_packages` needed anymore.
- Public API of `sifr.tls`:
  - Classes `TlsClientConfig`, `TlsServerConfig`, `TlsStream`, `TlsReadHalf`, `TlsWriteHalf` and factory functions `client_config_platform`, `client_config_default`, `client_config_with_roots`, `client_config_from_ca_pem`, `client_config_with_roots_and_client_auth`, `client_config_with_client_auth`, `server_config`, `server_config_from_pem`, `server_config_require_client_auth`, `connect_tls`, `accept_tls` are all preserved with the same argument shapes.
  - `TlsError` moved from being declared in `sifr/tls.sifr` to being declared in `_sifr/tls.sifr` and re-imported at the top of `sifr/tls.sifr`, so `from sifr.tls import TlsError` continues to work. Mirrors how M8a moved `NetError`.
  - `TlsStream.split()` signature widened from `-> tuple[TlsReadHalf, TlsWriteHalf]` to `-> Result[tuple[TlsReadHalf, TlsWriteHalf], TlsError]`. This is intentional (paired with runtime returning `Result<(i64,i64), String>`) and fixes the old phantom-handle-on-missing-stream behavior. Existing fixture `network_http_tls_loopback_split.sifr` already threads the split through a `try/except Error` block, so the auto-propagation compiles.
- Runtime lifecycle: `tls_stream_split` new failure path is exercised by the added test `tls_stream_split_rejects_unknown_handle`. HTTP consumer path (`consume_stream_for_http`) is untouched.
- Manifest: `_sifr.tls` moved `retained` → `closing`, `certification_rows` moved to `opaque_resource_core` / `async_runtime_core` (matching M6b/M3a splits), `registry_files`/`preamble_files`/`retained_direct_dependency_packages`/`direct_runtime_roots`/`exact_intrinsics` all removed, `removal_criteria` reworded to the closing-row form. Mirrors M8a `_sifr.net`.

## 1. Blocking findings

None. The diff cleanly removes every compiler-owned TLS surface, the sifr_stdlib wrappers cover all declared functions with matching signatures, dependency inference is complete, and the runtime split behavior change is paired with a targeted regression test. Local validation evidence covers stdlib unit tests, runtime tests, e2e demos, generated Cargo tests, retained-intrinsic tests, closure guard, and the emit substring check.

## 2. Non-blocking suggestions

- **Stale architecture doc row.** `internal_docs/sifr_sysroot_and_stdlib_architecture.md:130` still lists `preamble/tls_runtime.rs` in the "Current call sites" column even though that file is now deleted. The neighbouring `net_runtime.rs` row (line 129) is already stale from M8a, so this is not a M8b regression, but the milestone closeout is the natural moment to update both rows to reflect that these families now flow through `stdlib/_sifr/*.sifr` → `sifr_stdlib::{net,tls}` → `sifr_runtime::{net,tls}`.
- **Wasted handles in the runtime split error path.** `crates/sifr_runtime/src/tls.rs:422-423` allocates `read_handle` and `write_handle` via `next_handle_infallible()` before checking whether the source stream exists, so on the new `Err` branch two handle IDs are burned. This matches the pre-existing `tcp_stream_split` shape (`crates/sifr_runtime/src/net.rs:378-381`), so it is consistent — but a `let Some(stream) = …` guard first, then allocation, would tighten both. Not blocking; consider folding into an M8 closeout cleanup or M13.
- **Test coverage gap: split failure from Sifr.** Runtime-level split-rejection is covered by `tls_stream_split_rejects_unknown_handle`, and the loopback fixture covers the happy path. There is no e2e fixture that drives the new `Result[..., TlsError]` failure path from a `TlsStream.split()` call (e.g. calling split twice). M8a shipped without an analogous net fixture, so parity is preserved — but a small negative fixture would raise confidence that the propagation of the runtime `Err` through `sifr_stdlib::tls::tls_stream_split` → the direct-error mapping → user-visible `TlsError` really compiles as expected. Non-blocking.
- **User-facing signature change in `TlsStream.split`.** Not a defect — the old `tuple[...]` return was silently unsafe — but worth calling out in the milestone evidence entry so future readers see that the public shape changed alongside the runtime fix.

## 3. Verdict

**Satisfied.** The M8b diff completes the retained → closing transition for `_sifr.tls`, removes every compiler-owned TLS registry/preamble/fallback surface, wires sifr_stdlib::tls as the sole implementation path with signatures that match the declarations, updates dependency inference and the migration closure guard consistently with M8a's shape, and adds the runtime regression test that the split-fallibility change requires. No blocking correctness issues found.
