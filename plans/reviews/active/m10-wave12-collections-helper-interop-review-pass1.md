## Residual risks

- Any consumer that imports `new_set`/`defaultdict_*` from `_sifr.collections` (not through `sifr.collections`) is now broken at codegen — deliberate for the private surface, but if any first-party test/tool did this it would fail. The retired-name assertions in `registry_core_tests.rs` cover the codegen side; the underscore-vs-bare split in `stdlib/_sifr/collections.sifr` covers the source side.
- `sifr.collections`-only Cargo generation drops direct `serde`/`serde_json` deps entirely, but Counter still uses the `SerdeJson` codegen requirement (retained intentionally). Programs mixing Counter with public set helpers will still pull serde as required-features, which the `features_tests.rs` assertions reflect (`["collections", "json", "random"]` plus `serde_json` + `serde` raw deps). This is consistent with the retained-glue policy but is worth spot-checking in a program that only uses Counter (no sets/defaultdict) — it should still enable `collections` feature and pull serde as a required-crate, not as a stdlib module dep, once you audit the wave.
- `_defaultdict_*` still uses the legacy serialized-JSON-in-a-string format on the adapter side. The plan explicitly retains this as helper-leaf migration only; typed defaultdict language glue is deliberately left for later. No action here, but it means the private adapter's `dd: str` contract is load-bearing on serde_json availability inside `sifr_stdlib`, which is what `collections = ["json"]` in Cargo.toml enforces. Good.
