## Blocking findings

### 1. HIGH — Union error channels containing *builtin* errors still pass `check` and fail the native build (pass-2 finding 1 incompletely remediated)
- **Repro (verified with the working-tree compiler):** `def fail_with(flag: bool) -> Result[int, ValueError | KeyError]: ...` with per-member handlers → `sifr check`: "no errors found"; `sifr run`: SIFR-BUILD-0005 with rustc E0369/E0277 — the carrier enum derives `PartialEq, Eq, Hash` while the emitted `ValueError`/`KeyError` structs implement none of them. A mixed channel `CsvError | ValueError` fails identically, so any union with at least one builtin member is broken.
- **Root cause:** `generate_enum_definitions` (`crates/sifr_codegen/src/union_type_helpers.rs:209-217`) gates the equality/hash derives on the type-shape predicate `Type::supports_structural_equality` (`crates/sifr_type_system/src/types/type_queries.rs:158`), which returns true for builtin error classes (plain `message: str` fields), while the builtin error *structs* are emitted without those derives. The channel union in the function signature is also registered as an ordinary-value union (`register_union_type_with_usage`, `union_type_helpers.rs:119-121`), forcing full traits even though its only use is as an error carrier.
- **Why blocking:** pass-2 finding 1's repro explicitly recorded "Same failure with builtin members (`ValueError | KeyError`)". The remediation and its fixture cover only the stdlib-class quadrant. The pre-M10 installed release rejects this program at `check`, so the accept-then-fail behavior ships with this PR.
- **Remediation direction:** either make the enum derive gate consult the same emitted-derive capability the class emitters use (so enum derives never exceed member struct derives), or treat signature error-channel position as carrier-only usage; add a fixture mirroring `try_union_error_channel` with builtin and mixed members.

### 2. HIGH — Canonical `_sifr.python.PythonError` is emitted under the source-spellable name `PythonError`, colliding with any user class of that name; `check` passes, build fails
- **Repro (verified, package mode):** `from sifr.python import PythonError as PyErr` plus `class PythonError(Error): message: str; code: int` (no `@python` declaration needed) → `check` passes; build fails with E0428 "`PythonError` is defined multiple times", plus E0119/E0560/E0609 fallout. Same failure when the local class has the exact contract shape.
- **Root cause:** `_sifr.python.PythonError` is on the `GLOBAL_RUST_NOMINAL_IDENTITIES` exemption list (`crates/sifr_type_system/src/types/source_names.rs:36`), so `class_rust_name` maps the canonical identity to the bare identifier `PythonError` (asserted at `source_names.rs:142-143`) instead of a compiler-owned `__Sifr*` name. A user source class named `PythonError` legitimately owns that flat identifier, so the two emissions collide whenever `sifr.python` is imported (directly or via alias) alongside the user class.
- **Why blocking:** this is an identity collision across an import alias — the milestone's core remit — and a check/build parity break of exactly the class pass-2 established as blocking (its findings 1 and 2 also failed closed at rustc). The scenario is two lines of ordinary source. Not pre-existing: the pre-M10 release does not support declaration-first interop at all.
- **Remediation direction:** either detect the collision at `check` (reject or require the user class to be renamed when the canonical identity is in scope), or escape one side (e.g., emit the runtime-shared struct under a compiler-owned alias and keep `PythonError` for the user). The exemption comment says the prelude owns the name; the checker must then enforce that ownership.
