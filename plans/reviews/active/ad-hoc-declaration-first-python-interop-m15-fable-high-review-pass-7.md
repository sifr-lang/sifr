## New findings

### MINOR 1 — The didClose owner handoff silently fails while an unanalyzable document is open, contradicting the remediation's own documented guarantee (empirically reproduced)

`text_document_did_close` (`crates/sifr_lsp/src/notifications/mod.rs:174-200`) clears the closed document and calls `DiagnosticsController::publish_all`, which schedules jobs for every open document in sorted-URI order and drains them in `flush_ready` (`crates/sifr_lsp/src/diagnostics.rs:28-56, 58-107`). `flush_ready` propagates the first `document_diagnostics` error with `?` (`:78`), aborting the rest of the queue — and an analysis-excluded open document always errors there (`document_diagnostics` hits the `with_document_analysis` `?` at `diagnostics.rs:136-145`, its load diagnostics being empty per `analysis_workspace.rs:348-355`). So in exactly the scenario class this remediation addresses — a loader-excluded document open in the package — closing the current owner clears its diagnostics, then aborts before republishing the package diagnostic on the next eligible document whenever the excluded document's URI sorts ahead of it in the queue. Reproduced against HEAD with a scratch test through the real handler: the owner's clear was published, the handler returned `Err("analysis is unavailable for …/a/aux.sifr")`, and no publication carrying `SIFR-PYZC-0001` reached `z.sifr`. The server surfaces notification-handler errors as trace-only (`crates/sifr_lsp/src/server.rs:88-102`), so the failure is invisible: a package error `sifr check` reports is displayed **nowhere** until the next diagnostic-triggering notification flushes the sibling's still-queued job. This directly falsifies the unconditional sentence this remediation added to the architecture doc — "Closing the current owner clears it and republishes the package diagnostic on the next eligible document" (`internal_docs/python_interop_declaration_architecture.md:620-622`) — and the ledger's "closing the current owner recomputes and republishes the remaining owner, with a dedicated regression" (`plans/issues/active/ad-hoc-declaration-first-python-interop.md:2216-2218`); the dedicated regression's fixture contains no excluded document, and the new excluded-document regression never drives the close path, so the combination is untested.

Graded minor, not major: the abort-on-first-error drain and the watcher-batch `publish_all` are pre-existing (unchanged vs origin/main — an excluded open document already blocked watcher-triggered republication of later-sorting documents before M15); the sibling's queued job survives the abort, so any subsequent lifecycle or watcher notification heals the gap — unlike the pass-6 major, which no event except closing the excluded document could heal; and it is the same transient ownership-transition family passes 4–5 graded minor. What makes it more than a nit: it is silent, anti-conservative, triggered by the same mundane shape as the pass-6 major (any non-entrypoint `src/` module open), and it breaks the one transition the milestone specifically hardened and documented as guaranteed. Remediation direction: isolate per-job failures in `flush_ready` (trace-and-continue instead of `?`), or skip unpublishable documents in `publish_all`'s scheduling using the very `can_analyze_document` predicate this remediation added; add a combined excluded-document-plus-didClose regression; and either fix or truthfully condition the architecture-doc sentence and ledger clause.

### Nits (no individual remediation demanded; ledger at next touch)

- The project arm of `can_analyze_document` carries a `host.is_some()` conjunct that is redundant under the `host == None ⇒ files_by_uri empty` invariant; harmless defensiveness, but the invariant it silently depends on for exact `with_document` agreement is undocumented at either site.
- The excluded-document regression asserts the owner's diagnostics directly via `document_diagnostics` rather than through a publication drain, which is why the MINOR 1 delivery-path interaction stayed invisible to it.
