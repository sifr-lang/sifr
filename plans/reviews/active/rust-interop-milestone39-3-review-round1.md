## Review: M39.3 Rust Interop — Package-Local and Shared Bridge Modules

### Blocking findings

**B1. Generated bridge module path collides `module_name=Some("main")` with module-less binaries.** `generated_bridge_module_path` in `crates/sifr_driver/src/build/rust_interop_cargo_inputs.rs:61-68` emits `__sifr_bridge::main` for `None` and `__sifr_bridge::main` for `Some("main")`. The cache-fragment serializer in `crates/sifr_codegen/src/rust_interop_plan.rs:420-426` reinforces the collision by using `"<single>"` only for the textual module label but joining `rust_module_path` via `::`, which is identical for both inputs. Two declarations with different `module_name` therefore alias onto the same Rust namespace and have the same cache fingerprint segment — and the architecture's `crate::__sifr_bridge::<sifr_module_path>::<Name>Bridge` rule then breaks bijectivity. A Sifr package with a `main.sifr` module plus a `main` binary entry would silently emit colliding generated bridge types. Either use a distinct sentinel for the binary entry (e.g. `__sifr_bridge::<bin>` reserved root, or carry an explicit "no module" tag in the path) or reject `module_name == Some("main")` at plan time.

**B2. `is_rust_identifier` accepts Rust keywords for user bridge files.** `crates/sifr_package/src/projection_bridge.rs:373-380` validates `[A-Za-z_][A-Za-z0-9_]*`. A user-authored `src/bridges/match.rs` (or `crate.rs`, `self.rs`, `super.rs`, `if.rs`, `enum.rs`, etc.) passes the identifier check, gets added to the managed `src/bridges/mod.rs` as `pub mod match;`, and produces a Cargo build error instead of a stable `SIFR-RUST-CONFIG-*` diagnostic at the projection layer. This violates the "stable Sifr diagnostic, not Cargo noise" contract in the architecture's projection conflict rules and is user-triggerable. Extend the identifier check (or follow up with an explicit Rust-keyword reject) before adding the module to the generated `mod.rs`. A targeted unit test in `package_projection_tests.rs` is missing.

**B3. Shared-bridge-crate boundary scanner uses an unanchored substring match.** `first_generated_bridge_import` in `crates/sifr_driver/src/build/rust_interop_cargo_inputs.rs:88` returns the first `.rs` file whose contents contain the literal substring `"__sifr_bridge"`. That fires on comments (`// see __sifr_bridge for…`), unrelated identifiers (`fn __sifr_bridge_compat()`, `mod __sifr_bridge_v2`), doc tests, and string literals. A correct-by-construction shared bridge crate will be rejected with `SIFR-RUST-RESOLVE-0001`. The corresponding test in `rust_interop_tests.rs:170-204` only proves the positive direction; there is no negative test that a benign comment is *not* rejected. Tighten the check to look for `crate::__sifr_bridge` or `__sifr_bridge::` token sequences after stripping comments (the same `strip_rust_comments_and_whitespace` used by the pure-marker validator already exists in `sifr_package::source::layout`).

**B4. M39.3-required verification fixtures are still empty `.gitkeep` stubs.** The phase doc's M39.3 scope explicitly enumerates "fixtures for local bridge, shared bridge crate, generated projection ownership, bridge-version mismatch, plain cargo-check limitations, package archive validation, and bridge module conflict behavior", and `verification/areas/rust_interop/data/rust_interop_fixture_matrix.json` still lists them as `status: planned`. The on-disk dirs `verification/areas/rust_interop/fixtures/{local_bridge_blake3, shared_bridge_crate, bridge_version_mismatch, same_workspace_crate}` contain only `.gitkeep` files. Unit tests inside `crates/sifr_package/src/package_*_tests.rs` and `crates/sifr_driver/src/build/rust_interop_tests.rs` cover the projection logic, but the architecture's verification-area is normative for milestone closure and the fixture matrix is part of the cache-keyed contract. Treat as blocking for M39.3 closure unless the team has consciously deferred fixture authoring to a later checkpoint and recorded that in the phase file.

### Non-blocking concerns

**N1. Pure-marker → managed-marker upgrade is broken.** `init_package` writes `src/lib.rs` with `canonical_pure_marker_source()` (the `// Pure Sifr package marker…` line). When the user then adds `[rust] bridges = [...]`, `projection_bridge::diagnostics` flags `src/lib.rs` as "user-authored" (`projection_bridge.rs:200-205`) because the marker line is not `MANAGED_BEGIN`. `sifr repair` then refuses to overwrite it (`projection_bridge.rs:223-231`). Users are stuck unless they manually delete `src/lib.rs`. Add a recognized "owned by Sifr, safe to upgrade" predicate that includes the canonical pure marker, or have repair explicitly upgrade the pure marker to the managed bridge header.

**N2. `is_managed` is a bare substring check on `MANAGED_BEGIN`.** `projection_bridge.rs:369-371`. A user can accidentally (or maliciously) annotate their own file with that exact line and disable the projection-ownership guard. Combine with N1 — managed-file detection should be a stricter form (header pin to first nonblank line; or matched `BEGIN`/`END` envelope; or a checksum stamp).

**N3. `src/__sifr_bridge.rs` (file form) reserved diagnostic fires but `repair` still writes `src/__sifr_bridge/mod.rs` alongside it.** `projection_bridge::repair` at `projection_bridge.rs:122-129` doesn't short-circuit when the reserved single-file form already exists. The on-disk result is two competing module roots; rustc will error and the user gets two layers of confusion. Skip the dir-form write while the file-form conflict exists.

**N4. Diagnostic family fit drifts from the architecture.** Bridge projection conflicts reuse `PACKAGE_PROJECTION_MANIFEST_POINTER_DRIFT` / `_INCLUDE_DRIFT` (e.g. `projection_bridge.rs:382-388`). The architecture reserves `SIFR-RUST-CONFIG-*` for "manifest conflict, missing bridge directory". Unsupported `[rust].bridge-version` is reported as `SIFR-RUST-CARGO-0001` in `crates/sifr_driver/src/build/rust_interop.rs:312-336` even though it's a `sifr.toml` manifest-schema concern, not a Cargo metadata violation. Realign at least the M39.3-specific cases (bridge-version, bridge projection conflicts) to `SIFR-RUST-CONFIG-*` so the diagnostic-family inventory from M39.0 stays accurate.

**N5. `validate_backend_generated_bridge_imports` recursively scans the entire backend `src/` tree on every interop resolve, with no caching.** Pre-existing pattern but it ships in M39.3's diff. Combine the loose substring with no caching and you get an O(files × interop calls) cost for shared bridges. Hoist the result per backend into the resolver. Same applies to `collect_unsafe_bridge_files` (`rust_interop.rs:690-709`), which itself uses `source.contains("unsafe")` — also too loose, will match `unsafe_internal` identifiers and `// unsafe historically` comments.

**N6. Direct-only Rust-backed packages don't get any managed `src/lib.rs` or generated-bridge namespace projection.** `projection_bridge::diagnostics` and `repair` early-return when `has_local_bridges == false` (`projection_bridge.rs:45-47, 107-112`), but the architecture says "Rust-backed packages receive managed module declarations for bridges and generated bridge types". A `direct-crate-bindings = true` package with no local bridges silently keeps the pure marker, so `crate::__sifr_bridge::<module>::<Name>Bridge` won't resolve when M39.4 starts generating bridge types. Probably needs to land as a follow-on with M39.4, but worth recording explicitly.

**N7. `bridge_root_module_name` requires exactly two path components.** Bridge roots like `src/lib/bridges` or `src/internal/bridges` are silently rejected as projection conflicts. The architecture doesn't forbid deeper roots; if this restriction is intentional, document it and add a negative test.

**N8. `render_bridge_mod_rs` only declares direct-child `.rs` files.** Subdirectory bridge modules (`src/bridges/sub/mod.rs`) are not represented in the managed `mod.rs`. Acceptable for v1, but architecturally undocumented.

**N9. Tests use `std::process::id()` based temp roots in `rust_interop_tests.rs:686-692` and `SystemTime::now().as_nanos()` in `package_projection_tests.rs` / `package_rust_bridge_archive_tests.rs`.** Two tests in `rust_interop_tests.rs` with the same `name` from the same process collide. Use the nonce-style helper used by the package tests, or include the test fn name.

**N10. Cache-key fragment determinism test does not cover the new `generated_bridge_modules` channel.** `rust_interop_tests.rs:82-118` asserts `rust.probes=1` is present; `rust_interop_tests.rs:284-309` only checks `cache_key_fragment` equality. Add a test that changing `module_name` (and therefore the generated bridge path) does change the fragment.

**N11. `RustGeneratedBridgeModule.module_name == Some("<single>")` is the same after serialization as `None`.** Cache fragment writer at `rust_interop_plan.rs:420-426` uses the literal string `"<single>"` to render `None`. A real Sifr module named `<single>` would collide. Cheap defensiveness: prefix-encode the optional (e.g. `generated_bridge=opt:<name>` vs `generated_bridge=bin:` rather than a magic sentinel).

**N12. `validate_bridge_version` rejects only `bridge_version != Some(1)` but does not reject `bridge_version = None` independently from "missing".** That's actually fine, but no test asserts the `None` path explicitly — only `Some(2)` is exercised (`rust_interop_tests.rs:148-167`). Add a missing-version negative case.

**N13. `package_rust_bridge_archive_tests.rs` uses `production_schema: true`** but doesn't verify the inverse (development schema) behaves the same way. Minor.

### Cargo include / archive behavior — looks correct

- `cargo_include_entries` adds `src/**/*.rs` only when `has_local_bridges` is true (`projection_bridge.rs:32-34`). ✓
- `required_archive_entries` includes Cargo.toml + the managed projection files + discovered user bridge files for Rust-backed local-bridge packages (`projection_bridge.rs:168-190`). ✓
- `repair_projection` re-renders Cargo.toml using `render_cargo_toml_for_manifest`, which threads the manifest through `cargo_include_entries` (`projection.rs:101-108, 253-258`). ✓
- Archive validation diagnoses missing `src/bridges/mod.rs` correctly (`package_rust_bridge_archive_tests.rs:36-59`). ✓

### Cache-input wiring — looks correct in scope

`generated_bridge_modules` now feeds `cache_key_fragment` via `BTreeSet<RustGeneratedBridgeModule>` → sorted `Vec` (`rust_interop.rs:119-122`), so output is deterministic. The existing cargo-input digests (lock/profile/trust/build-env) carry over unchanged. The only cache holes I found are listed in B1, N10, N11.

### Is this enough for M39.3?

Not yet, on this review. Definition-of-done items that are satisfied: user bridge files are owned by users, projection conflicts emit stable diagnostics (modulo N4's family-fit nit), generated `crate::__sifr_bridge` is reserved in both file and dir forms, and bridge-version mismatch is rejected before Cargo executes. Items still open: the bijective mangling claim (B1), the keyword-safe user-bridge filename guarantee (B2), the shared-bridge-crate boundary check's correctness (B3), and the verification-area fixture bodies (B4). M39.3 is also conspicuously missing the same-workspace-crate behavior fixture/test the phase doc lists (the unit tests cover direct Cargo deps and bridge roots but not the `[dependencies] backend = { path = "backend" }` shape end-to-end). I'd recommend one more pass before sign-off.
