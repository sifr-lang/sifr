## Blocking findings

### 1. M3 breaks `stdlib/sifr/hashlib.sifr` (bytes_to_hex_strict has a live caller)
- **Evidence.** `stdlib/sifr/hashlib.sifr:2` `from _sifr.bytes import ..., bytes_to_hex_strict` and `:182` `return bytes_to_hex_strict(_hash_bytes(algorithm, data))`. The signature comes from the fallback (`crates/sifr_retained_intrinsics/src/collections_bytes_time.rs:254-260`) and the Rust body only exists as a private `fn` in `crates/sifr_stdlib/src/bytes.rs:17` (`fn`, not `pub`).
- **What M3 says.** "Make codegen dispatch exhaustive over `CompilerIntrinsicId`. Remove the attempt to lower every ordinary function call as an intrinsic." The target 17 typed IDs do not include `bytes_to_hex_strict`; its migration is scheduled for M4.
- **Failure scenario.** Land M3 as written and every hashlib caller ceases to compile: the call resolves against the fallback signature but generated Rust emits an unresolved `bytes_to_hex_strict(...)` call because sifr_stdlib does not expose it. Same problem exists for any residual raw-name intrinsic with a live source caller.
- **Recommendation.** Either (a) fold the `bytes_to_hex_strict` → `sifr_stdlib::bytes` + `_sifr.bytes` declaration migration into M3 acceptance (the pub adapter is a two-line change), or (b) reorder to M4 → M3, with M4 restricted to "residue that does not require typed intrinsic identity" (Counter arms, JSON defaultdict, `bytes_to_hex_strict` migration).

### 2. Fallback resolution has a THIRD call site that M5 does not enumerate
- **Evidence.** M5 says delete `re_export_intrinsic_fallbacks` (in `crates/sifr_driver/src/stdlib/bootstrap.rs:599`) and `resolve_retained_fallback` (in `crates/sifr_lowering/src/lower/private_stdlib_imports.rs:218`). But `crates/sifr_lowering/src/lower/mod_impl.rs:292-315` independently calls `sifr_retained_intrinsics::get_intrinsic_module(&module_name)` when `resolve_compiled_private_imports` returns `false` (module absent from externals). This third path resolves imports directly from the fallback module.
- **Failure scenario.** Landing M5 as written leaves `mod_impl.rs:292-315` behind. A `from _sifr.<placeholder>` import that isn't present in externals still resolves through the retained-intrinsics crate, contradicting the "one authoritative declaration source" invariant.
- **Recommendation.** Explicitly list all three call sites in M5, and add an M5 acceptance sub-item: `rg 'sifr_retained_intrinsics' crates/` returns zero matches (currently 4 live production references + workspace deps).

### 3. Retained direct dependency packages will list dead crates after M1/M4
- **Evidence.** `internal_docs/stdlib_retained_compiler_intrinsics.toml:135-155` `generated-feature-planning-glue.retained_direct_dependency_packages` includes `metrics`, `tracing`, `serde`, `serde_json`. Only `runtime_emit_diagnostic` uses `Metrics`/`Tracing` (`crates/sifr_codegen/src/intrinsics/registry/requirements.rs:9`) and only Counter uses `SerdeJson` (`crates/sifr_codegen/src/intrinsics/registry.rs:37-68`). No other codegen caller of these features exists.
- **Failure scenario.** After M1 and M4, four packages remain frozen in the retained list with no live caller; the manifest-vs-code guard is required to catch it, but M1 and M4 tasks do not require pruning the retained packages, and M6's "compare source declarations, typed HIR IDs, dispatch implementations, manifest entries, and owned files exactly" is vague on this specific list.
- **Recommendation.** Add explicit tasks: M1 removes `metrics` and `tracing` from `retained_direct_dependency_packages`; M4 removes `serde` and `serde_json`. M6 acceptance must add "no retained direct dependency package exists without a corresponding typed-intrinsic feature requirement".

### 4. M3 does not cover the lowering entry points for method calls
- **Evidence.** The current lowering that produces the raw string `"bytes_from_hex"` lives in `crates/sifr_lowering/src/lower/builtin_calls/bytes_len_range.rs:50-54` (and neighboring `from_ints`/sized ctors). Encoding uses `crates/sifr_codegen/src/intrinsics/registry.rs:69-84` behind synthesized names produced during lowering of `.encode()`/`.decode()`. M3 tasks say "Convert open and primitive bytes/encoding lowering to emit typed intrinsic HIR calls directly" but do not enumerate these lowering call sites, whose count and file locations matter for scoping.
- **Failure scenario.** A partial M3 that adds `CompilerIntrinsicId` to HIR but only rewires codegen (not lowering) still emits string-named `HirExpr::Call`, so the "raw-name dispatch is removed" invariant is preserved in codegen only, not at the HIR boundary.
- **Recommendation.** Enumerate lowering call sites in M3: `sifr_lowering/src/lower/builtin_calls/{bytes_len_range.rs, constructors.rs}`, encoding method-call lowering, and the `open` shadowing lowering. Acceptance must require zero string-named `HirExpr::Call` for the 17 typed IDs.

### 5. Removing E2E `infer_dependencies` may reveal additional production-side gaps that M2 does not commit to fixing
- **Evidence.** Beyond `metrics`/`tracing`, `harness_model.rs:412-513` also patches five module dependencies (`_sifr.fs`, `_sifr.net`, `_sifr.tls`, `_sifr.http`, `_sifr.signal`) and ~25 direct crates (`bytes`, `hyper`, `h2`, `http_body`, `cookie`, etc.) based on generated Rust content. Each patch exists because production `SysrootDependencyPlan` for some code path missed the dependency at some point in the migration.
- **Failure scenario.** M2 acceptance ("A fixture that passes grouped E2E has the same dependency plan it receives under standalone production build") assumes production is currently correct for every fixture. If it isn't (e.g., HTTP client crates without a corresponding `_sifr.http` module dependency), M2 either fails or must silently expand scope. The plan does not commit to fixing these.
- **Recommendation.** Add explicit M2 tasks: (a) enumerate every dependency currently added only by `infer_dependencies`; (b) for each, either prove it is already covered by `SysrootDependencyPlan` for its source-driven use, or fix compiler metadata in this milestone. Land the enumeration in the plan itself so scope is not open-ended.
