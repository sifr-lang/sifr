## Review: GitHub-hosted self-update channels

### Blockers

**B1. Workflow has no concurrency guard — two simultaneous runs can lose a channel update.** `.github/workflows/preview-release.yml` has no `concurrency:` block. The "Generate channel metadata asset" step is a classic read-modify-write: it fetches the current `channels.json`, overrides one channel slot, and re-publishes. If an alpha run and a beta run dispatch within a few minutes of each other:

- Run A reads `{alpha: a4, beta: b4}` → writes `{alpha: a5, beta: b4}`
- Run B reads `{alpha: a4, beta: b4}` (before A's upload propagates) → writes `{alpha: a4, beta: b5}`
- Channels.json ends up with `{alpha: a4, beta: b5}`; Run A's alpha bump is silently lost, but Run A's VERSION release still exists on GitHub.

Add a `concurrency:` group keyed on the `channels` release (e.g., `group: preview-release-channels`, `cancel-in-progress: false`) so the channel-metadata publication is serialized regardless of which preview channel is being cut. `create_new_version.sh` has the same race shape when invoked locally with `--mutation-mode github`, but at least operators run that one at a time by convention.

**B2. Channel-metadata bootstrap is brittle on a partial-channel repo.** `.github/workflows/preview-release.yml:225-227` does `raise SystemExit("could not bootstrap channels metadata from public GitHub prereleases")` whenever `set(latest) != {"alpha", "beta"}`. This fires whenever a fresh repo has zero prereleases, or has releases for only one of the two channels. The override block at `:250-256` already knows the current CHANNEL/VERSION, so the safer rule is: if a channel is missing from the bootstrap result, fill the *current* channel with `VERSION` and only abort if the *other* channel is still unknown. As written, the very first preview-release dispatch after this lands has to be preceded by a hand-bootstrapped `channels` asset, but that precondition is documented nowhere (see D1).

**B3. The workflow publishes channels.json without any agreement check.** The new workflow runs `generate_channel_metadata.sh` and `gh release upload channels` but never invokes `verification/areas/distribution_release/tools/validate_self_update_metadata.sh`. So a malformed bootstrap output, an installer-generation regression, or an asset-upload failure can still ship a `channels.json` that points at a tag/asset that does not actually exist. At minimum the workflow should do a post-publish verification: after the `${VERSION}` upload, parse `channel-metadata/channels.json`, then `gh release view "${VERSION}" --json assets` and assert that `sifr-installer-${VERSION}` is present and non-empty. Otherwise the safety the validator gives `create_new_version.sh` real-runs has no analogue on the CI path.

### High-risk findings

**H1. "Verify complete asset set" does not verify the installer asset.** `.github/workflows/preview-release.yml:146-167` only checks each `sifr-${VERSION}-${target}.tar.gz` + `.sha256`. The new asset `release-assets/sifr-installer-${VERSION}` (generated at `:169-176`) is uploaded via the wildcard at `:296` without any existence / size / shebang check. The Rust runner does `MIN_INSTALLER_BYTES=1024` + shebang validation at install time (`self_update_runner.rs:166-201`), so a malformed installer would be caught client-side — but only *after* `channels.json` already points at it and every self-updating client has already failed once. Add a small "verify installer asset" step that mirrors the runner's two checks (size ≥ 1024 bytes, first line starts with `#!`) before the prerelease publish step.

**H2. The published `channels.json` and the version installer asset can drift across the GitHub side and the site side.** `create_new_version.sh` writes both (site `versions/<version>` + GitHub `sifr-installer-<version>` from the same generated bytes, plus the `channels.json` upload). The new GitHub workflow only writes the GitHub side. Nothing keeps the website `versions/<version>` and `index/alpha/beta` dispatchers in sync with the GitHub installer asset bytes — the curl-installer path (`sifr.sh/install`) can lag the self-update path indefinitely. The PR's architecture allows this divergence, but the docs (`internal_docs/distribution_pipeline.md`) do not name an authoritative path or describe the operator workflow that reconciles them. If the workflow is meant to be the source of truth and `create_new_version.sh` is for the site-only deploy, say so explicitly; otherwise both paths need to publish to both targets.

**H3. Stale `metadata/channels.json` on the live site.** The previous architecture served `https://sifr.sh/install/metadata/channels.json`. The PR removes generation from `generate_dispatchers.sh` and removes the site-checked path in the validator, but does not delete the existing asset from the website deployment or from a deployment-removal checklist. Until the next site deploy purges `apps/sifr-site/public/install/metadata/`, that URL will continue serving an old version map (which any old client cached for the URL would still trust). The fixture clean-up in `verification/.../cases/common.sh:169-170` only affects test repos. Add a site-deploy step (or an explicit checklist item in `internal_docs/distribution_pipeline.md`) that removes `public/install/metadata/` on the next site rollout.

### Medium / nits

- `create_new_version.sh:307-323` calls `gh release create … --notes-file` then unconditionally `gh release edit … --notes-file` even on the just-created path — harmless but redundant.
- `scripts/distribution/generate_channel_metadata.sh:49-55` accepts `rc` in the regex and then rejects it via the explicit alpha/beta check; either drop `rc` from the regex or reuse the same channel allowlist used in `self_update_metadata.rs::parse_channel` to keep gating rules in one place.
- `crates/sifr/src/self_update_metadata.rs:88-93`: `self.text` is interpolated twice in the URL; minor readability win to bind `let version = &self.text;` once.

### Test gaps

- The new Python bootstrap block lives inline in the workflow YAML (`preview-release.yml:192-232`). Untestable in isolation. Promote it to `scripts/distribution/bootstrap_channel_metadata.sh` (or .py) and add a unit/verification case covering: both channels present, only one present, none present, draft releases skipped, tags with weird suffixes ignored. Otherwise B2 is impossible to regression-test.
- `create_new_version_real_run_plan_reuse.sh:49-50` checks `APP_VERSION` in both the site copy and the work-dir copy of the installer but does not assert byte equality. Add a `cmp "${INSTALLER_ASSET_FILE}" "${INSTALL_ROOT}/versions/${VERSION}"` so a future refactor cannot accidentally regenerate (vs. copy) and introduce divergence.
- No case covers `validate_self_update_metadata.sh` against a `channels.json` whose `alpha`/`beta` versions are well-formed but have no corresponding entry under `${INSTALL_ROOT}/versions/`. The existing drift fixtures construct the install root via `make_self_update_install_root_fixture` which always provides both. A missing-installer case would catch B3-class failures.

### Documentation drift

- **D1.** `internal_docs/distribution_pipeline.md` does not explain how the `channels` release tag is first created, nor the bootstrap precondition (both alpha and beta prereleases must exist). Add a "First-time setup" sub-section with the exact `gh release create channels …` invocation and an explicit "run this once before the first dispatch."
- **D2.** Neither `docs/self_update.md` nor `internal_docs/distribution_pipeline.md` documents that GitHub asset downloads redirect through `objects.githubusercontent.com`. The runner's `--proto =https --proto-redir =https` (`self_update_runner.rs:76-92`) correctly handles this, but it's worth a one-line callout under "Self-Update TLS And Delegation Policy" so future reviewers don't mistake the redirect for a TLS-policy violation.
- **D3.** `internal_docs/distribution_pipeline.md:225-238` lists the drift validator under "Installer artifact validation" but never says when in the release flow operators are expected to run it. Add: "Run after every `create_new_version.sh --real-run` and before the next `git push` on the site repo."

### Not a blocker

- `installer_url()` is correctly derived from a compile-time constant base + the version string (no env override), preserving the "metadata is resolution-only, never executable URL" invariant from prior reviews.
- `parse_channel` / `ChannelMetadata::parse` still rejects `stable`/`rc`, matching the workflow's input validation. Tests cover both.
- The new flow is consistent with `self_update_runner.rs`'s existing download / shebang-validate / lock / delegate sequence; no runtime changes needed in the runner.

**Bottom line:** B1, B2, and B3 should block merge. H1–H3 are operationally hazardous and worth fixing in this PR rather than as follow-ups. Everything else is low-risk and can be batched.
