### Notes (non-blocking, FYI for follow-up waves)

- **Stale intrinsic catalog entries.** `crates/sifr_stdlib_model/src/crypto_regex_uuid.rs::intrinsic_crypto()` still declares `sha256`, `sha256_bytes`, `md5`, `md5_bytes` (and presumably the others further down in the file) in the catalog. The fallback path now guards on `!fn_exports.contains_key(name)`, so the dead-code lookups are harmless today, but a future change that broadens fallback routing could accidentally re-route hash names. Worth trimming when wave 6 (base64/base32) lands.
- **Transitive cargo bloat.** With `_sifr.crypto → ["hash", "random"]` (generated_stdlib_features.rs:50), any user binary that pulls in `sifr.base64`/`sifr.random`/`sifr.secrets`/`sifr.tempfile` now also turns on the `hash` feature on `sifr_stdlib`, dragging blake2/md5/sha1/sha2_0_11 into the dep graph even though those callers never touch the helpers. This is the acknowledged cost of the partial migration and unwinds naturally once the remaining `_sifr.crypto` leaves move.
- **Test coverage.** `hash_leaf_matches_known_digest_vectors` only checks known vectors for SHA-256/MD5/SHA-1; SHA-224/384/512/Blake2b/Blake2s are only length-checked. Acceptable (the underlying crates ship their own test vectors), but adding one canonical vector per algorithm would lock down the hex formatting too.
- **`trusted_no_panic` contract.** Each helper in `hash.rs` is panic-free (digest crate APIs are infallible on `&[u8]`; `hex_digest` indexes a 16-byte table with values `0..=15`). The annotation is honest today — a future `.unwrap()`/`.expect()` slipping in would silently break trust; consider adding a clippy `#![warn(clippy::unwrap_used, clippy::expect_used)]` scope or an audit note if not already covered crate-wide.
